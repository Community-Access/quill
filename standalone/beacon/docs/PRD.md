## 1. Executive product decision

QuillBeacon will be an accessible, local-first, cross-platform navigation and knowledge application that lets a person save, organize, search, reopen, and share not only *things*, but exact *places within things*.

A conventional bookmark manager saves a web address. QuillBeacon will save context:

- A website.
- A heading, landmark, form field, passage, or anchor within a website.
- A local or cloud folder.
- A file.
- A heading, page, paragraph, selection, comment, or other location inside a document.
- A source-code repository, branch, file, symbol, line, issue, or pull request.
- A podcast show.
- A podcast episode.
- A publisher-provided podcast chapter.
- A user-created podcast chapter.
- A precise podcast or audio time point.
- A transcript passage tied to a media position.
- A radio station or stream.
- A recurring radio program.
- A live-stream moment, when the provider supports replay or catch-up.
- A video, chapter, time range, or transcript passage.
- An email, calendar event, application workspace, or any resource addressable through a URI or supported platform integration.
- A relationship among several resources, such as “this document explains the podcast segment I saved here.”

The product should feel less like a database and more like an accessible map of a person’s digital world.

QuillBeacon must be:

1. **Delightfully accessible from the first launch.**
2. **Native in interaction and presentation on each operating system.**
3. **Fast enough to use as an extension of memory.**
4. **Private by design.**
5. **Local-first and fully useful offline.**
6. **Synchronizable through QuillSync without surrendering ownership of the data.**
7. **Extensible enough to support resource types that do not exist yet.**
8. **Closely interconnected with the rest of the QuillVille ecosystem.**

## 2. Product name and brand

### 2.1 Recommended name: QuillBeacon

**QuillBeacon** is the recommended product name.

A beacon helps someone orient, return, locate, and continue. That metaphor applies equally well to web bookmarks, document positions, podcast chapters, audio time points, radio stations, folders, projects, and future resource types.

The term is broad enough to grow beyond bookmarks while remaining understandable.

### 2.2 Product language

The user interface should preserve familiar terminology while allowing the brand to add warmth.

- **Bookmark:** The conventional user-facing term for a saved item.
- **Beacon:** The QuillBeacon identity for a bookmark or saved destination.
- **Collection:** A user-created grouping of Beacons.
- **Smart Collection:** A live collection generated by a saved search.
- **Location:** A precise place within a resource.
- **Time Point:** A precise position in audio or video.
- **Chapter:** A publisher-created or user-created media section.
- **Trail:** An optional ordered sequence of related Beacons used as a reading list, workflow, lesson, research path, or media queue.
- **Inbox:** A temporary landing place for newly captured material.
- **Health:** Whether a Beacon is available, moved, changed, offline, or requires attention.

The default interface should use familiar words such as “Bookmark,” “Folder,” “Chapter,” and “Search.” Branded words must never be required knowledge. For example:

> Bookmark added to QuillBeacon.

not:

> Beacon crystallized into the luminance trail.

Clarity always wins.

## 3. Product vision

### 3.1 Vision statement

QuillBeacon gives every person an accessible, dependable, and private way to mark any meaningful digital destination and return to it instantly, on any supported device, with the original context preserved.

### 3.2 Product promise

> Save the exact place. Understand why it mattered. Find it again in seconds. Continue on any device.

### 3.3 The larger opportunity

People do not merely lose URLs. They lose:

- The heading they intended to revisit.
- The exact section in a policy document.
- The point in a podcast where an important idea was discussed.
- The folder containing a project deliverable.
- The radio stream they enjoyed.
- The reason they saved something.
- The connection between several related items.
- The context of what they were doing at the time.
- Their position when changing devices.
- Access when a page changes, a file moves, or a provider disappears.

QuillBeacon should solve the full “return to context” problem.

## 4. Product principles

### 4.1 Accessibility is the architecture

Accessibility is not a review phase. It determines the information model, navigation model, control selection, focus behavior, keyboard model, synchronization feedback, error recovery, media experience, and test strategy.

### 4.2 Local-first, cloud-connected

Every primary action must work locally. QuillSync adds continuity, backup, controlled sharing, and multi-device synchronization.

### 4.3 Native where the user touches it

The product may share a portable engine, data model, search system, and sync implementation, but its visible controls, menus, keyboard behavior, accessibility APIs, share surfaces, and platform conventions should be native.

### 4.4 Exact locations with graceful fallback

A saved location may become invalid when content changes. QuillBeacon must store multiple locator strategies and recover as close to the original destination as possible.

### 4.5 Search before filing

Users should not be forced to construct a perfect hierarchy. Powerful search, filters, recent context, and Smart Collections should make capture effortless.

### 4.6 User ownership

Users can export their library in open, documented formats. No essential capability should depend on a proprietary cloud copy.

### 4.7 Interconnection without lock-in

QuillBeacon should work beautifully with QUILLE and QuillSync while still supporting standard URLs, files, RSS, OPML, JSON, Markdown, HTML, M3U, and platform deep links.

### 4.8 Delight without mystery

Helpful automation is welcome. Invisible, irreversible, or unexplained automation is not.

## 5. Goals

### 5.1 Primary goals

1. Save resources and precise locations with minimal effort.
2. Return to saved destinations reliably.
3. Search the full library quickly and accessibly.
4. Synchronize data securely through QuillSync.
5. support Windows and macOS with genuinely native user experiences.
6. Prepare the architecture for iOS without redesigning the data model.
7. Provide first-class podcast, podcast episode, chapter, timestamp, transcript, radio, and media support.
8. Integrate tightly with QUILLE and future QuillVille applications.
9. Import existing bookmarks and subscriptions.
10. Preserve privacy, portability, and offline access.

### 5.2 Success definition

A blind keyboard and screen-reader user should be able to:

- Add a web page, file, folder, document heading, podcast episode, podcast chapter, timestamp, or radio stream without needing a mouse.
- Find a saved item among tens of thousands of records in seconds.
- Understand every result’s type, location, source, and state.
- Open the exact destination or receive a clear explanation and recovery choices.
- Move between Windows, Mac, and iPhone without manually recreating context.
- Create, edit, reorder, filter, export, and share collections without inaccessible drag-and-drop.
- Navigate media chapters and time points with efficient keyboard or gesture commands.
- Use the application without animation, color, spatial layout, or visual-only metadata.

## 6. Non-goals for the initial release

The first release will not attempt to be:

- A complete replacement for every web browser.
- A full document editor.
- A full cloud-drive provider.
- A social network.
- A general-purpose password manager.

- A commercial podcast hosting platform.
- A full digital audio workstation.
- A universal screen-scraping automation platform.
- An enterprise records-management or legal-hold system.

Some of these may become integrations, but they should not distort the first product architecture.

12. **When I leave the platform, let me take my data with me.**

## 10. The universal location model

A central innovation is the **Universal Location Descriptor**, or ULD.

A ULD stores several ways to return to the same place. It does not trust a single fragile coordinate.

### 10.1 Locator layers

1. **Canonical resource identity**
   - Normalized URL.
   - File identity or cloud provider item ID.
   - Podcast feed GUID.
   - Podcast episode GUID and enclosure identity.
   - Document stable ID.
   - Repository and commit identity.

2. **Native locator**
   - Named anchor.
   - PDF named destination.
   - EPUB CFI.
   - Word bookmark.
   - Podcast chapter start time.
   - Media fragment.
   - Source-code symbol.

3. **Structural locator**
   - Heading path.
   - Landmark and accessible name.
   - Document outline path.
   - Page and paragraph context.
   - Table name, row key, and column name.
   - Chapter hierarchy.

4. **Text-quote locator**
   - Exact selected text.
   - Prefix and suffix context.
   - Normalized fingerprint.
   - Language.

5. **Positional locator**
   - Line and column.
   - Page number.
   - Character offset.
   - Timestamp or time range.
   - Scroll percentage.
   - Spreadsheet cell.

6. **Recovery hints**
   - Previous title.
   - Previous surrounding headings.
   - Content hash.
   - Last successful destination.
   - Prior resource address.
   - User note.

### 10.2 Recovery behavior

When opening a location, QuillBeacon should:

1. Try the strongest native locator.
2. Try structural matching.
3. Try exact text matching.
4. Try fuzzy text and surrounding-context matching.
5. Try the last known positional locator.
6. Open the containing resource and announce that the exact location could not be confirmed.
7. Offer:
   - Open nearest match.
   - Review possible matches.
   - Update the Bookmark to the current location.
   - Keep the original location.
   - Mark as broken.
   - Locate manually.

The system must never silently replace an exact bookmark with a guessed location.

## 11. Podcast and episode design

Podcast support is a first-class product area.

### 11.1 Bookmarkable podcast entities

Users can save:

- A show.
- A feed.
- A season.
- An episode.
- A publisher chapter.
- A user chapter.
- A time point.
- A time range.
- A transcript quote.
- A link shown or discussed at a particular time.
- A listening position.
- An episode note.
- A relationship between an episode segment and another Beacon.

### 11.2 Chapter sources

QuillBeacon should detect and normalize chapters from:

1. Podcasting 2.0 JSON chapters.
2. Embedded ID3 CHAP and CTOC frames.
3. Feed or provider metadata.
4. Supported transcript metadata.
5. User-created chapters.
6. Optional locally generated suggested chapters.

The interface must identify the source:

- Publisher chapter.
- Provider chapter.
- Automatically suggested chapter.
- Personal chapter.
- Shared collection chapter.

### 11.3 Personal episode chapters

A user can create a chapter with:

- Title.
- Start time.
- Optional end time.
- Note.
- Tags.
- Related links.
- Transcript selection.
- Optional chapter artwork reference.
- Visibility: private, shared collection, or exported.

Personal chapters must not alter the publisher’s original media.

### 11.4 Time-point capture

From the media player, the user can invoke **Add Bookmark at Current Time**.

The capture form should prefill:

- Episode title.
- Show title.
- Current chapter.
- Current playback time.
- A short transcript excerpt, when available and permitted.
- Current playback speed.
- Source feed.
- Date captured.

The user can then:

- Add a title.
- Dictate or type a note.
- Add tags.
- Choose a collection.
- Convert the point into a chapter.
- Set an optional end point.
- Link another Beacon.
- Add to Listen Later or a Trail.

### 11.5 Chapter and time-point navigation

Required commands:

- Next chapter.
- Previous chapter.
- Open chapter list.
- Add time point.
- Start a time range.
- Finish a time range.
- Jump to time.
- Copy timestamp.
- Copy accessible share text.
- Copy a standards-based temporal link when supported.
- Search transcript.
- Move to next saved time point.
- Move to previous saved time point.
- Announce current show, episode, chapter, and time.

### 11.6 Transcript-linked bookmarks

When a transcript is available, QuillBeacon can store:

- Selected transcript text.
- Start and end time.
- Speaker label when provided.
- Transcript source and language.
- A fingerprint for later reattachment if transcript formatting changes.

Search results may match transcript text and open playback at the corresponding time.

### 11.7 Continue listening

QuillBeacon should distinguish:

- **Playback position:** The automatic place where listening stopped.
- **Time-point Bookmark:** An intentional saved moment.
- **Chapter:** A bounded section.
- **Listening history:** A private activity record that can be disabled or cleared.

### 11.8 Podcast subscriptions and scope

The product should support RSS and OPML as open foundations.

Recommended phases:

- **Initial:** Save feed, show, episode, chapter, and time point; play or open through an installed app.
- **Expanded:** Built-in accessible player, feed refresh, episode list, transcript view, listening queues, and download control.
- **Advanced:** Optional full subscription management, cross-device playback state, smart queues, private transcript indexing, and QuillSync-shared episode collections.

This prevents the first release from becoming an unfinished full podcast client while preserving a path toward one.

## 14. Capture experience

### 14.1 Capture modes

#### Instant capture

Saves immediately to Inbox with sensible metadata.

#### Guided capture

Opens an accessible form for title, note, collection, tags, location, and privacy.

#### Capture exact location

Uses an integration to preserve the current heading, selection, page, line, chapter, or time point.

#### Capture bundle

Saves several open tabs, selected files, or related resources as a Collection or Trail.

### 14.2 Global capture command

Desktop should offer a user-configurable global shortcut.

Recommended default candidate:

- Windows: `Ctrl+Alt+B`
- macOS: `Control+Option+Command+B`

Defaults must be configurable because assistive technologies and other applications may already use them.

### 14.3 Quick capture form

Fields:

- Title.
- Resource.
- Exact location summary.
- Note.
- Collection.
- Tags.
- Favorite.
- Add to Trail.
- Offline availability.
- Privacy and sharing.
- Save.
- Save and open.
- Cancel.

The form must support:

- Direct tab order.
- Field-specific keyboard shortcuts.
- Screen-reader labels and descriptions.
- No inaccessible token controls.
- Tag entry as both autocomplete and a conventional editable list.
- Undo after save.

### 14.4 Context captured automatically

Depending on source and permission:

- Window or document title.
- URL or path.
- Heading path.
- Selected text.
- Surrounding text.
- Page or line.
- Media time.
- Chapter.
- Source application.
- Date and device.
- Content type.
- Canonical address.
- Feed and episode identity.
- Referrer or parent resource.
- Optional screenshot or snapshot only when the user enables it.

Sensitive context capture must be transparent and controllable.

### 14.5 Capture routing rules

Users can define an ordered list of routing rules that file new web bookmarks
into a folder automatically. Each rule maps one **URL keyword** -- a domain
name (`github.com`) or any text a URL could contain (`/recipes/`) -- to one
folder.

Requirements:

- Matching is a case-insensitive substring test against the captured URL.
- The rule list is ordered; the **first matching rule wins** when a URL
  contains more than one keyword.
- One keyword maps to one folder. A keyword cannot be reused across rules;
  the editor rejects duplicates (case-insensitive).
- Rules apply to web bookmarks from every capture surface: browser
  extension, quick capture, clipboard, CLI, and imports.
- Rules apply only when the user did not explicitly choose a folder at
  capture time. An explicit choice always wins.
- A routed bookmark still lands in the Inbox; routing files it without
  removing it from review.
- Files, folders, podcasts, radio, and non-web URIs are never routed.
- The rules editor must be fully keyboard operable, with an accessible
  reorder mechanism (Move Up / Move Down buttons, not drag-and-drop).

- Tags.

- Selected text.

- Radio station, program, host, genre, region, and metadata.
- Related-resource titles.
- Source application.
- Created, modified, last opened, and last validated dates.
- Resource health.
- Custom fields.
- OCR text for user-approved snapshots.
- Semantic index, when enabled.

### 15.2 Search behavior

Search must be:

- Incremental.
- Typo tolerant.
- Accent insensitive when appropriate.
- Case insensitive by default.
- Fast with large libraries.
- Keyboard efficient.
- Screen-reader stable.
- Explainable.
- Available offline.
- Able to narrow without clearing the user’s query.
- Able to search within the current collection or across everything.
- Able to search exact phrases.
- Able to exclude terms.
- Able to search fields.
- Able to search dates and ranges.
- Able to find near-duplicates.

### 15.3 Query examples

```text
podcast accessibility chapter
type:episode tag:research
type:timepoint show:"Living Blindfully"
domain:arizona.edu heading:policy
type:folder project quill
collection:"Title II" modified:last30days
health:broken
has:note not:archived
type:radio language:English
transcript:"code signing"
added:today
opened:never
```

- Duration.

- Has transcript.

The dialog generates the query and allows saving it as a Smart Collection.

## 16. Organization model

### 16.1 Collections

A Beacon can belong to multiple Collections without duplication.

Collections may be:

- Private.
- Shared.

## 23. QuillSync architecture

### 23.1 Sync principles

- Local database is authoritative for the local experience.
- Sync is incremental.
- Offline edits are allowed.
- Server stores the minimum required information.
- Private content is end-to-end encrypted by default.
- Sync is resumable.
- Duplicate operations are idempotent.
- Every change has an audit-friendly local history.
- Deleting on one device does not instantly destroy recoverability on all devices.

### 23.2 Recommended server architecture

- Authentication and device registry.
- PostgreSQL for account, device, collection membership, and encrypted object metadata.
- Object storage for encrypted attachments and optional snapshots.
- Append-only operation log or versioned change records.
- Push notification service carrying only opaque change hints.
- Rate limiting and abuse controls.
- Regional and retention strategy documented before production.

### 23.3 Encryption model

Recommended approach:

1. A vault master key is generated client-side.
2. Data objects use per-object or per-collection data-encryption keys.
3. Keys are wrapped by the vault key.
4. The user’s vault key is protected through a recovery design that is understandable and accessible.
5. Shared Collections use separate collection keys distributed to authorized members.
6. The server cannot read private titles, notes, URLs, transcript quotes, paths, or attachment content.
7. Device revocation rotates or rewraps affected keys when necessary.

This design means server-side plaintext search is not available for private data. Search occurs locally after encrypted synchronization, which aligns with the local-first model.

### 23.4 Recovery options

The product must not create a recovery flow that is impossible for screen-reader users.

Possible options:

- User-generated recovery phrase.
- Printable and downloadable recovery kit.
- Trusted-device approval.
- Optional organization-managed recovery for enterprise deployments.
- Explicit warning that losing every authorized device and recovery method may make end-to-end encrypted data unrecoverable.

### 23.5 Sync conflict policy

Most fields can use deterministic field-level merge rules.

Examples:

- Adding different tags on two devices merges both.
- Removing a tag conflicts only if another device edits the same tag relationship.
- Notes use version history and a merge editor when concurrent changes overlap.
- Manual Trail order uses stable position identifiers.
- Deletion creates a tombstone and a recoverable Trash period.
- Playback position may use the latest meaningful progress, not simply the latest timestamp, to avoid moving backward unexpectedly.
- User-created chapter boundaries require a conflict review when both devices edit the same chapter.

### 23.6 Device handoff

A **Continue on Device** action can send an encrypted handoff request:

- Open this Bookmark.
- Continue this podcast episode at this position.
- Open this Collection.
- Continue this Trail.
- Open this document location in QUILLE.

The receiving device must confirm unsupported applications or unavailable local paths and offer alternatives.

## 37. Example end-to-end experiences

### 37.1 Save a document hotspot

1. Jeff is reading a policy in QUILLE.
2. He moves to the heading “Alternative Formats.”
3. He invokes **Add Bookmark at Current Location**.
4. QuillBeacon captures the file identity, heading path, selected paragraph, text context, and caret position.
5. He adds the note “Discuss with leadership after ACB.”
6. On another device, he searches `leadership alternative formats`.
7. QUILLE opens the document at the heading and announces it.
8. If the document changed, QuillBeacon offers the nearest verified match.

### 37.2 Save a podcast chapter and precise point

1. A podcast provides 12 chapters.
2. The chapter list is exposed as a native list.
3. Jeff opens “Building Accessibility into the Architecture.”
4. At 22:41, he presses **Add Time Point**.
5. The title, show, episode, chapter, timestamp, and transcript excerpt are captured.
6. He adds the note “This belongs in the QuillBeacon PRD.”
7. Later he searches `architecture podcast PRD`.
8. The result announces the episode, chapter, and time.
9. Opening starts playback at 22:41.

### 37.3 Create a personal podcast chapter

1. An episode has no publisher chapters.
2. Jeff starts a user chapter at 14:10.
3. He ends it at 26:35 and names it “Accessible Search Design.”
4. He adds related web and document Beacons.
5. The chapter becomes a searchable item and a step in a Trail.
6. It remains clearly labeled as a personal chapter.

### 37.4 Save a live radio moment

1. Jeff is listening to a station.
2. He invokes **Save What Is Playing Now**.
3. QuillBeacon stores station, stream, local time, time zone, current program metadata, and his note.
4. The station has no replay service.
5. The Bookmark clearly says that the original moment may not be replayable but preserves the station and context.
6. If a later archived episode is discovered, QuillBeacon can suggest linking it after user approval.

### 37.5 Continue a cross-device Trail

1. Jeff creates a Trail containing a web article, a policy heading, two podcast chapters, and a project folder.

4. On iPhone, Home offers **Continue Trail, step 3 of 5**.
5. VoiceOver announces the next podcast chapter.
6. On Mac, he completes the final folder-based step with an appropriate platform fallback.

## 38. Risks and mitigations

### 38.1 Exact-location fragility

**Risk:** Web pages and documents change.

**Mitigation:** Multi-layer locators, confidence scores, recovery review, content fingerprints, and repair history.

### 38.2 Product scope explosion

**Risk:** Bookmarks, podcasts, radio, documents, sync, and collaboration could become several products.

**Mitigation:** One universal model, phased delivery, external-player handoff before a full player, and strict MVP exit criteria.

### 38.3 Native multi-platform cost

**Risk:** Separate platform shells increase work.

**Mitigation:** Share the Rust core, schemas, tests, protocol, and design language while keeping native interaction surfaces.

### 38.4 Encryption recovery complexity

**Risk:** Users may lose access.

**Mitigation:** Accessible recovery kit, trusted-device recovery, clear education, and optional managed recovery models.

### 38.5 Search index size

**Risk:** Transcripts and snapshots create large indexes.

**Mitigation:** User-controlled indexing, per-source limits, rebuildable caches, storage dashboards, and optional offline packs.

### 38.6 Inconsistent podcast metadata

**Risk:** Feeds, GUIDs, chapters, and transcripts vary.

**Mitigation:** Normalize multiple standards, retain provenance, use enclosure and content fingerprints, and allow manual correction.

### 38.7 Live radio impermanence

**Risk:** A saved moment may not be replayable.

**Mitigation:** Communicate capability accurately and store program context without promising replay.

### 38.8 Accessibility regressions

**Risk:** New custom controls or framework updates reduce accessibility.

**Mitigation:** Native controls, automated API inspection, assistive-technology smoke tests, manual release gates, and accessibility-owned acceptance criteria.

## 44. Implementation plan (grounded in the QUILL stack)

This section maps the product vision onto the real QUILL engineering stack so
delivery is concrete rather than aspirational. It is the bridge between the
PRD and the first running code.

## 44.1 Architecture decision (revised against the real stack)

QuillBeacon follows the established QUILL companion-app pattern proven by
**Quill Cast** (`quill-cast`) and **Quill Radio** (`quill-radio`):

- A **thin standalone product repo** (this one) that anchors the frozen
  build environment and hands off to the engine, exactly like
  `quill_cast/launcher.py` and `quill_radio/launcher.py`.
- The **engine and UI live in the `quill` package** as
  `quill/apps/beacon.py`, reusing `quill.ui.app_shell.AppShellFrame` plus a
  `BeaconMixin`, the same way `RadioAppFrame(AppShellFrame, RadioMixin)`
  reuses the radio feature without reimplementing menus, tray, commands, or
  accessibility plumbing.
- Shared infrastructure is reused, not reinvented:
  - `quill.core.paths.app_data_dir` for the local store location.
  - `quill.core.storage.read_json` / `write_json_atomic` for atomic config.
  - `quill.core.commands.CommandRegistry` for the command palette.
  - `quill.core.a11y_regions.RegionTracker` for named regions and focus.
  - `quill.platform.announce_engine.AnnouncementEngine` for spoken/log
    status, and `quill.ui.dialog_contract.set_accessible_name` for labels.
  - `quill.stability.task_manager.TaskManager` for background indexing.
- The local store is **SQLite with FTS5** (WAL mode, transactional
  migrations), matching the PRD's storage recommendation and the stack's
  existing SQLite use. No new language runtime (Rust) is introduced for the
  first phase; the portable-core recommendation in section 19 is retained as
  a later optimization once the data model and ULD are proven in Python.

Rationale: the PRD's section 19 recommends a shared portable core with
native shells. QUILL's existing companion-app architecture already delivers
the "shared core, native shell" property for Windows and macOS using wxPython
plus platform-native accessibility, so QuillBeacon adopts it instead of
spinning up a parallel Rust toolchain. The ULD, search grammar, JSON schema,
and sync protocol remain provider-neutral and portable to a Rust core later
without redesign.

## 44.7 Second-pass in-repo completions

The gaps left after 44.6 are now closed, all inside this repo and covered by
tests. Each item is fail-safe: nothing leaves the machine by default, and
every network surface is behind an injectable or optional dependency.

- **Conflict review (PRD 23.5, 45.6):** `SyncController` persists note conflicts
  to `sync_conflicts.json` (deduped by entity + field while unresolved).
  `SyncHistoryDialog` lists unresolved conflicts and offers Use Local / Use
  Remote / Use Merged; `resolve_conflict` applies the choice to the beacon note
  and marks the conflict resolved. Conflicts are note-only (the only field
  `beacon_merge` surfaces a conflict for).
- **Cross-device vault pairing (PRD 45.7):** `export_vault_pairing` /
  `import_vault_pairing` share the scrypt salt so a second device derives the
  same vault key; the passphrase is entered on each device and never
  transferred. Pair Device action in Sync Settings (import replaces the local
  vault, with a warning).
- **Server hints badge (PRD 45.5):** `fetch_hints` calls `/sync/hints` and the
  Status Center shows "N new" / "up to date" / the error string. Fail-safe: no
  server, no token, missing requests, or an unreachable host all return an error
  dict, never raise.
- **Incremental sync (PRD 45.8):** schema v2 adds `beacons.updated` /
  `beacons.dirty` and a `beacon_tombstones` table (additive v1->v2 migration
  backfills `updated` from `date_added`). `sync_now` commits only dirty beacons
  plus pending tombstones after the first full snapshot, then clears the
  markers once the commit is in the local log (a later failed push still
  retries from the log, so no change is lost). `dirty` is device-local and
  never serialized in a record, so pulls never cause re-commit ping-pong.
  `trash`/`restore`/`archive`/`delete_permanent` all set the markers so they
  propagate. `open_count` is intentionally device-local and not synced.
- **Attachments UI (PRD 24.1):** `AttachmentsDialog` lists a beacon's
  files/URLs/notes with add (file via Browse, URL, or inline note), view (OS
  default handler for file/URL, a popup for notes), and remove. Edit menu
  (Ctrl+Shift+E). Attachments stay local-only, never synced as blobs.
- **Trails step-through (PRD 17.4):** trails appear in the sidebar with
  `done/total` progress; selecting one opens `TrailStepDialog` -- a listbox of
  steps with per-step notes, Previous/Next (persisted `current_step`), Mark
  Complete, and Open Current (hands the beacon back to the shell to read in
  place). Progress is announced.
- **Smart Collections manager (PRD 15.6):** `SmartCollectionsDialog` to edit
  (name/query/sort/scope) or delete saved searches, with `SmartCollectionEditorDialog`
  for the form. Tools menu. Deleting a Smart Collection never touches the
  bookmarks it matched.
- **Bulk add-to-collection + remove-tag (PRD 18.5):** two new Edit-menu bulk
  ops, each a single composite undo step. Bulk Remove Tag offers the tags
  present across the selection (Ctrl+Shift+V); Bulk Add to Collection creates
  the collection if needed (Ctrl+Shift+O).
- **Health revalidation (PRD 13.4, 17.4):** `quill_beacon/health.py` rechecks
  each beacon's resource. Local files/folders are checked against the
  filesystem; web links are checked only when a fetcher is supplied (no
  network by default -- web URLs are "skipped", health unchanged). Tools >
  Revalidate Health confirms before any network use and reports
  checked/available/broken/skipped. A failed check never aborts the batch.
- **Optional auto-sync timer (PRD 45.10; off by default):** `SyncConfig.auto_sync_seconds`
  (0 = off) drives a `wx.Timer` in the shell that fires `sync_now` on the
  chosen interval only when sync is configured and the vault is unlocked. Sync
  > Auto Sync picker (Off / 5 / 15 / 30 / 60 min). The timer is stopped on
  close and re-applied when transport is configured.

## 45. QuillSync implementation plan (aligned with QUILL Sync)

Section 23 sketched a conventional PostgreSQL-plus-object-storage sync server.
The QUILL platform already has a sync design -- QUILL Sync in
`s:\quill\docs\planning\plan.md` -- that is better suited to QuillBeacon:
git-like, versioned, diffable, rollback-capable, end-to-end encrypted, and
bring-your-own-remote. QuillSync adopts that model instead of inventing a
second database. This section is the concrete implementation plan.

## 45.1 Model: the library is a repository

QuillBeacon's local store is already schema-validated, atomically-written
records (SQLite rows + FTS5). Sync treats the library as a versioned
repository, borrowing git's ideas rather than inventing a database:

- **Versioned.** Every change batch is a commit with a human-readable,
  screen-reader-friendly message ("Added 3 bookmarks, edited note on
  'Keyboard Interaction'"). History is browsable and speakable.
- **Diffable.** "What changed between this library today and last Tuesday?"
  is a first-class accessible question with a first-class answer (PRD 17.3
  context rewind reuses this).
- **Rollback.** One command restores any prior state of any synced scope. A
  bad bulk-edit experiment is never a disaster (supports PRD 32.2 integrity
  and undo).
- **Profiles.** A "work" and "home" profile share a common base with
  per-device overlays (different offline packs, same collections and tags).

This maps cleanly onto the Beacon/Resource/Location model: each entity row is
an object; a commit is an append-only set of puts and tombstones keyed by
entity id; the server stores encrypted blobs and an opaque commit graph, not
plaintext.

## 45.2 Transport: three tiers, cheapest first

Matching QUILL's $0-to-Jeff philosophy and the consent-first rule (sync is off
until the user turns it on):

1. **BYO git remote.** Point QuillSync at a private GitHub/GitLab/Gitea
   repo. QuillBeacon manages the plumbing; the user never sees a merge
   conflict marker. QUILL's existing paramiko/SSH key work is directly
   reusable.
2. **BYO folder.** Any synced folder (iCloud Drive, OneDrive, Dropbox,
   Syncthing) as the remote, using the same commit format on files. Zero
   accounts.
3. **Hosted QuillSync.** A small service for people who do not want to
   think about remotes. This is the only tier that costs money to run, so it
   ships last and never becomes required. The server plan below covers it.

## 45.3 Security (non-negotiable)

- End-to-end encryption before anything leaves the machine. The sync payload
  is encrypted with a user passphrase-derived key (Argon2id KDF to a 256-bit
  AEAD key), so a compromised remote leaks nothing.
- Per-object data-encryption keys wrapped by the vault key (PRD 23.3
  retained). Shared Collections use separate collection keys distributed to
  authorized members.
- Secrets never sync in plaintext; some (OS credential-manager entries) never
  sync at all. A **sync manifest** marks each scope as `syncable`,
  `encrypted-syncable`, or `local-only`.
- Every outbound call goes through QUILL's existing network egress audit.
- Recovery is accessible (PRD 23.4): recovery phrase, printable recovery kit,
  trusted-device approval. No recovery flow may be impossible for a screen
  reader.

## 45.4 Sync scopes, smallest first

1. **Preferences and tags.** Tag taxonomy, collections, smart collections,
   settings, terminology preference. Small, low-conflict, immediately
   valuable -- "sit down at any machine and it is your QuillBeacon."
2. **Library content.** Beacons, notes, locations (ULDs), relationships,
   trails. Text merges use a three-way/CRDT strategy tuned for prose;
   conflicts surface as an accessible "two versions" review flow, never as
   inline markers (PRD 23.5).
3. **Opt-in extras.** Personal podcast chapters, listening positions,
   offline-pack manifests, optional snapshots (size-controlled, opt-in per
   PRD SEC-013).

Scope 1 alone justifies the feature; scopes 2-3 are what make cross-device
continue and Trails sing.

## 45.5 Hosted QuillSync server architecture

The hosted tier is a small service. It stores encrypted blobs and an opaque
commit graph; it cannot read private titles, notes, URLs, paths, transcript
quotes, or attachment content (PRD 23.3). Search stays local.

Components:

- **Auth and device registry.** Account and device identity; device
  revocation rotates or rewraps affected keys (PRD 23.3). Passphrase login;
  per-device tokens.
- **Commit log.** An append-only log of encrypted commits per repository
  (library). Each commit references a parent commit id, an encrypted manifest
  of object ids, and opaque metadata. This is the git-like core; it gives
  history, diff, and rollback for free.
- **Encrypted object store.** Content-addressed encrypted blobs (per-object
  DEK, wrapped by the vault key). Deduplicated by ciphertext hash. S3-compatible
  object storage or a content-addressed filesystem layout.
- **Push hint service.** Carries only opaque "new commits available" hints to
  online devices via websockets/APNs/FCM. Never carries plaintext or even
  object ids that would leak structure.
- **Shared Collection membership.** PostgreSQL for account, device,
  collection membership, and encrypted collection-key distribution. The
  server brokers key wrapping to authorized members; it never holds an
  unwrapped collection key.
- **Rate limiting and abuse controls.** Per-device and per-account limits;
  egress audit hook shared with QUILL.
- **Retention and purge.** Documented tombstone and object-retention policy
  (PRD SEC-011). Deleted cloud objects follow a documented purge timeline.

Recommended stack: a small Python service (FastAPI) reusing QUILL's
egress-audit and crypto helpers, PostgreSQL for membership metadata,
S3-compatible object storage for blobs, Redis for push-hint fanout. No new
language runtime; the same Python crypto used client-side is used server-side
for key wrapping.

## 45.6 Client sync protocol

- **Local is authoritative.** Offline edits always allowed; sync is
  opportunistic (PRD 23.1, 32.1).
- **Incremental and resumable.** A sync exchanges commit deltas, not the
  whole library. Idempotent operations (PRD 23.1).
- **Conflict policy (PRD 23.5).** Field-level deterministic merge for tags
  and collections; three-way merge with an accessible review flow for notes
  and chapter boundaries; tombstones and a recoverable Trash period for
  deletions; playback position uses latest meaningful progress, not latest
  timestamp.
- **Audit-friendly local history.** Every change records device, timestamp,
  and scope (PRD 23.1, 32.2).
- **Device handoff (PRD 23.6).** An encrypted handoff request ("open this
  Beacon", "continue episode at position") is a special commit the receiving
  device confirms.

## 45.7 Sequencing

1. **Scope 1 client (BYO git remote).** Pure desktop work; settings and tags
   as a repo. Reuses QUILL's storage and SSH code. Valuable on day one, no
   server needed.
2. **Scope 2 client (library content).** Three-way merge and accessible
   conflict review solved on desktop first, where debugging is easier. BYO
   folder tier lands here.
3. **Hosted QuillSync (server).** The server plan in 45.5, shipping last,
   never required. Account, device registry, commit log, encrypted object
   store, push hints.
4. **Scope 3 and shared Collections.** Personal chapters, listening
   positions, offline packs, and end-to-end-encrypted shared Collections
   riding the now-proven sync.

## 45.8 What this changes in section 23

Section 23's "PostgreSQL for everything" recommendation is replaced by the
git-like commit-log-plus-encrypted-object-store model above. PostgreSQL is
retained only for membership and key-distribution metadata. All other
section 23 requirements (E2E by default, local authority, offline edits,
idempotent ops, tombstones, accessible recovery, device handoff) are
preserved and strengthened by versioning and rollback.

## 44.8 Read-only web publish surface (in-repo, built)

A read-only public web view of an explicitly-published collection (PRD 27.1; plan
doc section 12). Not a sign-in surface and not a capture surface.

- **Static render + localhost preview.** `quill_beacon/publish.py` renders the

- **Accessibility.** Semantic HTML5: a skip link, one `<h1>`, `<article>`/`<h2>`

## 45.10 Incremental commits and auto-sync (in-repo, built)

Two operational refinements landed in the Beacon build:

- **Incremental commits (PRD 45.8).** A full-snapshot commit on every sync is
  correct but wasteful. The library now tracks per-beacon `updated` and a
  device-local `dirty` flag, plus a `beacon_tombstones` table for permanent
  deletes. After the first full snapshot, `sync_now` commits only dirty
  beacons and pending tombstones, then clears the markers once the commit is
  in the local log. `dirty` is never serialized in a record, so applying a
  pulled record never makes the receiving device re-commit (no ping-pong).
  Trash/restore/archive/delete all set the markers so they propagate; the
  first sync after a v1 upgrade still takes a full snapshot.
- **Auto-sync (off by default).** `SyncConfig.auto_sync_seconds` (0 = off)
  drives a shell-side `wx.Timer` that calls `sync_now` on the chosen interval.
  The timer only fires when sync is configured and the vault is unlocked, so
  an unconfigured install never touches the network. The user picks the
  interval (Off / 5 / 15 / 30 / 60 min) from Sync > Auto Sync; it persists and
  restarts with the app.

## 45.9 Authentication: magic links via Postmark

The hosted QuillSync server uses **passwordless magic-link authentication**
delivered by email through **Postmark** (or any pluggable transactional email
provider). This is an accessibility decision, not just a convenience one.

### Why magic links

Passwords and captchas are a screen-reader minefield: password managers
intermittently fill the wrong field, captchas present audio challenges that
degrade under speech, and "prove you are human" flows frequently trap
keyboard users. A magic link removes all of that:

- The user enters only their email address.
- QuillSync sends a single-use, short-lived, signed link.
- Clicking the link authenticates the device and issues a per-device token.
- No password to remember, lose, or recover; no captcha.

This satisfies SEC-009 (auth screens meet all accessibility requirements)
by making the auth screen a single labeled edit field and a button.

### No web interface (client-based verification)

There is no hosted web UI for sign-in. The entire auth UX lives inside the
desktop companion app: one in-app dialog (email field + "Send sign-in link"
button) plus the user's existing mail client. The magic link uses a **custom
URL scheme** (`quillsync://verify?token=...&device=...`) so activating it in
the mail client hands the token straight to the registered companion app, not
to a browser tab. The server's `/auth/verify` endpoint returns JSON for the
client to consume; it is not a page a person reads. A hosted HTTPS verify URL
is kept only as a fallback for headless environments and shows a single
"open the app" line, never a form. See `Docs/PLAN-quillsync-integration.md`
section 0.5 for the per-app flow and install-time scheme registration.

**Scheme registration helper.** `quill_beacon/scheme_register.py` registers and
unregisters the `quillsync://` scheme per platform so the OS launches the app
when a verify link is activated: Windows writes `HKCU\Software\Classes\quillsync`
(no admin needed), Linux writes a `~/.local/share/applications` `.desktop`
handler, and macOS is handled via the app bundle `Info.plist` at build time. It
is fail-safe (dict returns, never raises) and ships a CLI
(`python -m quill_beacon.scheme_register register|unregister|status`). It is
installer-adjacent code: an installer, setup wizard, or the user invokes it; it
does not run at app startup by default.

### Flow

1. **Request (in-app).** User enters email in the companion app's Sync
   Settings dialog (one labeled field, one "Send sign-in link" button).
   Rate-limited per email and per IP.
2. **Issue.** Server generates a cryptographically random token, stores its
   hash with an expiry (15 minutes) and a single-use flag, and sends an email
   via Postmark containing a link of the form
   `quillsync://verify?token=...&device=...`.
3. **Verify (in-app, no browser).** The user activates the link in their mail
   client; the OS opens the registered companion app, which calls the server's
   `/auth/verify`. The server hashes the presented token, matches it, checks
   expiry and single-use, then issues a per-device bearer token bound to
   device metadata. The link is invalidated. No web page is rendered.
4. **Device registration.** The device token is registered against the
   account; the user names the device ("Jeff's laptop"). Device revocation
   (PRD 23.3) rotates or rewraps affected keys.

### Security properties

- Tokens are single-use, short-lived (15 min), and stored only as a hash.
- The link is bound to the requesting device fingerprint so a forwarded link
  cannot be replayed on another machine.
- Postmark delivers through a provider whose deliverability is high; the
  server never trusts the email body for anything but the token, and the
  token alone grants only a device enrollment, not vault-key access. The
  vault key is still protected by the user's passphrase-derived key
  (section 45.3), so account access never equals content access.
- Email is the only PII the hosted server holds for auth; it is never used
  for analytics (PRD 33, SEC-008).

### Provider abstraction

Email sending is behind a small `Mailer` interface so Postmark can be
swapped for SES, Mailgun, or a self-hosted SMTP without touching the auth
flow. The default is Postmark because of its deliverability and
transactional-only posture. No email is ever sent without the user's action;
there is no marketing or engagement email (PRD 33.2).

### Accessibility of the email itself

The magic-link email is plain-text-first with a clear, single, full link on
its own line, a plain-language sender name ("QuillSync sign-in"), and a
short statement of purpose. Screen readers should hear the link and purpose
without parsing decorative HTML. A redundant accessible HTML part is
included for clients that prefer it, but the text part is authoritative.

### Recovery interaction

Magic links double as a recovery primitive: a locked-out user can sign in
on a new device with a magic link, then restore the vault from a recovery
kit or via trusted-device approval (PRD 23.4). The accessible warning that
losing every authorized device and recovery method may make end-to-end
encrypted data unrecoverable is presented in plain text before enrollment.
## 46. QuillSync as the shared sync framework

## 46.1 The framework lives here

QuillSync is not a Beacon feature; it is the shared sync layer for every QUILL
companion app. The canonical implementation lives in this repo as the
top-level `quillsync/` package, with no dependency on Beacon's domain model.
It speaks only the `RecordStore` protocol (three methods over opaque JSON-able
record dicts) and a `MergeFn` the application supplies.

Package layout (built here):

- `quillsync/crypto.py` -- vault key (scrypt), per-object DEKs, AES-GCM AEAD,
  content-addressed blob hashes. The single audited crypto path every app
  shares. `quill_beacon/sync_crypto.py` re-exports it for back-compat.
- `quillsync/protocol.py` -- `RecordStore` Protocol, `MergeFn`, `Commit`,
  `ManifestEntry`, `Conflict`, `default_merge`.
- `quillsync/transports.py` -- `Transport` base, `FolderTransport` (BYO
  folder, tier 2), `ServerTransport` (adapts the hosted server's bulk
  push/pull to the per-item Transport interface, tier 3).
- `quillsync/engine.py` -- generic `SyncEngine`: commit log, push, pull,
  topological apply, tombstones.
- `quillsync/merge.py` -- `union_lists`, `three_way_note` (line-based three-way
  merge with accessible conflict surfacing).
- `server/` -- the reference hosted server (stdlib http.server + sqlite) with
  magic-link auth (45.9), push/pull/hints, and `server/client.py`.

Beacon is the exception (PRD 46.2): its adapter `BeaconRecordStore` and
`beacon_merge` live here in `quill_beacon/sync.py`, wrapping `BeaconStore` for
the framework. Every other app's adapter lives in its own repo.

## 46.2 The integration contract (what each companion app implements)

An app integrates by writing, in its own repo:

1. A `RecordStore` adapter: `get_record(id) -> dict|None`, `put_record(id,
   dict)`, `delete_record(id)`. The dict is the app's own portable shape; the
   framework encrypts it without inspecting it. `None` means deleted/trashed
   and syncs as a tombstone.
2. A `MergeFn`: `(local_record|None, remote_record) -> (merged_record,
   conflicts)`. Built from `union_lists` and `three_way_note` for consistent
   merge behavior across apps.
3. A vault key from the user's passphrase (`quillsync.derive_vault_key`), kept
   in sync across devices via the recovery kit (PRD 23.4).
4. A transport: `FolderTransport` for BYO folder, or `ServerTransport` over the
   app's own HTTP client for the hosted server.

Then `SyncEngine(adapter, vault, device=..., data_dir=..., merge_fn=...)`
gives the app commit/push/pull with no further framework knowledge.

## 46.3 Integration plans (planned, not built here)

The per-app integration plans -- what each repo would add, which scopes it
syncs, and how it sequences against Beacon -- are in
`Docs/PLAN-quillsync-integration.md`. That document covers Quill (settings-as-
a-repo + Vault scopes 1-3), Quill Radio (stations/favorites/recordings), Quill
Cast (episodes/publishing state), and iOS (Quill Pocket, plan only). It lists
the concrete adapter each repo would write against the contract above, and
explicitly does not change those repos.

## 46.4 Server integration

The reference server in `server/` is wire-compatible with `ServerTransport`
and is the shared backend for every app: one account, one vault, per-app
namespaces inside the encrypted object store. The production target (FastAPI +
Postgres + S3 + Redis, PRD 45.5) keeps the same JSON contract, so apps do not
change when the server is upgraded. Auth is magic-link (45.9) for all apps;
device tokens are scoped per app namespace so a Beacon device token cannot read
Quill Cast objects (PRD 23.3 device revocation rotates per-app keys).

## 47. Intelligent assistance (local heuristics, no AI required)

Phase 5 adds on-device assists that run without any model or network call
(`quill_beacon/assist.py`). They are opt-in menu actions, never background
processing that changes the library without the user asking.

- **Suggest tags** (Ctrl+Shift+T): term-frequency tag suggestions from the
  selected beacon's title and note, stopword-filtered, excluding tags already
  present. The user invokes it; suggested tags are added in one action and
  announced.
- **Suggest relationships** (Ctrl+Shift+K): ranks other beacons by shared
  tags (weight 3), shared collections (2), and same domain (1), excluding
  self and already-related beacons. Top matches are linked with a reason note.
- **Summarize note** (Ctrl+Shift+M): an extractive summary -- the highest-
  scoring sentences by word frequency, returned in original order -- shown in a
  dialog and announced.

## 47.4 Semantic search -- opt-in hook, no default model

`assist.semantic_search` is a seam, not a feature: with no index registered it
returns an empty list, so the capability is silent until the user turns it on.

the framework ships no model and makes no network call. This keeps the
free-first, local-first ethos (PRD 5, 33) while leaving a documented extension
point for users who bring their own model.
