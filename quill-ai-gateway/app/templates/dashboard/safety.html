These are the protections that are not rows in a table. Most of them are code or configuration that holds quietly; two of them can rot without anybody noticing, which is why they are listed here with a live state rather than only in a log.

What each check protects, and whether it is holding
Check State What it protects
No web search, no tools Holding The only things ever sent are the model name, the text, and two size limits ({{ allowed_keys_count }} fields in all). Web search alone would bill at $10 per thousand calls — more than everything else put together. A test fails the build if that changes.
Nobody is charged for a blank answer On If the model spends its whole budget thinking and returns nothing, the request is not counted against anybody. The real cost is still recorded against the budget, because the provider still billed us.
Nobody is charged for a request that failed On A passage that was too long, an outage, or a missing model all give the person their request back. The counters are taken before any of those are checked, so without this they would quietly lose one.
Sign-ups are throttled {% if reg_hourly > 0 or reg_daily > 0 %} On {{ blocked_today }} refused today {% else %} OFF {% endif %} Anyone can connect a computer without an account, which is deliberate — it is what makes this usable for somebody who has never had an API key. These limits ({{ reg_hourly }} an hour, {{ reg_daily }} a day per internet address) are what stop one person scripting a thousand of them.
New accounts start small {% if new_account_hours > 0 %} On {% else %} Off {% endif %} {{ new_account_cap }} requests for the first {{ new_account_hours }} hours, then the full allowance. A throwaway account is worth a fraction of a real one, which is what makes farming them uneconomic. It can never give a new account more than an established one gets.
Spending pauses itself {% if budget_cap > 0 %} Armed at ${{ "%.2f"|format(budget_cap) }} at {{ budget_percent }}% now {% else %} NOT SET {% endif %} If total spending reaches the cap, everything switches off without waiting for anyone to read an alert. ${{ "%.2f"|format(spend) }} spent this month.
Alerts reach a human {% if alerts_configured %} Configured {% else %} NOT CONFIGURED {% endif %} Without this, the 50%, 75% and 90% warnings go to a log nobody reads, and the first you hear of a runaway month is the service switching itself off. Set GATEWAY_ALERT_WEBHOOK_URL in the server's environment file.
A default model is set {% if model_ok %} Yes {% else %} NO — everything is failing {% endif %} Without one, every request is refused as though the service were paused. Set it on the Models page.
Nothing anyone wrote is stored {% if content_columns %} BROKEN {% else %} Holding {% endif %} The usage table has no column that can hold document text, prompts or answers. Checked against the live database mapping rather than trusting a comment, because a migration that added one would be the worst thing this service could ship. {%- if content_columns %} Found: {{ content_columns|join(", ") }}.{% endif %}
Troubleshooting records expire {{ pending_diagnostics }} held The one exception to the line above. Each is scrubbed before it is written and deleted after 30 days by a scheduled job, not by a promise. Run flask --app run.py cleanup-expired daily from cron.

Two of these are worth checking by hand rather than trusting: whether the alert webhook really delivers, and whether the cron jobs really run. Both fail silently, and both matter most at the moment something else has already gone wrong.
