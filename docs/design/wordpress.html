WordPress in QUILL and QUILL Lite

Payment integration is specified by the current implementation notes and QAF plugin contract. These supersede the initial payment proposal: desktop authoring and reporting share the WordPress transport; provider credentials and checkout remain plugin-owned.

Product requirements, draft 0.1, 2026-11-03. Status: proposed, nothing built beyond what section 2 says already exists.

1. What this is

Write, open, edit and publish WordPress pages and posts, and manage the site’s Media Library, from inside QUILL and QUILL Lite, with every editor tool still in reach: Find, Replace, spelling, dictation, Read Aloud, bookmarks, the Markdown and HTML tools, Choose Your AI.

This is not a site builder and does not touch the theme. The site keeps its look; we work on the content inside it.

Three rules shape every decision in this document:

  1. Simple first. A person who only wants to post a weekly news item should need three things: connect once, write, publish. Everything else is there when wanted and invisible when not. No command needs AI.
  2. Many sites. Multiple sites are a requirement, not an extra. Every document knows which site it belongs to, and every confirmation names it.
  3. Both kinds of WordPress. Self-hosted sites and WordPress.com sites work the same way from the user’s side. Only the Connect step differs.

Nothing reaches a public site without a deliberate Publish or Update, and nothing is ever deleted for good without a local copy first.

2. What already exists (2026-11-03)

QUILL has a publishing framework, built and tested, but mostly switched off:

  • quill/core/publishing.py, publishing_clients.py, publishing_providers.py: saved connections (several, with one marked current), the application password in Windows Credential Manager, an HTTPS-only endpoint policy (_validate_endpoint_security), and these operations: verify, browse pages and posts by status, load, compare, create, update, publish and schedule. The client speaks /wp-json/wp/v2.
  • quill/core/publishing_linkage.py remembers which local file came from which remote item.
  • quill/ui/publishing_tools.py and main_frame_publishing.py: the Connections, Edit Connection, Browse and Schedule dialogs, plus a Publish submenu in main_frame_menu.py.
  • Gates: future.publishing_read (connect, browse, open) is on only in the Full Quill profile. future.publishing (anything that sends) is locked_off=True.
  • QUILL Lite has no publishing. quill/apps/lite.py says so on purpose, and this PRD changes that (section 11).

Missing:

  • categories and tags;
  • slug, excerpt and featured image;
  • the Media Library;
  • Trash;
  • a conflict check: modified_gmt is fetched and never compared;
  • local drafts and previous versions;
  • Open by Web Address;
  • WordPress.com;
  • any of it in QUILL Lite.

3. Who it is for

  • The weekly poster: a business or community group posting news. Needs New Post, a category and Publish.
  • The page fixer: someone sent a link and one sentence is wrong. Needs Open by Web Address, Find and Update.
  • The site keeper: looks after two or five sites, for work and for volunteering. Needs the site switcher, drafts that stay with their site, and the Media Library.
  • The writer: long posts, many images. Needs alt text help, a check before publishing, and previous versions.

4. Connecting a site

4.1 One dialog, three fields

Connect a WordPress Site asks for:

  • the site address;
  • the username;
  • the application password.

There is also a name field for the site, which defaults to the site’s own title once the connection is verified. Connect verifies before it saves, and says exactly what was wrong if it fails:

  • wrong password;
  • not HTTPS;
  • the REST API is blocked by a security plugin;
  • the account lacks the role.

4.2 No copying passwords where WordPress allows it

WordPress 5.6 and later has an Authorize Application screen (/wp-admin/authorize-application.php). It can hand the new application password straight back to the app, with no copy and paste.

  • QUILL opens that page in the default browser and listens on a one-time local loopback address for the reply.
  • What WordPress accepts (researched 2026-11-03):
    • Core changeset r62096 (24 March 2026, ticket #57809) allows a plain http:// success_url on the loopback addresses 127.0.0.1 and [::1], on any site. Before it, plain http was accepted only on sites marked as a local environment (WordPress 6.2), so most live sites refused it.
    • localhost is still refused on purpose: RFC 8252 section 8.3 warns about it.
    • Not yet confirmed: which release ships r62096. Check the WordPress 7.0 field guide before building.
  • Decision: the flow works in three tiers, all automatic. The user only ever presses Connect.
    1. QUILL asks the site its version, from the REST index the client already reads. On a version that has r62096, it uses http://127.0.0.1:<random port>/wordpress-done with a one-time state. The password arrives by itself. QUILL saves it, verifies the connection, and says “Connected to Site Name”.
    2. On an older site it uses no success_url at all. WordPress then shows the new password on its own page with a Copy button. QUILL’s dialog waits on a single Paste field: “Copy the password WordPress is showing you, then come back and paste it here.” The clipboard is checked when the dialog gets focus back, and a password-shaped value (24 characters in groups of four) is offered: “Use the password you just copied?”
    3. If the authorize screen is turned off (a security plugin, or wp_is_application_passwords_available false), Connect says so in plain words. It offers the manual route through the profile page.
    • Never https:// to a page of ours that relays the password. A relay we run would be a place a password passes through, and nothing needs it.

A “Get an application password” button opens the profile page’s Application Passwords section, for sites where the authorize flow is turned off.

4.3 WordPress.com

  • WordPress.com sites use OAuth through public-api.wordpress.com/oauth2-1/authorize. Content is served by https://public-api.wordpress.com/wp/v2/sites/<site>/..., which is the same wp/v2 shape the client already speaks, under a different base URL with a bearer token.
  • The user chooses “WordPress.com” in Connect, presses Sign In, approves in the browser, and picks the site or sites to add. One sign-in can add every site that account manages, each as its own connection.
  • WordPress.com sites on plans that allow plugins also accept an application password on their own domain. If the user types such an address, the self-hosted path works and we don’t argue.
  • What WordPress.com accepts (researched 2026-11-03):
    • Its OpenID configuration (public-api.wordpress.com/.well-known/openid-configuration) advertises an OAuth 2.1 endpoint pair: /oauth2-1/authorize and /oauth2-1/token.
    • It supports response_types_supported: ["code"], code_challenge_methods_supported: ["S256"] and token_endpoint_auth_methods_supported including "none", plus refresh_token grants.
    • Scopes include sites, posts, media, taxonomy, comments and global.
    • The older /oauth2/ docs describe the implicit grant (response_type=token) as deprecated, with tokens lasting from 18 hours to two weeks.
  • For everyone (Jeff, 2026-11-04). WordPress.com sign-in has to work for every person on every WordPress.com plan, the free one included, without plugins and without anyone registering anything. That is why it runs through QUILL’s own registered WordPress.com app: Jeff registers it once, the client id ships in every build, and each person signs in with their own WordPress.com account. The application-password route on a site’s own address stays available for plugin plans, but it is never the only way in.
  • Decision: use the authorization code flow with PKCE (S256) as a public client, with token auth none.
    • No client secret ships in the installer, and none is needed.
    • Do not use the implicit grant.
    • Ask for sites posts media taxonomy comments, not global: the narrowest scopes that cover everything in this PRD, and what the consent screen shows the user.
    • Keep the refresh token in Credential Manager. Renew silently, so the user signs in once, not every two weeks.
    • If a refresh fails, say “Sign in to WordPress.com again” and offer Sign In. Never fail silently on a publish.
  • Redirect: register http://127.0.0.1/wordpress-done (loopback, any port, per RFC 8252) when creating the app.
    • Not yet confirmed: whether WordPress.com’s Applications Manager accepts a loopback redirect, and whether it matches any port or needs exact ports. Test with the real app registration before building.
    • If loopback is refused: register one https:// page on the QUILL site, docs/site/wordpress-done.html. A static page, it shows the one-time code with a Copy button and “Paste this into QUILL”. The code alone is useless without the PKCE verifier, which never leaves the computer, so the page handles nothing secret. Static hosting on GitHub Pages means no server of ours.
  • Still to verify against a live site: that the wp/v2/sites/<site>/media and /block-types routes behave as they do on a self-hosted site. Every endpoint the client uses gets a recorded fixture from a WordPress.com test site.
  • Our side (Jeff):
    • Register a WordPress.com app under Community Access, at developer.wordpress.com/apps. It needs a name, a description, the redirect above, and the “public client” or native type if offered.
    • Give Claude the client id. It is not a secret and goes in settings.
    • Keep a free WordPress.com test site for the fixtures.

4.4 Many sites

  • The Sites list is the existing Connections dialog, simplified. It offers:
    • Add;
    • Rename;
    • Verify;
    • Remove (the connection only, never the site’s content);
    • Make Default.
  • Switch Site is one key. It opens a short list and the choice is spoken.
  • The default site is where New Page and New Post go, and what Open browses. Every dialog that touches a site has a Site combo box at the top, defaulting to the default site, so nobody has to switch first.
  • An open document belongs to its site for life. Switching the default never moves it. The status bar and Document Properties say “WordPress: Site Name, Draft”.
  • Confirmations name the site and the item: “Publish ‘Spring Workshop’ to Community Radio?”. This matters most when the same title exists on two sites.

5. Pages and posts

5.1 New Page, New Post

A small dialog asks for:

  • the site;
  • the title;
  • Markdown or HTML (default from the last choice, Markdown first time);
  • the slug (the last part of the page’s address), filled in from the title as it is typed. Leave it alone to keep the suggestion.

For a post it also asks for categories and tags. The excerpt and everything else live in Properties and are not asked up front. Creating it sends nothing.

The format is fixed once the document is created. A Markdown document never later gets read as HTML, or the other way round, so nothing on the page is quietly reinterpreted. Markdown is turned into HTML only when it is sent. Preview in Browser shows the result at any time.

The title is kept apart from the body, because the theme prints it. The body starts with the first paragraph, not a Heading 1.

5.2 Open

Open Page or Post has these controls:

  • site;
  • type;
  • status (Published, Drafts, Pending, Scheduled, Private, Trash);
  • a search field.

The list reads “title, status, last changed”. Enter opens the item. Paging is automatic as the list is walked; there is no More button.

Open by Web Address works like this:

  • Paste any link to a page or post, or press it with a link already on the clipboard.
  • QUILL finds which saved site it belongs to and opens the item. That might not be the default site.
  • If no saved site matches, it offers to connect that site.
  • If the item is already open, it switches to that tab instead of opening a second copy.

Existing items open as HTML, with WordPress’s block comments (<!-- wp:paragraph -->) kept intact, so the block editor still sees blocks afterwards. This is the safe default.

  • Open as Markdown is a choice in the dialog, with a plain warning that block layout is not kept.
  • A Markdown document QUILL created stays Markdown. QUILL keeps the Markdown source locally, keyed by site and id, so reopening it gives back Markdown, not converted HTML.

5.3 Saving, three separate actions

Action Key What happens
Save Ctrl+S A local working copy only. Never sends.
Save Draft to Site (assigned) An unpublished draft on the site.
Publish or Update (assigned) Asks once, naming site and title, then publishes.
  • Closing a WordPress document never publishes it.
  • Local drafts are kept automatically. Open Local Draft lists them by site.
  • A Private or Scheduled item keeps that status on Update.

After Publish, the page address is spoken and placed on the clipboard. Open on Site opens it in the browser at any time.

5.4 Conflict protection

Before every Update, QUILL re-reads the item’s modified_gmt. If someone else changed the site copy since it was opened, nothing is sent. The user is told who changed it and when, and offered three choices:

  • Compare (the existing compare, both ways);
  • Open the Site Copy;
  • Send Mine Anyway, which asks a second time.

5.5 Properties

One dialog (Alt+Enter on a WordPress document) holds:

  • title, slug, status and excerpt;
  • categories and tags (the post only);
  • the featured image (section 6.4);
  • whether comments are open;
  • the read-only facts: the site, the address, the author and when it last changed.

Each field has its own F1 help.

Categories and tags:

  • one checkable list each, with a search field above it;
  • each item says “checked” or “not checked”;
  • “New Category” and “New Tag” create one on the site when the account is allowed to;
  • a summary line reads “2 categories, 3 tags”.

5.6 Trash and versions

Move to Trash:

  • Works from the open document or from the Open list.
  • It is WordPress’s Trash, never permanent deletion.
  • A local copy is kept, and Trash is a status in Open, so it comes back.

Previous Versions:

  • Lists newest first. Each row has the date, the title and the reason, such as:
    • “Opened from site”;
    • “Saved”;
    • “Site copy before update”;
    • “Before AI change”;
    • “Before restore”.
  • Before restoring, View opens a version’s full text and its properties (the title, slug, status, categories and tags) in a read-only window. From there you can copy one paragraph instead of restoring all of it.
  • Restore puts the version in the editor. It never publishes.
  • Where the account can read them, the site’s own revisions (/wp/v2/<type>/<id>/revisions) appear in the same list, marked “On the site”. That makes this a true history, not just what QUILL happened to keep.

5.7 The whole editor, and finding commands

A WordPress document is an ordinary QUILL document. Nothing about the editor is reduced for it. All of these work exactly as they do anywhere else:

  • Find, and Find and Replace;
  • heading and structure navigation;
  • select, cut, copy and paste, and Change Case;
  • the spelling and grammar checker;
  • dictation;
  • AutoCorrect and abbreviations;
  • bookmarks and document notes;
  • the Markdown and HTML insert tools: headings, links, email links, lists, tables and images;
  • several documents open at once, from one site or several, and Compare;
  • Read Aloud.

Finding commands:

  • File > WordPress lists them all.
  • The Command Palette, in QUILL and QUILL Lite alike, finds any of them by typing “WordPress” or part of a command’s name. Every WordPress command is in it, with its key beside its name.

5.8 Scheduling

Schedule Publish already exists in the publishing core. It goes into File > WordPress beside Publish or Update. It asks for the date, time and time zone, confirms with the site and the title, and the item then shows as Scheduled in Open. Change Schedule and Publish Now work on a scheduled item.

5.9 After publishing

  • Draft addresses need a sign-in: a draft’s address only works for someone signed in to WordPress. QUILL says so when it copies one: “Draft address copied. It needs a WordPress sign-in to open.”
  • Adding a new page to a menu: publishing a new page does not add it to the site’s menus. After a new page is published, QUILL offers, once, “Add it to a menu?”. That opens the Menus window (9.9) at the right place. The question can be turned off.

5.10 When things go wrong

Every failure is spoken with its reason and the next step. The common ones:

What happened What QUILL says and offers
The password was refused It names the account and site. It offers to check that the application password belongs to that account, and Reconnect.
Connected, but an action was refused It names the role and what that role cannot do (9.2).
A page cannot be found It suggests checking the site, the type, the status and the search. Open always loads every page of results, so “more results” is never the cause.
A save was not confirmed The local draft stays. QUILL re-reads the site before it offers Try Again, so nothing is created twice.
An upload was not confirmed QUILL checks the Media Library for the file before it offers to upload again (6.2).
The site copy changed Conflict protection (5.4).
Visual Review missed a change It says the page may be a cached copy and suggests checking that the update finished (6.11).
A security plugin blocks the API It says so plainly, and says what to ask the site’s administrator for.

Page builders: content made with a page builder is protected. That includes Elementor, Divi and WPBakery, and shortcodes. It opens as islands (8.1), editable as text where the builder stores text and otherwise kept byte for byte. QUILL names the builder, and says that layout changes belong in the builder.

6. Media Library

This is a first-class window, not a file picker.

6.1 Browse

The Media Library window:

  • opens with: one key from any WordPress document or from the menu.
  • site: chosen by a Site combo at the top.
  • controls:
    • a search field;
    • a type filter (Images, Audio, Video, Documents, All);
    • an “Only unattached” check box.
  • each row reads: title, type, size in pixels for images, file size, alt text or “no alt text”, upload date.
  • paging: automatic.
  • the details pane shows, read-only:
    • the address;
    • the caption;
    • the description;
    • what it is attached to;
    • Used In: the pages and posts whose content links to this file, found by searching for its address. The search is slow, so it runs on request with a progress announcement.

6.1a Listen and watch (Jeff, 2026-11-04)

An audio or video file in the Media Library can be played without leaving QUILL, so you can check what a file is before you insert it, remove it, or write its transcript.

  • Play: on an audio or video row, Play (or Enter on the row) opens a small player window. It uses the shared transport panel that QUILL and Quill Media Player already use, so the keys are the familiar ones:
    • play and pause;
    • stop;
    • back and forward;
    • Go to Position;
    • speed;
    • volume;
    • the position and length, on request.
  • Video: plays its sound and shows the picture. If the site has a captions track for it, Captions reads the current caption on request.
  • Streamed, not saved: the file streams from its address on the site, over HTTPS. Nothing is downloaded unless you choose Download.
  • Other ways to play it:
    • Open in Quill Media Player, for chapters, bookmarks and resume;
    • Open in Browser.
  • In a document: Play Media Here plays the audio or video block at the caret.
  • The same in both editors, through the shared module.

6.2 Upload

  • Ways to upload:
    • one or many files from the computer;
    • an image on the clipboard;
    • a file from a web address.
  • Before upload: each file gets its title, alt text, caption and a Decorative check box. The alt text field is the focus first for an image.
  • During upload: progress is spoken per file. A failed file says why, and the rest carry on.
  • No duplicates: if the same file (same name and size) is already in the library, QUILL asks “Use the one already there?” before uploading a second.

6.3 Edit and remove

  • Edit Details: changes title, alt text, caption and description on the site.
  • Remove from Library:
    • Confirm first: names the file and the site, and says how many pages use it, if Used In has run.
    • Back up first: WordPress media has no Trash, so removal is permanent. QUILL downloads a copy to a local “Removed from Site Name” folder first, and the confirmation says so.
    • Many at once: several files can be chosen and removed together, with one confirmation that gives the count.
  • Download: saves a copy locally.
  • Copy Address: puts the file’s address on the clipboard.

6.4 Attach and insert

  • Insert Picture from This Computer: one command, from any WordPress document.
    • Choose the file: a standard Open dialog.
    • Then the image dialog opens (6.7), with everything:
      • alt text, with Suggest;
      • Decorative;
      • caption;
      • display width;
      • Use as Featured Image;
      • Link to;
      • Describe Image.
    • Insert: uploads the file with its title, alt text and caption, then places it at the caret. Upload progress is spoken, and so is the outcome: “Picture inserted: Volunteers at the spring fair”.
    • No duplicates: if the same file is already in the library, QUILL offers to reuse it instead of uploading again (6.2).
    • Offline, or before the document is on the site: the picture is inserted from the local file straight away, with all its settings. It is marked “not uploaded yet” in the document, in Where Am I and in Check Before Publishing. On Save Draft to Site or Publish, QUILL uploads every local picture first, swaps each local path for its library address, and keeps each one’s alt text, caption, width and featured-image choice. A page never reaches the site pointing at a file on the writer’s computer.
    • Pictures dropped or pasted in (below) go through the same path.
  • Insert into Document:
    • places the image at the caret, as Markdown or HTML to match the document;
    • a figure with alt text and caption;
    • an optional display width;
    • for audio and video, the matching block markup.
  • Alt text is per placement: changing it in the document changes that occurrence only, never the library item everywhere.
  • Attach to This Page or Post: sets the media item’s parent. This is WordPress’s own sense of “attached”, which galleries and some themes use. It is separate from inserting.
  • Set as Featured Image: works from the library, from the document’s Properties, or from an inserted image. “Remove Featured Image” sits beside it.
  • Pasting an image into a WordPress document offers to upload it and insert it, alt text first.

6.5 Image size, and file size

These are two different things, kept as two separate commands:

  • Image Size: the width the image is shown at. Proportions are kept, nothing is cropped, and it changes only the markup.
  • Make a Smaller Copy:
    • Pillow is already in the runtime, so this happens on the computer.
    • Choose a maximum width and a format.
    • Before and after, it reports pixels and file size.
    • Upload and Use replaces only this occurrence. The original stays in the library.

6.7 The image dialog

Inserting an image, by upload or from the library, opens one dialog. In tab order:

  1. Alternative text, an edit field, with Suggest beside it (6.8).

  2. Decorative, a check box. Checked, it empties and disables the alt text field and writes alt="". Its help says what decorative means: the image adds nothing a visitor needs.

  3. Caption, an edit field. Visible text for credits, names and context.

  4. Display width, a combo box offering:

    • Full width;
    • the theme’s content width;
    • Half;
    • a number of pixels.

    It always keeps the proportions. The image’s real size is said beside it: “Image is 2400 by 1600”.

  5. Use as Featured Image, a check box.

  6. Link to, a combo box: nothing, the file, or an address. Choosing an address turns the alt text label into “Alternative text (say where the link goes)”, because a linked image’s alt text is the link’s name.

  7. Describe Image, Insert and Cancel.

Image Size on an inserted image opens the same dialog at that image, showing:

  • the current width;
  • the proposed width, with “Preview on the Page” (6.11);
  • “Back to Earlier Size”. QUILL keeps each placement’s earlier widths in the document’s local history, so this works after a save, not only within one session.

6.8 Alt text and descriptions

There are three image reports, kept apart because they answer three different questions. Each one’s help says which question it answers.

Report Who it is for Question
Suggest Alt Text visitors using a screen reader What does this picture contribute here?
Describe Image the person writing What is actually in this picture, and is it any good?
Visual Review the person writing How does this picture sit on the real page?

Suggest Alt Text:

  • What it sends: the image, the heading above it, the paragraphs either side, the caption, and the link target if there is one.
  • The instruction it gives the AI asks for:
    • one or two sentences on the image’s purpose, not its pixels;
    • visible text read out exactly;
    • no “image of”;
    • no invented names. If a person is shown and the page does not name them, the suggestion says “a person” and the field’s help says to add the name if it matters.
  • Charts and diagrams: for a chart or a diagram it proposes short alt text and offers “Add a Fuller Description After the Image”, a paragraph inserted below for the user to edit.
  • Decorative images: when the image looks decorative (a divider, a texture), it says so and suggests the Decorative check box rather than inventing words.
  • The result is only a proposal: it lands in the field, selected, ready to be replaced or corrected. It is never saved on its own.

Describe Image works on any library item, any inserted image, any generated picture and any smaller copy. It gives a longer report, which opens in a read-only text window with Copy and Save:

  • the subject;
  • the arrangement;
  • the colours and lighting;
  • any visible text, quoted;
  • the mood;
  • problems: awkward cropping, distorted hands or faces, garbled lettering, a crowded composition, low resolution for its size.

It always looks at the actual file, never at the description it was made from. That is the existing Studio rule: “a separate look by the vision model”.

Beyond: an Alt Text Review for the whole document. It lists every image with its current alt text, marks the empty, the filename-like (“IMG_2041.jpg”) and the suspiciously long, and offers Suggest on each, one at a time.

6.9 Making a picture

The Picture Maker that Audio Studio already has (quill/core/ai/image_generation.py, quill/ui/studio_picture_maker.py) moves to the shared quill/ui/ layer. It follows the same pattern as the hosted AI, so QUILL, QUILL Lite and Studio all reach one implementation.

  • The description: one edit field, with the help suggesting what to include: the subject, the style, the colours, the arrangement, the background and anything to avoid.
  • Shape: Square, Landscape or Portrait. These are the existing IMAGE_SIZES.
  • Background:
    • Normal.
    • Solid colour, with a colour name chosen from the site’s theme palette (8.4).
    • Transparent. Offered only when the provider can make one: OpenAI image models can and Imagen cannot. When it cannot, the option is missing rather than failing later, and its help says why.
  • Make the Picture:
    • It asks first, naming the provider and model, as Studio does today.
    • It saves the file on the computer only. It never uploads and never changes the page.
    • A Describe Image report on the result opens at once.
  • The versions list: every version is kept, each with its description. “Change Description” goes back to the description with the conversation so far, and Make the Picture again adds a version.
  • On a chosen version:
    • Describe Image;
    • Open in Image Viewer;
    • Save As;
    • Make a Smaller Copy (6.5);
    • Insert into Document, which opens the image dialog (6.7) with the upload done on Insert.
  • Suggest from Page Content:
    • The AI reads the page, or the selection, and proposes three things: a description, a shape and a background, with one sentence on why the picture would suit the content.
    • All three land in the Picture Maker’s fields, editable, and nothing is made until Make the Picture.
  • An honest rule: a generated picture is an illustration, never a screenshot. If the description asks for an application’s screen, menu or dialog, the Picture Maker says once, plainly, that a real screenshot is the right thing for a reader who needs to see real controls, and goes ahead if asked again.

6.10 The site logo

The site logo is the theme’s logo on every page, not an image in one post, so changes to it are previewed first and always reversible.

  • Find it: Site Logo reads the standard site_logo setting (/wp/v2/settings) and the media item behind it, and says:
    • the file;
    • its real size;
    • the width the theme shows it at, measured on the public page (6.11).
  • Another kind of logo: if the theme uses a header image or a page builder’s own logo instead, Site Logo says so and stops. That one belongs to the theme’s own controls.
  • Propose a width, then Preview on the Page:
    • QUILL renders the public home page at desktop and phone widths, with the logo at the proposed width.
    • The rendering is done by injecting a style into the captured page, so nothing on the site changes.
    • A Visual Review report on the two views opens.
  • Apply to Site:
    • It is available only after a preview has succeeded.
    • It confirms, naming the site, the old width and the new width.
    • Then it makes a resized copy (with Pillow), uploads it, and sets it as site_logo.
    • The original media item is never touched or removed.
  • Restore Earlier Logo: lists the logos QUILL has set, newest first, each with its size and date.
  • Conflict-safe: before Apply and before Restore, QUILL re-reads site_logo. If someone changed it since the preview, nothing is sent, and the user is told.
  • It needs the right permission: the manage_options capability. Without it, the command says so and nothing more.

6.11 Visual Review

Visual Review tells a blind site owner what a sighted visitor sees, image by image. It moves here from section 10, because most of what it reports is about images.

  • Capture:

    • The installed Microsoft Edge, or Chrome when Edge is missing, captures the public page at a desktop width (1366) and a phone width (390). It runs in headless mode with the DevTools protocol.

    • There is no browser window to manage, and the default browser is not changed.

    • Progress is spoken: “Capturing the phone view”.

    • What is measured, from the live page:

      • every image’s displayed width and height;
      • whether it overflows the content area;
      • whether it loaded, partly loaded or failed;
      • its position relative to the nearest heading;
      • its existing alt text.

      These are facts, gathered by the browser, not guessed by the AI.

  • Report:
    • The AI gets both screenshots, the page text and the measurements.
    • It writes:
      • an overall impression;
      • the desktop layout;
      • the phone layout;
      • spacing and balance;
      • what works well;
      • then one entry per image: where it is (“below Individual Training”), the measured size on each view, the existing alt text, a fresh description of what is shown, and whether it suits the text around it.
    • Each finding is labelled as one of three kinds:
      • “likely a problem”;
      • “a design choice you may want”;
      • “worth checking”.
    • The report opens in a read-only text window, with Copy and Save as Text.
  • From report to fix:
    • Each image entry with a size suggestion has “Try This Width”. That opens Image Size (6.7) at that image, with the width filled in.
    • After the user Updates the page, “Review Again” reruns the review on the same views.
  • Preview and Review:
    • This version reviews a proposed change without publishing it. It captures the current public page with a proposed image width or logo width injected as a style, and reports on that.
    • It is how Image Size and Site Logo preview.
    • What it cannot preview is unpublished text, and it says so.
  • Honest about what it saw:
    • It reviews the public page only. If the document has unpublished changes, it says “This reviews the page as published. Your unpublished changes are not in it.”
    • It separates “the image failed to load”, “the image had not finished loading” and “this part of the page was not captured”, rather than calling an image broken.
    • If the captured page is older than the last Update, it says the site may be serving a cached copy.
  • What it sends: the screenshots, the page text and the measurements, to the AI chosen in Choose Your AI, after the usual consent. Capturing itself sends nothing anywhere except a normal visit to the public page.

7. Check Before Publishing

Publish runs a short check and speaks the result in one line, for example “Ready to publish: no problems found” or “2 things to look at”. The list then opens, and each item jumps to its place in the document.

The checks:

  • an image with no alt text that is not marked decorative;
  • a link with no text, or a link to a page on this site that does not exist;
  • a heading that skips a level, or a Heading 1 in the body (the theme already shows the title);
  • an empty title;
  • the document belongs to a different site than the default, with the site named;
  • the site copy changed since opening (section 5.4).

None of these blocks publishing. “Publish Anyway” is always there. The check is fast and runs locally, except the link check, which only reads the site.

8. Blocks, made plain

The block editor is where most WordPress sites now keep their layout: buttons, columns, galleries, call-outs, accordions, embeds, and patterns the site owner designed. In a browser it is a drag-and-drop canvas full of floating toolbars, and it is one of the hardest parts of WordPress to use with a screen reader.

QUILL does it differently. A block is just a piece of the document with a name, and every action on it is a command, a list or a form. Nothing is dragged and nothing floats.

8.1 What a block looks like in QUILL

The idea is that ordinary writing is ordinary writing. A paragraph is a paragraph, a heading is a heading, and a list is a list.

  • Ordinary blocks need no markup. The core blocks that map onto something QUILL already has are written the way they always are, as Markdown or HTML: paragraph, heading, list, quote, image, table, separator, code and preformatted. QUILL adds and removes the block comments (<!-- wp:heading {"level":2} -->) itself, on open and on send. The user never sees or types one.

  • Other blocks are fences, in Markdown. Anything else is written as a readable fence. That is the same ::: syntax QUILL already uses for page breaks and divs, so there is one idea to learn, not two:

    ::: button "Book a session" https://example.org/book

::: columns
::: column
Morning sessions run from nine.
::: column
Evening sessions run from six.
::: end columns

::: details "What does it cost?"
The first session is free.
::: end details

  • HTML documents keep the real block markup, but QUILL folds each block comment into one spoken line: “Button block: Book a session”. Arrowing never makes the user read JSON.

  • A block QUILL does not know is an island. A plugin’s block, a complex gallery or a form shows as one protected line, for example “Contact form block (from a plugin), press Enter for its settings”. It is sent back byte for byte unless the user changes it on purpose, so nothing on the site is ever broken by being opened in QUILL.

8.2 Inserting a block

Insert Block (one key) opens a search field over a list:

  • What the list holds:
    • every block the site allows, from /wp/v2/block-types;
    • the site’s own patterns, from /wp/v2/block-patterns/patterns;
    • the site’s synced patterns (/wp/v2/blocks).
  • What each row reads: the block’s name and a one-line description, in the site’s language.
  • Searching: typing “but” finds Button and Buttons.
  • Order: the most-used blocks come first, and then the rest from A to Z.

Choosing one opens a short form with only the fields that block needs:

  • Button: text, link, open in new tab;
  • Columns: how many;
  • Details: the summary line;
  • Embed: the address;
  • Gallery: a check list of images from the Media Library;
  • Cover: an image and its text.

The form is generated, not hand-built. It comes from the block type’s attribute schema, so a plugin’s block gets a usable form too. The fields QUILL has a better control for (images, links, colours) get that control.

Patterns are the simplest thing of all. A site owner, or their designer, builds “Event announcement” or “Staff profile” once in the block editor. From then on, anyone can insert it by name and fill in the words.

8.3 Moving through blocks

  • Next Block and Previous Block: a quick-navigation pair. Each move says the block type, its position and its first words, for example “Image block, 4 of 12: Volunteers at the spring fair”.

  • Where Am I: says the block and its nesting, for example “Paragraph, inside Column 2 of Columns”.

  • The Blocks window: a tree view of the whole document, one row per block, with nested blocks as children. From the tree:

    • Move Up and Move Down (Alt+Shift+Up and Down, the keys the block editor itself uses);
    • Duplicate;
    • Remove;
    • Change To, for example paragraph to heading, list to paragraphs, or image to cover;
    • Group and Ungroup.

    Enter goes to the block in the document.

  • Undo: every one of these is a single undo step.

8.4 Block settings

Block Settings on the current block opens a form, never a sidebar:

  • alignment;
  • width (wide or full, where the theme allows);
  • colours;
  • font size;
  • spacing;
  • any other attribute the block has.

Colours and sizes come from the theme by name. QUILL reads the theme’s palette and font-size presets, from theme.json through the global styles endpoint. So the choice reads “Accent (dark green)” and “Large”, never #2f5d50 or 1.375rem.

The theme decides what is offered. A user cannot pick a colour the site’s design does not have. That is also how the block editor itself behaves when a theme locks its palette.

8.5 Never breaking a block

The block editor marks a block as “invalid” when its saved HTML is not exactly what that block would have written. A tool that writes blocks carelessly leaves the site owner a page full of warnings. So:

  • Core blocks match WordPress exactly. For every core block QUILL writes, the serializer produces the markup WordPress’s own save code produces. The tests run against WordPress’s published block fixtures (the full-content fixtures in the Gutenberg repository).
  • Dynamic blocks (latest posts, query loop, navigation) are a comment with attributes and no saved HTML, so there is nothing to mismatch.
  • Untouched blocks go back byte for byte (section 8.1).
  • A preview from the site itself. Preview Blocks renders the document through the site’s block renderer (/wp/v2/block-renderer) and shows the result in the existing browser preview. The user hears what the real site makes of the blocks before publishing.
  • Check Before Publishing (section 7) gains one more check: a fence QUILL could not turn into a block, named with its line.

8.6 What this is not

  • Not a new canvas. There is no visual layout surface. The theme draws the page; QUILL edits what goes in it.
  • Not full-site editing. Templates, template parts, the site header and the navigation menu stay in WordPress (section 1).
  • Not a second block editor to maintain. The core-block list is the thirty or so blocks people actually write with. Everything else comes from the site’s own block types, with generated forms, or stays a protected island.

9. Accessibility, the whole way through

Sections 4 to 8 make WordPress usable by a blind writer. This section goes further, in two directions:

  • For the writer: every part of running a site that is hard in a browser becomes a list, a form or a spoken answer.
  • For the site’s visitors: QUILL helps the writer publish pages that are accessible to everyone who reads them, and helps them prove it.

Each feature names the REST API routes it uses, so nothing here depends on a plugin. Routes marked “6.x” need that WordPress version. On an older site, the feature says plainly that the site is too old for it, and why.

9.1 What the API offers, and what we use it for

The core REST API was surveyed on 2026-11-03 (developer.wordpress.org REST API reference, plus the newer routes).

9.2 Know what you can do before you try

On connect, and again daily, QUILL reads users/me?context=edit, which gives the account’s roles and capabilities. Every command then knows ahead of time whether it will work.

  • A Contributor: cannot publish. So Publish becomes Submit for Review (status pending), and the help says why.
  • An Author: cannot publish pages. So Publish Page is dimmed, with the reason as its label.
  • The Sites list says the role for each site: “Community Radio, Editor”.
  • No guessing: WordPress errors such as rest_cannot_publish are never where the user finds out. Each one is mapped to a plain sentence in case it happens anyway.

9.3 Never lose a word

  • Autosaves: while a WordPress document is open, QUILL writes the account’s autosave (/<type>/<id>/autosaves) every two minutes, as well as the local working copy. This is what the block editor itself does. If the computer dies, the words are on the site too, and WordPress’s own “there is an autosave newer than this version” notice works for anyone who opens the item in a browser.
  • Reading autosaves: Open notices an autosave newer than the published copy, whether from a browser session or a crashed QUILL, and offers it: “There is an unsaved version from yesterday, 4:12 PM. Open that instead?”
  • Previous Versions: autosaves appear in the list (5.6), marked “Autosave on the site”.

9.4 Check This Page, the visitor’s way

Check Before Publishing (7) looks at the writer’s text. Check This Page looks at what a visitor actually gets: the theme, the header, the menus, the footer and the content together.

  • Render: headless Edge or Chrome loads the public page (or, before publishing, the block renderer’s output inside the theme’s preview, 8.5).

  • Check: QUILL runs axe-core on the rendered page.

    • axe-core is bundled with the app, so nothing is downloaded at run time.
    • It is the same engine the accessibility rules already ask CI to use.
    • The check reads the page; it sends it nowhere. No AI is involved.

  • Report:

    • One line first: “Community Radio home page: 3 problems, 2 to check”.
    • Then a list with one row per finding, in plain words: what is wrong, who it affects, and where it is (“in the site footer”).
    • Each row has Explain, which gives the WCAG criterion by number and name, and one paragraph on why it matters.

  • Content or theme: each finding says whose it is.

    • In the content: “Go to It” opens the document at the block, and, where the fix is mechanical (empty alt text, an empty link, a skipped heading), offers “Fix It”, which shows the change before applying it.
    • In the theme or a plugin: QUILL says so, names the theme or plugin (from themes and plugins), and offers “Write a Note for the Theme Author”. That is a plain-text report of the finding, the page and the WCAG criterion, ready to paste into a support forum or email.

  • The page’s shape: the report ends with the page as a screen reader meets it. It reads it from the browser’s accessibility tree (the DevTools Accessibility.getFullAXTree):

    • landmarks;
    • the heading outline, including the theme’s own headings;
    • link and button counts;
    • the reading order.

    This is how a writer finds out that their theme puts the site title in a Heading 1 and their page title in another.

9.5 Check the Whole Site, and fix it in bulk

Check the Whole Site runs Check This Page across every published page and post. It works through the list in the background, with progress spoken every ten pages, and can be cancelled and resumed.

  • The report has three views:
    • by page;
    • by problem (“Images with no alt text: 41, on 17 pages”);
    • by owner (content, theme, plugin).
  • Fix in Bulk: for content problems that repeat, it offers to fix them in bulk.
    • Missing alt text: steps through each image in turn: Suggest (6.8), edit, Next. A count is kept.
    • The same image missing alt text in many places: fills each in with the library’s alt text, after a list showing every place it will change.
    • “Click here” and “read more” links: each one is shown with its sentence, for the writer to rename.
  • One confirmation: fixes are made in local copies first. Then, after one confirmation that names the site and gives the number of pages, they go in one request (batch/v1). A version of every page is kept first, so Undo Site Fix can put them all back.
  • History: each run is kept with its date, so the writer can say “41 problems in March, 6 now”. The history is per site and stays on the computer.
  • Site-wide Find and Replace: the same machinery, for words rather than problems. For example: a phone number that changed, a person who left, a renamed programme.
    • It searches all content (search), lists every match with its sentence, and lets each be included or skipped.
    • Then it replaces in one batch, after the same confirmation, and keeps a version of each page.
    • Undo puts them all back.

9.6 Captions, transcripts and listening versions

  • Captions for video: a video in the library, or one being uploaded, can have captions made on the computer by the transcription QUILL already has.
    • QUILL makes the captions file (WebVTT), opens it for review in a plain text window where each cue is a line with its time, and then uploads it.
    • It attaches the captions to the video block as a track, so the player’s CC button works.
    • Speaker names and sound descriptions (“[applause]”) are suggested, and each one is editable.
  • Transcripts for audio: an audio file gets the same transcription. QUILL offers to insert it below the player as a Details block, “Read the transcript”, so it does not swamp the page.
  • A listening version of a post: Make a Listening Version.
    • It reads the post with the user’s chosen Read Aloud voice into an MP3, on the computer.
    • It uploads the MP3 and inserts an audio block at the top of the post: “Listen to this post (6 minutes)”.
    • When the post is updated, it says the recording is out of date and offers to remake it.
  • Embeds, named before they go in: pasting a YouTube, Vimeo or podcast link asks the site’s oEmbed proxy (oembed/1.0/proxy) what it is. QUILL then says the title and author before inserting, and gives the embed a title attribute, so it is never an unnamed frame for visitors.
  • Documents: uploading a PDF or Word file offers “Also Publish as a Page”.
    • It converts the file with the existing converter, opens the result as a new WordPress page for review, and links the two.
    • Many visitors with disabilities find a page easier than a PDF, and the page can be checked (9.4).
    • Nothing is published without the usual Publish.

9.7 Colours that pass, and say so

  • Contrast ratios as part of the name: QUILL reads the theme’s palette and its text and background colours from global-styles. Every colour choice in Block Settings (8.4) then says its contrast against the background it will sit on:
    • “Accent (dark green), 7.2 to 1, passes”;
    • “Pale yellow, 1.4 to 1, too faint for text”.
  • Warn, don’t block: a combination below WCAG AA (4.5 to 1 for body text, 3 to 1 for large text) is allowed but warned about, with the reason.
  • Palette Report: every pairing in the theme, pass or fail. It is useful for a writer whose designer chose the palette, and it can be pasted into “Write a Note for the Theme Author” (9.4).
  • Colour never alone: a block that relies only on colour to mean something, such as red text for “cancelled”, is flagged by Check Before Publishing. The flag suggests also saying it in words.

9.8 The Comments window

Comments are moderated in the same window shape as the Media Library: a Site combo, a status filter (Waiting, Approved, Spam, Trash) and a list.

  • Each row reads: the author, the post, the date and the first words.
  • On a comment:
    • Approve, Unapprove, Spam, Trash;
    • Reply, which opens a small editor with spelling and dictation;
    • Edit;
    • Open on Site.
  • Comment threads: shown as a tree, so replies sit under their parent.
  • Many at once: several comments can be acted on together, with one confirmation that gives the count.
  • Waiting comments: on opening a site, QUILL says how many are waiting, once: “Community Radio: 3 comments waiting”. This can be turned off per site in Sites.

9.9 Menus, widgets and the site map

The parts of a site that are drag-and-drop in the browser are lists here.

  • Menus (menus, menu-items, menu-locations, 5.9+): a tree of each menu. Each row reads “Sessions, page, level 1, 3 of 7”.
    • Add Page, Add Post, Add Category and Add Link;
    • Rename;
    • Move Up, Move Down, In and Out (Alt+Shift+arrows, the block editor’s own keys);
    • Remove;
    • Which Location, for example the header or the footer.
    • Checking the menu: every item must have a name. An item that points to a page that is now a draft or in the Trash is flagged as a dead link for visitors.
  • Navigation blocks (block themes): the same tree, reading and writing the wp_navigation post instead.
  • Widgets (sidebars, widgets, widget-types, 5.8+), for classic themes: each widget area is a list, and each widget has a settings form, generated from its schema as blocks are (8.2).
  • The site map: Site Map is a tree of every page by parent, with each post under its categories. Enter opens an item. Its point is to answer “where does this page live?” without the visual admin.
  • Templates and template parts (5.9+, block themes): read-only. Template Outline lists the header, the footer and the template a page uses, with the blocks in each. That tells a writer why something they cannot find in their page appears on it. Editing templates stays out of scope (8.6).

9.10 The Site Check and the site’s own settings

  • Site Check reads wp-site-health/v1. It gives the WordPress version, the PHP version, HTTPS, available updates, and whether the REST API and loopback requests work. Each answer is a plain line, and “critical” items come first. It is how a site keeper hears that their site is behind, without the admin dashboard.

  • Site Settings (settings, manage_options only):

    • the site title;
    • the tagline;
    • the site language;
    • the time zone;
    • the date format;
    • the front page and posts page.

    These are in one form, and each change is confirmed by name. The site language matters for accessibility: it is the page’s lang attribute, so it decides which voice a screen reader uses for every visitor.

  • Sign Out This Site: revokes QUILL’s application password on the site itself (users/me/application-passwords/<uuid>), as well as forgetting it locally. Remove in Sites asks whether to do both.

9.11 Writing accessibly, as you go

These are in the editor, for any WordPress document, and none needs AI.

  • Language of a passage: Mark Language puts a lang attribute on the selection, for example a French quotation in an English post. A visitor’s screen reader then switches voice there. QUILL’s own Read Aloud honours it too, using the multilingual voices.
  • Tables: Insert Table always asks for a header row and a caption. A table without a header row is flagged by Check Before Publishing.
  • Link text:
    • A link whose text is the address, “click here”, “here” or “read more” is flagged, with its sentence.
    • A link that opens a new tab gets “(opens in a new tab)” added to its visible text, as WordPress itself does.
  • Emoji and symbols in headings and links: these are flagged. A screen reader says the whole name (“sparkles”), and in a heading or link that is heard on every visit.
  • Motion: an animated GIF or an autoplaying video is flagged.
    • An autoplaying video gets an offer to turn off autoplay.
    • A GIF gets an offer to make a still first frame with Pillow, with the animation as a link.
  • Images of text: Describe Image (6.8) says when an image is mostly text. Check Before Publishing then suggests putting the words in the page, where everyone can read and search them.
  • Reading level: an optional readability line in Properties, worked out locally (“Reading level: about 9th grade, 14 words per sentence”). It notes the longest sentences, with Go to It on each.
  • In Short: an optional AI summary of the post in two or three plain sentences, inserted at the top as an “In short” block for the writer to edit. It is a help for readers with cognitive disabilities, and for everyone in a hurry.

9.12 An accessibility statement

Write an Accessibility Statement opens a new page draft from a plain template. It includes:

  • the standard aimed at (WCAG 2.2 AA);
  • the date of the last Check the Whole Site, with its result;
  • known problems that belong to the theme or plugins, from the report;
  • a contact line, with the site’s admin email offered;
  • the date.

It is the writer’s page to edit, and nothing is published without Publish. Running Check the Whole Site later offers to update the statement’s date and known-problems list.

9.13 Administration

Everything the REST API lets an account manage gets a list window or a form. Each one opens from File > WordPress > Manage, and shows only what the account’s role allows (9.2). Every change is confirmed by name and site. Every removal says what happens to whatever depended on the item.

Categories and Tags (categories, tags): one window, two tabs.

  • Each row reads: the name, the slug, the number of posts, and the parent (categories only, shown as a tree).
  • Add, Edit and Delete:
    • Add and Edit set the name, slug, description and parent.
    • Delete says how many posts use the item. A deleted category’s posts fall back to the site’s default category, and QUILL names it.
  • Merge Into: moves every post from one category or tag to another, then deletes the empty one. The API has no merge, so QUILL does it as one batch (batch/v1) after one confirmation that gives the post count. A record is kept, so Undo Merge can put the posts back.
  • Convert: turns a tag into a category, or a category into a tag, the same way.
  • Find Unused: lists items with no posts, for tidying, with several removable at once.
  • Default Category: the one posts get when none is chosen (the default_category setting).
  • Other taxonomies: any custom taxonomy the site exposes (taxonomies with show_in_rest), such as a plugin’s “Event type”, gets the same window, named by its own label.

Users (users, list_users and up):

  • Each row reads: the name, the username, the role, the email and the number of posts.
  • Add User: username, email, name, role and a generated password. WordPress sends the new user their sign-in details, and QUILL never shows or stores the password.
  • Edit: the name, display name, email, role and biography.
  • Change Role: for several users at once.
  • Delete: WordPress requires the user’s content to go to someone else, so QUILL asks who that should be first and names how many posts will move. Deleting yourself is refused, with the reason.
  • My Profile: your own name, display name, biography and website. This is what visitors see on your author page.
  • Application Passwords: lists each user’s application passwords with their names and when each was last used. Revoke works on any one of them, with QUILL’s own marked. It is how a site keeper shuts off an old app or a lost laptop without the dashboard.

Plugins (plugins, activate_plugins; WordPress 5.5+):

  • Each row reads: the name, the version, active or inactive, the author, and whether an update is available (from Site Check, 9.10).
  • Activate and Deactivate: each confirmed by name. Deactivating a plugin that the site’s pages use warns first. QUILL knows this from the blocks and shortcodes it found in Check the Whole Site.
  • Add Plugin: searches the WordPress.org plugin directory by name, reads its rating, its last update and its “tested up to” version, and installs it inactive. Activation is a separate, deliberate step.
  • Delete: only for an inactive plugin, confirmed.
  • Accessibility plugins: QUILL recognises the well-known ones and says what each does. When Check the Whole Site finds a problem a plugin would fix, it says so.
  • Block plugins (block-directory): the block directory offers single-block plugins. Insert Block (8.2) searches it when the site has no matching block, and offers to install one, inactive, after confirmation.

Themes (themes):

  • Each row reads: the name, the version, and active or inactive.
  • What the active theme supports: read-only, from theme_supports. For example the logo, wide blocks, block styles, and editor colours. That explains why an option is or is not offered in Block Settings.
  • Activation: the REST API cannot switch themes, so the window says so and offers Open in Dashboard at the right page.

Pages and posts in bulk (posts, pages, batch/v1):

  • Selecting in Open: the Open list (5.2) allows many items to be selected.
  • Bulk Edit: changes status, author, categories, tags, comment setting or page parent for all of them together.
    • It is one confirmation, naming the count and the site.
    • It is one batch.
    • A version of every item is kept first.
    • Undo Bulk Edit puts them back.
  • Page Order: a tree of pages by parent, with Move Up, Move Down, In and Out. These set parent and menu_order.
  • More in Properties: per item, Properties (5.5) also offers:
    • the page template, from the theme’s templates;
    • the author;
    • the post format;
    • Sticky (keep at the top of the blog);
    • a password for a password-protected item;
    • pingbacks;
    • the publish date, which can be backdated.
  • Other post types: any custom post type the site exposes (types with show_in_rest), such as “Events” or “Products”, appears in Open and in New with its own label. Its fields come from its schema, the same way blocks’ forms are generated (8.2).

Synced patterns (blocks, the wp_block type):

  • Each row reads: the pattern’s name, whether it is synced, and where it is used.
  • Edit: a synced pattern is edited as a document. Saving it updates every page that uses it, and the confirmation says how many.
  • Rename, Delete and Unsync: Unsync turns each use into ordinary blocks first, so nothing on the site goes missing.
  • New from Selection: makes a pattern from the blocks selected in the editor.

Site identity and reading (settings, adding to 9.10):

  • The site icon: the browser tab picture. It is chosen from the Media Library, and a square image is checked for.
  • Reading: posts per page, and whether the front page is the latest posts or a chosen page.
  • Discussion defaults: whether new posts take comments and pingbacks, and whether emoji are turned into pictures.
  • Writing: the default post format.
  • Contact: the site’s admin email and the week’s first day.

Fonts (font-families, font-collections; WordPress 6.5+, block themes):

  • lists the installed fonts and their faces;
  • offers to install one from the site’s font collections;
  • shows each font’s name together with a plain-words description: serif or sans serif, and whether it suits body text or headings.

Choosing which font the theme uses stays a design choice outside QUILL (8.6).

What stays in WordPress: some things the API cannot do. QUILL says so in the one place someone would look for them, and offers Open in Dashboard:

  • switching the theme;
  • WordPress core updates;
  • import and export;
  • multisite network administration.

9.15 More from the API (2026-11-04 review)

A second pass over the REST API found more that is reasonable to use. Each item below is checked against the site’s own index first (routes, namespaces and the account’s capabilities), so a site without it never offers it, and a dimmed command says why.

Writing and reviewing:

  • Notes on blocks (WordPress 6.9+): editorial notes left on a block in the block editor are comments of type note, so QUILL can show them.
    • A Notes list beside the document, each reading “Sam on the second paragraph: tighten this”.
    • Go to It, Reply, and Resolve.
    • Add Note on the block at the caret.
    • This is collaboration a screen-reader user has never been able to join in the block editor. Verify the route on the test site before building.
  • Custom fields: any post meta a site registers for the REST API (show_in_rest) appears in Properties as a labelled field, generated from its schema as block forms are (8.2). That gives SEO titles and descriptions from plugins that register them, event dates, and the like.
  • Which application password is this: Sites shows, for each site, which of the account’s application passwords QUILL is using (users/me/application-passwords/introspect). Sign Out This Site revokes exactly that one.

Pictures:

  • Choose a size when inserting: the library’s own sizes (media_details.sizes: thumbnail, medium, large, full) are offered by name and width in the image dialog. Picking “medium, 300 wide” uses the site’s smaller file rather than scaling the full one in the page. That saves visitors’ data, and it is simpler than Make a Smaller Copy for most cases.
  • Edit a picture on the site (media/{id}/edit, WordPress 5.5+): rotate, flip, and crop to a ratio (square, 4:3, 16:9). The original is kept, the edit makes a new library item, and Describe Image runs on the result so you hear what the crop kept.

Look and layout:

  • Style variations (global-styles/themes/{theme}/variations, block themes): list the theme’s ready-made looks by name, each with its Palette Report (9.7), so a person can choose the variation whose colours pass. Applying one asks first, names the site, and keeps the old one to go back to.
  • Site Styles, the safe subset: the site’s colour palette and font sizes can be edited by name (global-styles/{id}). Every colour shows its contrast against the background as you choose it. Anything else in theme.json stays in the Site Editor (8.6).
  • Pattern Directory (pattern-directory/patterns): search WordPress.org’s free patterns from Insert Block, beside the site’s own. Each one is described in words, with its blocks listed, before it goes in.
  • Pattern categories (wp_pattern_category): Synced Patterns (9.13) can be grouped and filtered by category.

Plugins QUILL recognises:

When a popular plugin’s namespace is in the index, QUILL turns on a small, plain extra for it, and says so in Site Check. Without the plugin, nothing shows. These are sized as “useful in a sentence”, never a full second admin:

  • BITS Accessible Forms (baf/v1): forms (section 17a).

  • The Events Calendar (tribe/events/v1):

    • events in Open, with start, end and venue in Properties;
    • New Event;
    • a plain “Coming up” list.

    Community organisations live on their calendars.

  • WooCommerce (wc/v3), read and light edit only:

    • products in Open, with price and stock in Properties;
    • orders as a list QUILL reads aloud, never edits, and never exports without asking.

  • SEO plugins that register meta (Yoast SEO, Rank Math): the title and description in Properties, with a length count spoken as you type.

  • Accessibility plugins: recognised in Check the Whole Site, which says when one already fixes a finding (9.13).

Running the site:

  • Abilities (wp-abilities/v1, WordPress 6.9+): sites can describe actions they offer to AI agents. Where Choose Your AI is on and the site lists abilities, Ask can use them. Every ability is listed by name, off until checked, approved per use, and shown in the answer. This follows the vendor tools rule in code.md decision 4. Verify the route on the test site.
  • Site Check, every test: the separate Site Health tests (HTTPS, loopback, background updates, the authorization header, page cache) each read as one line. The authorization-header test explains, when it fails, why application passwords would not work.
  • Bulk moderation: select many comments and approve, spam or trash them in one batch, with one confirmation that gives the count.
  • Library-wide alternative text: the Alt Text Review (6.8) extended to the whole Media Library. It steps through every picture with no alternative text, offers Suggest, and saves in batches.

Left out on purpose:

  • editing templates and template parts, beyond reading them (8.6);
  • WordPress core updates and theme switching, which the API cannot do;
  • import and export;
  • multisite network administration;
  • anything that would make QUILL a second dashboard rather than a writing tool.

New value, from routes not yet used:

  • Hear where a link goes before you add it (url-details):
    • Inserting a link: Insert Link reads the target page’s title and description aloud, so a typo in an address is caught at once.
    • Fixing vague link text: for a “click here” or “read more” link that Check Before Publishing found, Fix It offers the target page’s own title as the link text. This one route turns the most common accessibility problem on the web into a one-key fix.
    • Checking links: Check This Page uses it to report links whose pages are gone.
  • Insert Icon (icons, icon-collections, WordPress 7.x): a searchable list of the site’s icons by name. Each one is either decorative, so screen readers skip it, or given a label that says what it means. An icon is never left unnamed.
  • Big uploads that do not fail (sideload, finalize): long videos and big audio files upload in pieces, with progress spoken. After Edit a Picture on the Site, Regenerate Sizes (post-process) remakes the thumbnail and medium copies so the theme shows the edit everywhere.

  • Undo a menu change (navigation and menu-items revisions and autosaves): the Menus window keeps a history, so a removed menu item can come back.
  • How much space the site uses (directory-sizes): Site Check says the size of uploads, themes, plugins and the database, in words (“Uploads: 1.2 GB”). It warns before a big upload on a host that is nearly full.
  • Download a copy of the site’s design (wp-block-editor/v1/export, block themes, administrators): a zip of the theme with the person’s changes, saved to their computer before they try a style variation.

New value that uses routes already in the plan:

  • Send This Document to WordPress: any document open in QUILL can become a new draft on a chosen site, whether a Word file, Markdown, a text file or a dictated note. Its pictures go to the Media Library, its headings become heading blocks, and its first heading becomes the title. This is the most natural way in for a writer who already works in QUILL.
  • Publish to Another Site: copy a post to another connected site, as a draft there. Pictures are uploaded again, and categories and tags are matched by name (or created, after asking). One newsletter on three sites is a common need for people who keep several sites.
  • Duplicate: make a new draft from any page or post, on the same site or another, with everything but the date and status.
  • Download My Writing: every page and post on a site saved to a folder of Markdown or Word files, with pictures and a contents page. It is an offline archive, a backup the person can read, and a way to move house. The export runs in the background and can be resumed.
  • Send a Folder as Drafts: a folder of Markdown or Word files becomes drafts on a site in one go. One confirmation gives the count, and each file is checked first with Check Before Publishing.
  • Coming Up: a list of everything scheduled on every connected site, by date. It answers “what goes out next week?” in one place.
  • What Changed on My Sites: since you last looked, new comments, posts others published, plugin updates waiting and site health warnings, across every site. One list, read on request; never a pop-up.

    • media;
    • categories;

    • revisions;
    • search;

    • Trash is recoverable;

  • Unconfirmed sends: if a send is not confirmed (time-out, lost connection), the local draft stands. QUILL re-reads the site before offering to try again, so it never creates a duplicate post.

17a. Forms (merged from forms.md, 2026-11-04)

Forms are written in BITS Accessible Forms’ language (BFL) and published to sites running BAF, so they belong with the rest of WordPress. They also work with no site at all, as web pages, Word documents and braille-ready copies.

17a.1 What this is

Write, check, try out and publish accessible forms from QUILL and QUILL Lite: contact forms, event registrations, membership renewals, surveys and feedback forms. You write the form as a short, readable text document, in the editor you already use, and QUILL turns it into:

  • a form on a WordPress site;
  • a standalone web page;
  • a printable or large-print document;
  • a braille-ready copy.

You can fill it in yourself, with your screen reader, before anyone else sees it, and read the responses afterwards in a list.

Why. Building a form today almost always means a drag-and-drop canvas, which is one of the hardest things on the web for a screen-reader user. But a form is really structured text: a title, pages, sections, questions, choices and rules. QUILL is good at text.

QUILL Accessible Forms (QAF), first called BITS Accessible Forms (BAF) (S:\code\qaf, which was S:\code\baf until 2026-11-08), is the WordPress side. It is a WCAG 2.2 AA form plugin with a plain form language, BFL (Barrier-Free Language), a REST API, 30+ field types, choice libraries, conditional logic and entry views. QUILL does not build a second form engine for the web. It becomes the accessible way to write, check and manage BAF forms, and it brings over everything from BAF that makes sense on a computer rather than a server (17a.3).

Four rules shape the plan:

  1. Simple first. A contact form is New Form, three questions, Publish.
  2. Both editors. QUILL and QUILL Lite get the same forms, from one shared module. Lite is never behind and never ahead (CLAUDE.md).
  3. One language. Forms are written in BFL, exactly as BAF reads it. No third syntax beside Markdown and QUILL’s ::: fences.
  4. People’s answers are private. Responses stay on the site. QUILL reads them only when asked, says what it is downloading, and never writes them to a log.

17a.4 Writing a form

17a.4.1 New Form

  • Where: File > New > Form…, in both editors.
  • It asks for:
    • the title;
    • a template: blank, contact, event registration, membership renewal, survey, accessibility feedback, or volunteer sign-up;
    • where it will live: a WordPress site with BAF, or “just this computer” for HTML and print.
  • The result: a BFL document (.bfl), with syntax colouring where the editor has it, and headings for pages and sections in heading navigation.

17a.4.1a What a form looks like in the document

A form is plain BFL text, one question per few lines, so it reads naturally line by line and every editor tool works on it:

form "Spring fair sign-up"
@submit_label "Sign me up"

section "About you"

text "Your name" #name
@required
@autocomplete name

email "Email address" #email
@required
@help "We only use this to confirm your place."

radio "How did you hear about us?" #heard
  "A friend"
  "Our newsletter"
  "Somewhere else"

if heard is "Somewhere else"
  text "Where?" #heard_other

page

select "Which session?" #session
@choices time_slots_hourly
  • Headings: a section line and a page line are headings for heading navigation, so you can jump between parts of a long form.
  • Labels: a question’s label is in quotes, followed by its #id.
  • Settings: the lines starting @ underneath set what it does.
  • Indented lines are its choices, or the questions a rule shows.
  • Rules: an if line reads as the sentence it is.
  • No hidden markup. There is nothing but this text.

17a.4.2 Insert Field

  • Where: Insert > Form Field…, with a key.
  • The list: every field type, searchable, with a one-line description.
  • On choosing one: a short form asks only what that field needs, for example label, id, required, help text, choices, or a choice library (searchable). Insert writes BFL at the caret, in the block style the document already uses.
  • Insert Section and Insert Page Break sit beside it.

17a.4.3 The form outline

  • Where: View > Form Outline.
  • What it shows: a tree of pages, sections and fields. Each row reads “Email address, email field, required, page 1”.
  • What you can do:
    • Enter goes to the field;
    • Move Up and Down, and In and Out, with Alt+Shift and the arrows;
    • Duplicate, Remove;
    • Change Type.
  • Undo: each is one undo step.
  • The same shape as the WordPress Blocks window, so it is learned once.

17a.4.4 Rules in sentences

Rules (Format > Form Rules…) lists every condition as a sentence:

  • “Show Company name when Type is Business.”
  • “Total is Quantity times Price.”
  • “Show State when Country is United States.”

Add Rule builds one from three choices: when what, is what, then what. QUILL writes the BFL if block, and reads the sentence back. Nobody has to edit rule syntax unless they want to.

17a.4.5 Form Properties

Form Properties… holds everything that is not a question:

  • submit label, success message, redirect;
  • notifications and autoresponders;
  • submission limits and scheduling;
  • whether CAPTCHA and the honeypot are on (read-only);
  • the BAF form id and site, once published.

17a.5 Checking a form

Check This Form runs locally while you write, as Check Before Publishing does for pages (section 7). Every finding says what to fix, with Go to It. It looks for:

  • a field with no visible label, or a label that is only a placeholder;
  • a group of choices (radio, checkbox, Likert) without a group question;
  • required fields marked only by an asterisk or colour;
  • a field with a format rule (mask, pattern, minimum) and no help saying what is expected;
  • name, email, phone and address fields without autofill hints (the autocomplete tokens BAF writes);
  • a rule that points at an id that does not exist, or hides a required field forever;
  • a page with no questions, or a form over 30 questions on one page;
  • duplicate ids;
  • a choice list over 15 items that would be easier as a library or a search.

BFL errors (an unclosed block, an unknown modifier) appear in the same list, with BAF’s own wording, and so do the site’s /bfl/validate results when connected.

17a.6 Fill It In Yourself

Fill It In Yourself builds the form as a real, native window in QUILL, from the same BFL, with the shared rules evaluator. You tab through it exactly as a visitor would:

  • labels, groups, help text, errors and required states are announced;
  • pages have Next and Back;
  • conditions show and hide fields as you answer;
  • calculations update.

Submit does not send anything. It shows what would be sent, as a list of question and answer pairs, and checks every rule. Test on Site sends one marked test entry through /submit/{id} when connected, so the whole path can be proved. It is deleted afterwards if the account can.

This is the feature only QUILL can offer: a screen-reader user hears their own form before anyone else does.

17a.7 Publishing and exporting

  • Publish Form (to a site with BAF):
    • it creates or updates the form through /forms, after a confirmation naming the site;
    • conflict protection and previous versions work as for pages (5.4, 5.6);
    • Insert Form Into Page puts the form’s block or shortcode into a WordPress page.
  • Save As Web Page: a standalone, accessible HTML form, using BAF’s markup patterns. It submits to an address you give, or nowhere when it is for printing.
  • Save As Word Document: a printable form, with lines to write on, and check boxes as boxes. A large-print version uses 18 point and up.
  • Save As Braille-Ready Text: one question per block, with choices listed, through QUILL’s braille output.
  • One source, every format, so a paper form and its web form can never disagree.

17a.8 Responses

  • Responses… lists a form’s responses newest first: “Response 41, 3 November, 2:10 PM, Jane Smith, Event registration”.
  • Views:
    • list;
    • one at a time: question and answer pairs, read line by line;
    • grouped by date: the calendar view;
    • grouped by place: the map view.
  • Find: across every answer.
  • Export:
    • to Table and CSV Studio, as an accessible grid;
    • to CSV;
    • to a Word document for one response, or all of them.
  • Delete: a response, or several, after a confirmation that gives the count.
  • Waiting count: “4 new responses to Event registration”, when you open a site, like waiting comments in WordPress. You can turn this off.
  • Privacy: responses are downloaded only when Responses is open, kept in memory, and never written to a log. Exports go where you choose.

17a.9 AI, optional

Through Choose Your AI, as everywhere else in QUILL:

  • Draft a Form: describe it in a sentence, get BFL to read and edit. It is a proposal, applied as one undo step.
  • Plain Language: rewrite the questions and help text more simply, proposed for review.
  • Suggest Autofill Hints and Help Text: for the fields Check This Form flagged.
  • Summarise Responses: a written summary of a survey’s answers. It sends the answers to the AI, so it asks first, every time, and says how many responses it would send.

17a.14 Is BFL complete? Not yet (checked against BAF’s code, 2026-11-04)

BAF has 67 field classes (includes/fields/). Its BFL parser recognises fewer.

Field types BFL cannot write or read today (absent from the parser’s type list, the compiler, and the language guide):

  • Input: appointment, colour, currency, range and slider, toggle, OTP (one-time code), rich text, typed signature.
  • Choice: image choice, matrix (grid questions), NPS (net promoter score), quiz (questions with scoring).
  • Other: map, payment, progress, social, summary, table.
  • Validator gaps: the validator also rejects the WordPress fields BAF supports for posting content and registering users: post title, content, excerpt, image, category, tags and custom field; user email, login and password.

columns and page work, as layout keywords rather than field types.

What this means: a form built in BAF’s visual builder with any of those fields cannot be exported to BFL and back without losing them. So today BFL is a subset of BAF, not its whole language.

Combinations BFL cannot express yet:

  • Conditions are single tests. The operators are is, contains, starts, ends, greater, less, empty and filled. There is no “and” or “or” in one condition, no “is not”, no “is one of”, and no “else”. Nesting if blocks gives “and”, but “or” needs the questions repeated.
  • No page-level or section-level conditions, to skip a whole page.
  • No date comparisons (before, after, within N days), and no comparing two fields with each other.
  • Calculations: check the formula language against the calculation, total, price, quantity and coupon fields. Those fields exist, but are only partly reachable from BFL.
  • Repeaters with nested sections or conditions inside them: untested.
  • Quiz scoring and outcomes (score to message), and save and resume (the save field): not in BFL.

The plan: make BFL complete in BAF itself. That is the language’s home, and QUILL must match it byte for byte. Work in S:\code\qaf:

  1. One written BFL specification, beside the guide, listing every field type with its modifiers, every block style, and the condition and calculation grammar.

  2. Add the missing field types to the lexer, parser, validator, compiler, exporter and formatter, with an example of each in the guide.

  3. Extend conditions:

    • and, or, not;
    • is one of;
    • else;
    • date operators;
    • field-to-field comparison;
    • conditions on page and section.

    Every condition still reads as a sentence.

  4. Quiz scoring, outcome messages, and save and resume.

  5. A round-trip conformance suite: every field type and every combination is built in the visual builder, exported to BFL, imported again, and compared. The same fixtures run against QUILL’s Python reader (17a.13, question 2).

  6. Only then does QUILL’s Insert Field offer the new types, and Check This Form learns their accessibility rules. For example:

    • a matrix needs row and column headers;
    • a colour picker needs a typed alternative;
    • a map needs a written location field;
    • an OTP field needs its digits announced one at a time.

Until BFL is complete, QUILL keeps any field it cannot express as an island (the same idea as unknown blocks, 8.1). It is shown as one protected line, and sent back unchanged, so opening a form in QUILL never loses a field.

17a.15 The foundation: a JSON form model, with BFL as its readable face (Jeff, 2026-11-04)

This replaces 17a.14’s plan of extending BFL on its own. BFL stays what people write, but it is no longer the definition.

  1. The form model. A documented JSON model, with a published JSON Schema, is the single definition of a form:

    • fields and their types;
    • pages and sections;
    • choices and choice libraries;
    • rules, calculations and scoring;
    • smart defaults and masks;
    • translations;
    • settings and confirmations;
    • a version.

    BAF stores this model. BAF’s visual builder, BFL, and QUILL’s windows are all views of it. Every feature exists in the model first, so no view can fall behind.

  2. One expression language for conditions, calculations, quiz scoring and smart defaults. It is small and fully specified:

    • and, or and not;
    • comparisons, and is one of;
    • dates (before, after, within N days);
    • field references and arithmetic.

    The model stores the expression. BFL and QUILL show it as a sentence (“Show Company name when Type is Business or Type is Charity”).

  3. BFL becomes a readable notation of the model, and nothing more:

    • every model feature has a BFL spelling;
    • BFL to model, and model to BFL, round-trip exactly;
    • BAF’s PHP and QUILL’s Python both check against the same schema, instead of two parsers trying to agree.

    The missing field types and conditions (17a.14) are added to the model first, then given their BFL spelling.

  4. Import and export, each a mapping to and from the model:

    • SurveyJS JSON;
    • XLSForm (the spreadsheet form standard in community and humanitarian work);
    • Google Forms, through its API;
    • plain HTML forms;
    • the WordPress form plugins: Gravity Forms, WPForms, Contact Form 7 and Ninja Forms.

    Anything a source has that the model cannot hold is listed in an import report, never silently dropped.

  5. Translations built in: one form, several languages, with each language’s labels, help and messages side by side. Fill It In Yourself can be run in each language.

  6. Versioning:

    • The form: each form carries the model version it was written for.
    • Old forms: older forms are upgraded by a documented migration, and never broken.
    • BFL: a form written in BFL carries its version on its first line.

  7. A shared conformance suite, in the BAF repository:

    • the schema;
    • an example of every field type and every rule shape;
    • the round trips BFL to model to BFL, and builder to model to builder;
    • every import and export.

    QUILL runs the same fixtures against its Python reader in CI.

Where the work happens:

  • S:\code\qaf: the model, the schema, the expression language, BFL’s mapping, the builder’s mapping, the conformance suite, and the imports and exports that run on the site.
  • quill/core/forms/: the same model and its expression evaluator in Python, BFL in and out, schema checking, and the imports and exports that run on the computer (XLSForm, SurveyJS, HTML). QUILL and QUILL Lite share it.

17a.16 BAF is the forms plugin (Jeff, 2026-11-05)

Forms on a site use BITS Accessible Forms (BAF). Nothing else on the site needs a plugin: every other WordPress feature uses only WordPress’s own REST API and application passwords.

The reason a plugin is needed at all: WordPress has no forms. Something on the site has to show the form to visitors, check and store their answers, send the emails, and keep spam out. QUILL runs on the writer’s computer, so it cannot do that for visitors.

Without BAF: a site without BAF can still use a form saved as a standalone web page (Save As Web Page). That page submits to an address the writer chooses, and has no Responses window.

Not now: other form plugins (Gravity Forms, WPForms, Contact Form 7, Ninja Forms) are supported for import only. Publishing to them is not planned unless people ask for it.

17a.17 The name: QUILL Accessible Forms, and .qaf files (Jeff, 2026-11-05)

  • The plugin’s new name: BITS Accessible Forms (BAF) is renamed QUILL Accessible Forms (QAF), in its plugin header, slug, text domain, readme, docs and admin screens.

  • The code: the plugin is not released yet, so its code prefixes move as well:

    • the PHP class prefix BAF_ becomes QAF_;
    • the REST namespace baf/v1 becomes qaf/v1;

    baf/v1 stays as a read-only alias for one release, so a test site already running it keeps working.

  • Form files are .qaf. That answers 17a.13 question 1: a form saved from QUILL or QUILL Lite is name.qaf, opened by File > Open, recognised by its first line (bfl 1, the form language’s version), and associated with QUILL by the installer.

  • The language inside a .qaf file keeps its readable form. It is called the QAF form language in user-facing text, rather than BFL.

  • QUILL’s side: menus, help, docs, tutorials, the regression plan, and the .bfl constant that becomes .qaf.
