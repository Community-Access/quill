QUILL Lineups: rule-built, hand-ordered listening for Radio and Cast

Status: as built, 2026-10-13. This is the design of record for QUILL Lineups in Quill Radio and QUILL Cast. It began as a proposal for review (the root rules.md, revisions 1 to 4); this version keeps that proposal’s reasoning and corrects everything that changed while it was built. Where the proposal and the code disagreed, the code won, and the difference is named in “What changed from the proposal” at the end.

The requirements as a contract are section 23 of the Quill Radio PRD (standalone/radio/docs/prd.md); the listener’s account is Chapter 17 of the Quill Radio user guide; the Radio tutorial is Build a lineup that fills itself (quill/core/radio/tutorials/lineups.py).

The public promise

The design keeps every part of the announcement (2026-10-13):

This will come in the next release for both Radio and Cast… QUILL Lineups. Fully rule and hands on driven. It is a sophisticated way of bringing anything in, including local media, into a list. You will be able to order the list, add and remove items yourself or automagically based on rules that you personally define.

Promise Where it is kept
The next release, Radio and Cast One engine and one window module, used by both apps; one shared file.
Named QUILL Lineups Decided: “Lineups” in menus, window titles and F1; “QUILL Lineups” where the feature is introduced.
Rule-driven and hands-on Rules bring items in and say when they go; the listener’s hands outrank them.
Bring anything in, including local media Nine kinds, from both apps, including Radio’s Local Media from Cast’s window.
Order the list yourself Moves are the listener’s; a refresh never reorders.
Add and remove items yourself Add to Lineup on every row that plays; Delete, and removed means removed.
Or automatically, by rules you define Rules, each with its own Keep choice, explainable through Why Is This Here.

1. The idea in one paragraph

A Lineup is a named list of things to listen to or watch, built by rules the listener writes and ordered by hand. “Morning” might be: the two news stations I always start with, which never leave; every unplayed episode from my News folder published since yesterday, each gone once I have heard it; and my saved YouTube videos, each kept for two weeks. Every rule says what comes in and when it goes. The listener moves items, keeps the ones that must stay, and removes the ones they do not want, and the rules never undo what the listener’s hands did. One list can hold any mix of radio stations, saved browse places, podcasts and episodes, YouTube videos, playlists and channels, recordings and Radio’s Local Media.

2. The name

QUILL Lineups, decided. “Presets” already means Alt+1 to Alt+0 in Radio (the first ten favorites), and a listener expects a preset to be one station on one key. “Smart List” collides with Cast’s smart playlists, “Mix” suggests shuffled music and is YouTube’s word, “Station” collides with every real station, and “Channel” collides with the YouTube channels a Lineup contains. “Lineup” is broadcasting’s own word for “what is on, in order” and reads naturally for stations, episodes and videos alike.

Before Lineups, Cast’s Play Queue had Save Lineup… and Apply Lineup… over manual playlists that held a snapshot of the queue. Two meanings of one word in one family would have been a trap, so those verbs now save to and apply from QUILL Lineups (section 10).

3. Who it is for

The same morning took five windows: Favorites for the stations, Cast’s Inbox or a smart playlist for the episodes, Radio’s My YouTube for the videos, Local Media for the downloaded talk, and memory for the order. Cast’s smart playlists see only episodes, and an episode leaves the moment it stops matching. Radio’s Favorites hold stations and places but never refill. A Lineup is the one list that sees both apps, keeps itself fresh, and lets each rule decide how long its items stay.

Success: a listener opens Lineups, arrows to Morning, presses Enter, and the morning plays in the order they chose, with yesterday’s heard episodes gone, today’s in, and the two stations exactly where they always are.

4. What a Lineup can hold

Every item is a reference, never a copy: an ItemRef(kind, key) (quill/core/lineups/refs.py), where the key is the identity that thing already has in its owner. Row text is resolved at display time, so a renamed show reads correctly.

Kind Key Read from Listed completely?
Radio station the Favorites station key (stats.station_key) Favorites, station tags, recently played No
Saved browse place the browse: node id Favorites No
Podcast (a follow) Cast show id podcasts_library.json Yes
Podcast episode show id and episode guid podcasts_library.json Yes
YouTube video the normalised watch URL saved YouTube items No
YouTube playlist the normalised playlist URL saved YouTube items No
YouTube channel the normalised channel URL followed channels No
Local Media item playlist id and item id radio-local-media.json Yes
Recording the recordings index id the recordings index Yes

Every kind is available in both apps. Both read the same data folder; a Lineup made in Cast can hold a radio station, and one made in Radio can hold a Cast episode. If an app cannot play a kind, it hands the row to the app that can (section 7).

4.1 Four answers, not three

The proposal had three answers to “what is this reference now?”. Building the sources showed a fourth was needed:

Answer Meaning Example
present The owner knows it, with its facts. The episode is in the library.
missing The owner says it no longer exists. The show was unfollowed; the recording was deleted.
unavailable The owner could not be asked. Cast’s library could not be read.
unlisted The kind’s source is only part of the world, and this one is not in it. A station added from a directory search that is not in Favorites, tagged or recent.

Only a complete kind (episodes, shows, Local Media, recordings; sources.COMPLETE_KINDS) can be missing: if Cast’s library does not list an episode, it is gone. Stations, places and YouTube come from lists that are only part of the world, so not finding one says nothing about whether it exists. Treating “not in Favorites” as “missing” would have marked every station added from a search as missing on the next refresh.

Rows of partly listed kinds store their play data. A row added by hand carries the owner’s own serialised record (Row.payload, a RadioStation’s dictionary for a station or a video), so an unlisted row still plays exactly as it did when it was added.

5. Rules: what comes in

5.1 The shape

A Lineup has zero or more rules (quill/core/lineups/rules.py). Each says, in the order its sentence reads:

  1. What kind it looks for: one kind per rule.
  2. Where to look: a scope field (Folder, Podcast, Label, Channel, Favorites folder, and so on) and any number of its values. Values are ORed; fields are ANDed with each other and with the tests, as Cast scopes a smart playlist.
  3. Which ones: tests of field, test and value, with Match all or Match any.
  4. In what order: as the source orders them, newest, oldest, shortest, longest, by name, most listened.
  5. How many: a count limit, a per-group limit (per podcast, channel, album or Favorites folder; fields.GROUP_FIELDS), and “up to N minutes in all”.
  6. How long they stay: the rule’s Keep choice (section 6).

Rules OR with each other: the Lineup is everything any rule brings in, plus what the listener added. This is Cast’s Episode Filters model (tests ANDed inside a rule, rules ORed), which listeners already know.

Every rule reads back as one sentence (describe.rule_sentence), including how long its items stay and what it finds now:

Podcast episodes in folder “News”, where Played is no and Age is at most 1 days, newest first. They go once finished, or after 2 days. Finds 3 now.

Radio stations in favorites folder “Morning”. They always stay.

5.2 One engine, generalised from Cast’s

The tree had three rule models. Beacon’s saved searches are AND-only and tied to its database; Cast’s two (filter_conditions, playlists) were the right foundation, wx-free and strictly typed. quill/core/lineups/conditions.py reuses Cast’s operators and spoken phrases over a per-kind field registry (fields.py), which is the one thing Cast’s engine lacked. Its rules carry over unchanged:

  • A missing number never matches a number test. A podcast with no length is never “at most 10 minutes”.
  • An unknown field or kind is kept but disabled, so a rule written by a newer build matches nothing and says “It finds nothing until it is fixed”, rather than silently widening to everything.
  • An empty rule never makes “any” match everything: one predicate per test that is set, then sort, then limits.

The packages, as built:

Module What it holds

fields.py Per-kind fields (text, number, yes/no, list) and ItemFacts.
conditions.py Tests over fields, built on Cast’s operators.

5.3 What a rule can test

All of these come from what is already on disk; none needs the network.

Kind Fields
Episode Title, Podcast, Folder, Label, Age, Length, Played, Started but not finished, Percent heard, Downloaded, Season, Episode number, Episode type, Days since last played
Podcast Title, Folder, Label, Favorite, Paused, Language, Category, Unplayed episodes, Newest episode age
Station Name, Favorites folder, In Favorites, My tag, Directory tag, Country, Language, Codec, Bitrate, Source, Time listened, In recently played
Place Name, Source, Favorites folder
YouTube video Title, Channel, Length, Live, Saved by me (no Age: saved videos carry no date)
YouTube playlist Title, Channel, Number of videos
YouTube channel Name, New-video alerts on
Local Media Title, Artist, Album, Playlist, Length, Days since added, Is a video
Recording Name, Length, Age, Status

Text tests: contains, does not contain, starts with, ends with, is, is not, wildcard, matches or does not match a regular expression. Number tests: at least, at most, is, is not. Yes/no fields: is, is not. A list field (tags, labels) passes a text test when any one value does.

5.4 What rules deliberately cannot do

  • Query the internet. Rules read Favorites, station tags, recent stations, saved YouTube items, followed channels, Local Media, the recordings index and Cast’s library. The network egress audit is unchanged, and a refresh works offline.
  • See every YouTube upload. The proposal assumed a subscriptions cache on disk. There is none: videos in a followed channel’s feed are fetched over the network as the listener browses and are not kept. So rules see saved videos and playlists and followed channels, there is no “every new upload” starter, and the user guide says so rather than hiding it.
  • Change anything. A rule never marks an episode played, follows a show or downloads a file. Cast’s library is only read.
  • Name a folder that does not exist and widen. Such a rule finds nothing, and its sentence says so: ‘in folder “News”, which does not exist’.

6. Rules: when things go

6.1 Entry and exit are separate questions

An item that leaves the moment it stops matching is right for “unplayed episodes” and wrong for almost everything else. A news station should never leave. A new video should stay a few days. An episode should stay until it is heard even once it is no longer “published in the last day”. So every rule has two halves: tests decide what comes in; Keep decides when it goes.

6.2 The Keep choices

Keep (code) The item goes when
While it matches (follow) It stops matching the rule.
Until finished (until_done) It has been played to the end, or past a percentage (default 95). Cast’s own “played” always counts.
For a number of days (for_days) N days (1 to 365) after the rule claimed it, whether it still matches or not.
Until finished, or a number of days (until_done_or_days) Whichever comes first.
Always (always) Never, unless removed by hand.

Max kept caps a rule on top of any choice: the newest N claims stay, so a “for days” rule over a busy source cannot fill the Lineup. The per-group cap (“at most 1 per podcast”) is part of “how many” (5.1), which is how “the latest from each” works without a second mechanism.

Defaults follow the kind (rules.default_keep): episodes, YouTube videos, Local Media and recordings get Until finished, or 7 days; every other kind gets While it matches.

Some kinds are never finished. Stations, places, podcasts, channels and playlists are not offered either “finished” choice. A stored “until finished” on such a rule (from an import, or a kind change) reads as its nearest real meaning (Keep.effective): Until finished becomes While it matches, and Until finished or N days becomes For N days. Without that, a station rule would keep its stations forever by accident.

A choice from a newer build reads as Always, the cautious reading: keeping things is recoverable, letting them go silently is not.

6.3 The row record

Field Meaning
ref The ItemRef.
name The last name the owner gave it, for rows nobody can resolve.
claims Rule id to the time that rule first claimed it. Rule ids are stable, so reordering or renaming rules never breaks a claim.
held None, kept or added: the listener’s hand.
moved Whether the listener moved it, for the budget (section 7).
arrived When it entered this Lineup.
payload The owner’s own record, for partly listed kinds (4.1).

The listener’s hands outrank the rules:

Hand state Effect
Added by hand Stays until removed. Adding an item that a rule already brought in makes it held too.
Kept (Keep This Item, Ctrl+K) Stays whatever its rules say; toggle off to give it back to them.
Removed (Delete) Leaves now, goes to Removed Items, and no rule ever brings it back. Adding it by hand again takes it off Removed Items.

6.4 When two rules claim the same item: it stays while any claim holds

The proposal said “the longest-lasting claim wins”. As built, the rule is simpler and stronger: an item stays while any claim holds it. Each claim is judged by its own rule’s Keep choice; when one lets go, the item stays as long as another still wants it, and its position never changes because a claim was added or dropped. KEEP_STRENGTH survives only to choose which reason Why Is This Here gives first.

6.5 Released memory

A rule can let an item go while still matching it: its days ran out, the listener finished it, a cap pushed it out. Without memory, the very next refresh would see it match and bring it straight back. So a release is remembered per rule (Lineup.released) and cleared once that rule stops matching the item; after that, a fresh match is a fresh arrival. The same test guards arrivals: a new claim must pass the exit test it would face on the next refresh, so an episode already heard never arrives in an “Until finished” rule only to leave a moment later.

6.6 Guarantees

Each is a test in tests/unit/core/lineups/test_lineup_merge.py:

  1. Nothing leaves because something could not be checked. A row whose owner is unavailable, or whose rule cannot be evaluated (off, unusable, its kind unreadable), is left exactly as it was.
  2. Nothing leaves without trace. Every departure is in Recently Left (the last 100 per Lineup) with its reason: “finished”, “2 days passed”, “it no longer matches rule 2”, “it no longer exists”, “rule 1 keeps at most 5”.
  3. A removed item never returns from any rule.
  4. A kept or hand-added item never leaves except by hand.
  5. Refresh never reorders. Surviving rows keep their relative order.
  6. Refresh is idempotent.
  7. Time is measured, not counted. “3 days” is 72 hours from the claim.
  8. An item stays while any claim holds it.

And two outside the merge:

  1. A rule change never takes anything silently. Deleting a rule that brought items in asks Keep Them or Let Them Go; a change that lets items go says how many before OK; Cancel changes nothing.
  2. A big loss is reported. If one refresh removes more than half a Lineup and more than 10 items (BIG_LOSS_MINIMUM), it is still applied (it is what the rules say) but said plainly: “18 items left Morning: 7 days passed. Recently Left can bring them back.”

6.7 One refresh, in order

merge.refresh is pure and deterministic:

  1. Resolve every row. Unavailable rows are carried over untouched.
  2. Evaluate each active rule (on, usable, its kind readable).
  3. Add new claims to existing rows first, so a row one rule lets go while another now wants it simply stays where it is.
  4. Judge every claim by its rule’s Keep; drop the ones that let go, remembering releases.
  5. Rows with no claims and no hand state leave, recorded in Recently Left.
  6. Gather arrivals in rule order; an item two rules find arrives once with both claims.
  7. Apply Max kept caps, newest claims first.
  8. Place arrivals by the Lineup’s New items go setting: with the other items from the same rule (default), at the top, or at the bottom.

7. Playing a Lineup

  • Enter on an item plays it and carries on to the end; Enter on a Lineup plays the Lineup. Ctrl+Alt+P plays the whole Lineup from the top. Ctrl+Shift+Enter (Play Next) and Ctrl+Alt+Enter (Add to Up Next) mean what they mean in Local Media.
  • In Radio, a session on the player controller (quill/ui/radio/lineups_playback.py) plays mixed kinds one after another and advances at each natural end (track_end, after the reconnect and book checks). Starting a Lineup ends a Local Media session, because two lists cannot both decide what comes next. A podcast plays its newest unplayed episode.
  • Live things never end. A live item plays until the listener moves on, and the first one in each run says how: “Live. Press Ctrl+Shift+Period for the next item.” The app-wide Next Chapter and Previous Chapter keys (Ctrl+Shift+. and Ctrl+Shift+,) step a Lineup playing through from any window, even on a live stream; on an episode or file with chapters, chapters come first. Next at the last item says “This is the last item.” and keeps playing, because a key that ends the run by accident is worse than one that says it cannot go further. Skip Live Items (per Lineup, off by default) leaves them out.
  • Say what cannot be seen: “Skipped The Archers, missing.”, “End of Morning.” at a natural end, and “Stopped after X.” when Stop After This Item stops. A YouTube item says “Starting X.”, not “Playing X.”, because it can still be refused.
  • The play-through budget (per Lineup, in minutes) leaves rule rows out from the end; kept, added and moved rows are never left out, and the item the listener chose always plays.
  • Places open Browse. A saved place or a YouTube channel is somewhere to browse, not something to play. Enter on one opens Browse Stations, and a play-through skips it. Browse Stations opens at its top level: it cannot yet be opened on a given node, so the sentence says the place is under Favorites if it was saved there. This is a gap, not a design.
  • In Cast, episodes play through Cast’s Play Queue: the chosen episode and the Lineup’s episodes after it go to the front of the queue, by the same rule Apply Lineup always used, and Cast carries on by itself. Stations, YouTube, Local Media and recordings are handed to Radio (handoff.py): a small request naming only the Lineup and the rows, through the family open-request queue with the action lineup_play, opening Radio if it is not running. Radio reads the rows from its own copy of lineups.json and plays them; no URL travels in the request.
  • Finishing is the owner’s fact. “Until finished” reads Cast’s own played state and position; a Lineup never writes Cast’s library.

8. Where the data lives

  • One family file, lineups.json in the shared data folder, versioned through versioned_store (schema 1), written with write_json_atomic, in Radio’s backup set (RADIO_DATA) and Cast’s. It holds each Lineup’s name, rules with stable ids, settings, rows, released memory, Removed Items and Recently Left.
  • Each app’s Start Here is that app’s own setting (start_lineup_id in each app’s history), not part of the shared file, because each app starts on its own.

8.1 Two apps writing one file

“Load, change, save the whole file” would let the last save win and throw away the other app’s edit: exactly the hazard the survey found in Radio’s writes to Cast’s library. So the file is never saved from a copy held in memory (store.py, ops.py):

  1. Every change is an operation named by keys, never by positions: “move this item to just after that one”, “keep these”, “replace these rules”, “refresh this Lineup”.
  2. Applied under a short lock. The app creates a lock file beside lineups.json exclusively, re-reads the file, applies the operation to what it just read, writes atomically and releases the lock. A lock older than 10 seconds is treated as abandoned, so a crash cannot wedge either app.
  3. An operation that no longer makes sense is a no-op and says so, rather than guessing (“Those items have left the lineup since they were cut.”).
  4. The other app notices the file’s size and modification time, checked every two seconds, and reloads by key, so its cursor does not move.
  5. Every Lineup and the book carry revision numbers, increased by every operation, and test_two_apps_writing_at_once_lose_nothing proves that two writers interleaving their edits lose none of them.
  6. A refresh is an operation too: the catalogue is gathered off the UI thread, then each Lineup is folded under the lock against the file as it is then, so a move the other app made a moment ago is never undone by a refresh.

9. The window

9.1 A peer window with its own menu bar, in both apps

The Lineups window (quill/ui/lineups/window.py) is one module used by both apps through a small host (quill/ui/radio/lineups_host.py, quill/ui/podcasts/lineups_host.py). It is a peer window, like Local Media: its own taskbar entry, on the Window menu and in the Ctrl+Tab order, one per app. Its own menu bar (Lineup, Edit, Arrange, Play, then the app’s Station and Window menus) comes from one table (menus.py) that also labels the context menus and answers the keys, so the three cannot drift. A window of its own was chosen because the main window’s menu bar had no free keys left; here F5 can be Refresh Now.

Reached, in Radio, from Playback > Lineups… (radio.lineups, Ctrl+U), every peer window’s Station menu (surface_app_menu.COMMANDS), the Go To pool, and the Command Palette (“Internet Radio: Lineups…” and “Lineups: Go to a Lineup…”); in Cast, from its own menu and palette on the same chord (family rule 2). Ctrl+Alt+U, the first choice, is Help > Check for Updates in both apps; the menu-accelerator gate caught it.

9.2 Layout

  1. Lineups: “Morning, 14 items, 1 hour 50 minutes, 2 new, start lineup”. Moving the selection loads that Lineup’s items at once. Enter plays it, Alt+Enter edits its rules, F2 renames, Delete deletes after asking, Alt+Shift and the arrows move it.
  2. Show: All kinds; Episodes and podcasts; Stations and places; YouTube; Local media and recordings. Moves in a filtered view move among the visible items. This replaced the proposal’s Group By Kind, which would have needed a tree, with its extra level speech and a second ordering model.
  3. Items: a report-mode list whose rows are one sentence in a fixed order, name, kind, length, source, state (Radio PRD section 13, the columns are the sentence). The name is first so first-letter navigation lands on the thing itself; state is last and only present when there is one (kept, missing, unavailable, played, live).
  4. A real status bar: “Morning: 14 items, 1 hour 50 minutes. Updated 06:02.” Lineup Summary (Ctrl+T) speaks the same, then each rule.

Empty: a sentence, New Lineup (focused) and Start from an Example buttons; the sentence is said once. An empty Lineup’s status reads “Morning is empty. Its rules find nothing now.”

9.4 What the screen reader hears, and what it does not

GATE-12 and GATE-13: say only what the reader does not already say.

  • A move speaks the new position only: “Moved to 3 of 14.” At an edge: “Already at the top.” Never the row text.
  • A refresh with the window active changes rows without moving the cursor: only rows whose words changed are rewritten, and the selection is restored by reference. One queued outcome sentence follows, through the listener’s feedback setting: “2 added, 1 left.” If the selected row left, that is said first (“Your item left: finished.”) and the cursor goes to the row that took its place, never to the top. A timed refresh with no change says nothing; Refresh Now always answers (“No changes.”).
  • Other Lineups say nothing; their arrivals show as “2 new” on their row until the Lineup is chosen.
  • Delete answers “Removed. Removed Items can bring it back.” (with the count when several were removed), and every undoable action ends with the family’s “Ctrl+Z undoes this.”
  • Failures always speak: “Lineups could not be refreshed: …”.

9.5 Why Is This Here

Alt+Enter on an item opens a read-only box whose text is built from the row record:

In Morning because rule 2 found it: Podcast episodes in folder “News”, where Played is no and Age is at most 1 day, newest first. They go once finished, or after 2 days. 1 day left.

In Morning because you kept it. It stays whatever the rules say, until you remove it.

In Morning because rules 1 and 3 found it. Rule 1 keeps it longest: They always stay.

A rule that keeps things is only trustworthy if the listener can ask it why.

9.6 The rule editor

  • Rules (“Rules for Morning”): each rule’s full sentence and “Finds N now”; Add Rule, Edit Rule, Remove Rule, Move Up, Move Down; and the Lineup’s own settings: New items go, Play-through budget in minutes, Skip live items when playing through. Nothing changes until OK.
  • Edit Rule, in labelled groups in the order its sentence reads: What it looks for (Look for); Where to look (Narrow by, Filter values, and a multiple-selection Values list where Space selects); Tests (Add Test, Edit Test, Remove Test, Match); Order and amount (Order, Count limit, Per group limit, Up to minutes in all); When they go (Keep, Days, Percent heard that counts as finished, Max kept, Rule switched on); Try it (Try It and a Matches list).
  • Changing what a rule looks for applies when focus leaves that control (or on OK), and asks before clearing its tests, because they belong to the old kind. Narrow by starts on “Choose what to narrow by” (look everywhere), and switching it keeps the values already chosen.
  • Clear the List, in Removed Items and Recently Left, asks first: it cannot be undone, and clearing Removed Items lets rules bring those items back.
  • Try It fills the read-only Matches list and moves focus there; the list’s label carries the count (“Matches, 7 items”), set before focus moves so the reader says it on arrival. A count said just before a focus move is cut off, and one in a label that changes silently is never heard, so the count lives where focus goes.
  • OK and Cancel carry no access keys (GATE-14); Close is bound through the dialog contract; every control has inline help, and the F1 purpose of every Lineups surface is written once (help_text.py) and taken by both apps’ catalogues.

9.7 Explaining it in the product

The whole model in four sentences, the F1 text for the Items list:

Rules add items, and each rule says when its items go: when they stop matching, when you have finished them, after some days, or never. Moving an item changes the order but not how long it stays. Keep holds an item whatever the rules say. Delete puts it in Removed Items, and no rule brings it back.

Plus the Radio tutorial, which builds Morning step by step, rather than a pop-up tip.

Saved YouTube YouTube videos you saved, for 14 days.

Finish These Episodes started and not finished, until finished.

The proposal’s “From My Channels” (new uploads from alerted channels) was dropped for the reason in 5.4, and replaced by Saved YouTube.

9.9 Many Lineups

As many as the listener likes, each with its own rules, order, settings, Removed Items and Recently Left. New Lineup (Ctrl+N), New from an Example (Ctrl+Alt+N), Duplicate (Ctrl+D; “Morning (copy)”, rules with new ids, Removed Items and Recently Left empty), Rename (F2), Delete (Shift+Delete, asks, naming what goes; undoable), and reorder with Alt+Shift and the arrows. Names are unique ignoring case. Lineups: Go to a Lineup… in the Command Palette asks for a Lineup by name and opens the window on it; the proposal’s one palette entry per Lineup was not built.

Export Rules writes a small JSON file (quill_lineup_rules: 1) of rules and settings, never items; Import Rules makes a new Lineup from one, whose rules then find the same things on this machine.

9.10 Start Here, per app

Any one Lineup can be the window an app opens in. Radio and Cast each keep their own pin, because each app starts on its own.

  • Set it with Start Here (Ctrl+Alt+H), a check item on the Lineup menu and the Lineup’s context menu. Choosing it on another Lineup moves the pin; choosing it again on the pinned one clears it. The Lineup’s row says “start lineup”.
  • At launch (radio_launch_tasks.py, deferred with wx.CallAfter like the rest of launch) the Lineups window opens in front of the main window, on the pinned Lineup, and its rules run as it opens. The main window is untouched and still shows its main view.
  • This reintroduces a second window at launch, which Radio PRD section 19 moved away from (“opening a second window at launch was the problem, not the solution”). It is acceptable only as an explicit opt-in: never a default, never a migration, undone the way it was done.
  • What can go wrong. First run wins (the pin applies from the next launch). Opening the app with files wins. A pinned Lineup that was deleted is said once (“Your start lineup no longer exists. Quill Radio opened as usual.”) and the pin is cleared.
  • Not built: the proposal’s Preferences route (“When Radio starts, open”) and “Also start playing it”. The menu item is the one route, and nothing plays on start.

10. Cast’s Play Queue lineups, folded in

Cast’s Play Queue had Save Lineup… and Apply Lineup… (quill.core.podcasts.queue_lineups), where a “lineup” was a manual playlist holding a snapshot of the queue. Those are now QUILL Lineups (quill/core/lineups/cast_queue.py, quill/ui/podcasts/lineups_queue.py):

  • Save Lineup saves the queue as a Lineup of hand-added episodes, in order. Saving over a Lineup of the same name replaces its rows and keeps its rules.
  • Apply Lineup puts a Lineup’s episodes at the front of the queue through the same apply_lineup it always used, so the verb and its sentences are unchanged.
  • Old snapshots (manual playlists whose id starts lineup-) are copied into Lineups once; the playlists stay where they were.

11. When rules run

Rules run while the Lineups window is open, and each time it opens:

  • when the window opens;
  • when a store the rules read changes, in either app (the watched files’ sizes and modification times, checked every two seconds);
  • every ten minutes, for the time-based Keep choices (refreshing.TIMED_REFRESH_SECONDS);
  • on Refresh Now (F5).

The proposal assumed the existing background refresh timers would run rules with the window closed. They do not: a closed window runs nothing. Reading Cast’s library on a timer for a window nobody has open would cost every listener for the benefit of none, and opening the window brings every Lineup up to date before it is read. The limit is stated in the user guide.

12. Fixed first: saved places survive a restart

A saved browse place is a RadioStation with an empty stream_url. RadioStation.from_dict returned None for an empty stream_url, and to_dict never wrote source, so every place saved to Favorites vanished on restart. Lineups reference places, so this was fixed first: from_dict accepts an empty stream URL when the station_uuid is a browse: node id, and to_dict writes source only when set, so a directory station’s record is byte-for-byte what it was. Regression: tests/unit/core/radio/test_saved_places_survive_restart.py.

15. What changed from the proposal

Proposal (rules.md, revision 4) As built
The name was a question. QUILL Lineups, decided.
The longest-lasting claim wins. An item stays while any claim holds it; strength only orders the reasons.
Three answers: present, missing, unavailable. Four: unlisted added for partly listed kinds, and only complete kinds can be missing.
Rows store no titles or URLs. Rows of partly listed kinds store the owner’s own play record, so an unlisted row still plays.
No memory of releases. Lineup.released, cleared when the rule stops matching, so a released item does not bounce back.
Rules read the YouTube subscriptions cache. No such cache is on disk: rules see saved videos and playlists and followed channels; the “From My Channels” starter became Saved YouTube.
A place plays. A place or channel opens Browse Stations at its top level and is skipped in a play-through.
The window’s keys to be confirmed. Keys as in 9.3; Duplicate is Ctrl+D; Removed Items Ctrl+Alt+Z and Recently Left Ctrl+Alt+L; opening is Ctrl+U in both apps.
A window of its own in Radio. A peer window in both apps, one module, each app’s Station and Window menus beside its own.
Cast’s queue lineups not mentioned. Save Lineup and Apply Lineup folded into Lineups (section 10).
One start pin, possibly shared; Preferences route; play on start. A pin per app, the menu item only, nothing plays on start.
Rules run on the existing background refresh timers. Rules run while the window is open and each time it opens.
Palette entry per Lineup. One “Lineups: Go to a Lineup…” chooser.
