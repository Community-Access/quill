Accessibility Testing for QUILL’s Core Tasks

This page is the short, repeatable accessibility test for QUILL: the core tasks a new user must be able to complete, the keyboard-only, screen reader, manual and documentation checks for each, and the record of every run. It is part of QUILL’s accessibility commitments.

It does not replace the detailed plans. Those go much deeper, and this page points to them:

  • qa-core-journeys.md: nine end-to-end editor journeys with sample files and exact expected speech.
  • screen-reader-test-plan.md: one case for every accessibility, focus and keyboard fix.
  • dialogs.md: every QUILL dialog, by keyboard.
  • The app sign-off sheets in docs/qa for QUILL Lite, Quill Radio, QUILL Cast and QUILL Transcribe.

What the build already checks

Do not spend a manual pass on what the machine checks; those rules fail the build on their own. They are listed under “Checks the build runs” in ACCESSIBILITY.md: the accessibility suite, the dialog keyboard contract, unique access keys, menu keys, F1 help, announcement and braille parity, and the documentation gates. They run on every pull request in .github/workflows/accessibility-ci.yml and .github/workflows/pr-ci.yml, and locally with:

pytest tests/accessibility -q
python -m quill.tools.platform_report

Automated checks find some barriers, never all. The checks below need a person.

The core tasks

These are the tasks every new user meets in their first session. Each check list below covers all of them.

  1. Install and first run: run the installer, start QUILL, and get through the setup wizard to an empty document.
  2. Open a document and move by heading: open a Markdown or Word file with File > Open (Ctrl+O), and move through its headings with Next Heading (Ctrl+Alt+H) and the screen reader’s own heading keys.
  3. Write, format and save: type a paragraph, make a line a heading, save with Ctrl+S, and save a copy in another format with File > Save As.
  4. Find and replace: find a word with Ctrl+F, then replace it with Ctrl+H.
  5. Change a setting: open Preferences (Ctrl+,), find a setting with “Find a setting”, change it, and close with OK.
  6. Get help and report a problem: press F1 on a control, then open Help > Get Help from Support… (Ctrl+Alt+F2) and review the report without sending it.

Documentation review, 2026-10-28

A review of the documentation’s Markdown sources, made while adopting the Open Source Accessibility Framework. It was an automated scan of all 393 Markdown files in the repository plus a reading of the representative set above; it was not a screen reader test of the rendered pages.

  • Structure: no skipped heading levels in the README, CONTRIBUTING.md, ACCESSIBILITY.md, the user guide or the current release notes. Five other documents have a second H1 or a skipped level; tracked in issue #1695. Several long design documents and PRDs combine parts under more than one H1; they are references for developers and are left as they are for now.
  • Alternatives: no Markdown image without alternative text. The eight places the scan flagged as HTML images without alt were prose about the <img> element, not images.
  • Links: no “click here”, “read more” or “here” link text found.
  • Captions: no embedded video in the Markdown documentation. Podcast episodes and transcripts are kept in step by GATE-SITE-LINKS.
  • Tables: every table is a Markdown table with a header row; rendered tables keep their table role (GATE-DOCA11Y).
  • Code blocks: all code is text. 133 fenced blocks have no language name, which does not affect how they are read, so they are left as they are.
