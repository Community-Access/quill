WordPress regression testing for QUILL and QUILL Lite

Payment checkout has an additional acceptance checklist. Do not assume the test site’s QAF plugin implements the payment contract; Verify Payment Setup must report version-1 readiness before testing checkout. No live payment acceptance is implied by the ordinary WordPress regression run.

A real WordPress site exists for testing every WordPress feature in QUILL and QUILL Lite, with known content, so a test always starts from the same place and its results can be compared from one build to the next.

  • Site: https://lp.csedesigns.com/wordpress/
  • Dashboard: https://lp.csedesigns.com/wordpress/wp-admin/
  • WordPress version: 7.1.4 when it was built (2026-11-04). It is new enough for the application-password handback to 127.0.0.1 (wordpress.md 4.2, tier 1).
  • Kind: self-hosted. WordPress.com is tested separately, once QUILL’s WordPress.com app is registered.

Accounts

There is one account per role, so the role behaviour can be tested (wordpress.md 9.2):

Username Role Can publish posts Can publish pages Can upload
quilladmin Administrator yes yes yes
quill-editor Editor yes yes yes
quill-author Author yes no yes
quill-contributor Contributor no no no
quill-subscriber Subscriber no no no

The passwords are never written into this repository. They live on the server, readable only by its owner:

  • the sign-in passwords and an application password for each of the first four accounts: ~/app/wordpress-test/test-accounts.txt;
  • the administrator’s sign-in password: ADMIN_PASSWORD in ~/app/wordpress-test/.env.

To read them: ssh lp.csedesigns.com cat app/wordpress-test/test-accounts.txt. Paste an application password into QUILL’s Connect a Site; never into a chat, an issue or a test file.

Where the test passwords live

No password is ever in this repository. There are two copies, both private.

On this computer, in Windows Credential Manager. Each password is a generic credential under the service QUILL WordPress test site (lp.csedesigns.com), with the user name <login> <kind>, where kind is sign-in or application. There are nine:

  • quilladmin sign-in and quilladmin application;
  • quill-editor sign-in and quill-editor application;
  • quill-author sign-in and quill-author application;
  • quill-contributor sign-in and quill-contributor application;
  • quill-subscriber sign-in (the subscriber has no application password).

The live run (docs/qa/wordpress-live-run.py) reads the application passwords from there. If one is missing it looks next in the file named by QUILL_LIVE_ACCOUNTS, then in QUILL_LIVE_APP_PASSWORD_<LOGIN> (for example QUILL_LIVE_APP_PASSWORD_QUILL_EDITOR), and says which login it could not find. It never prints a password.

On the server. ~/app/wordpress-test/test-accounts.txt (mode 600) holds the sign-in passwords of the four test accounts and the application passwords of the first four logins, one per line, as <login> sign-in password: ... and <login> application password: .... The administrator’s sign-in password is ADMIN_PASSWORD in ~/app/wordpress-test/.env.

Refreshing the local copy. Whenever the server’s copy changes, after setup.sh builds a fresh site or a reset makes new passwords, copy them across again:

python docs/qa/wordpress-test-site/store-passwords.py --admin-sign-in

It reads the server’s file over ssh, stores each entry in Credential Manager, and prints only the names it stored. Without --admin-sign-in it leaves the administrator’s sign-in password alone. reset.sh as it is written keeps the accounts and their passwords, so an ordinary reset needs no refresh.

Before each test run

Put the content back to its starting state:

ssh lp.csedesigns.com app/wordpress-test/reset.sh

It keeps the accounts, application passwords, settings and media, and reseeds every page, post and pattern. Then confirm the site is as expected:

ssh lp.csedesigns.com app/wordpress-test/verify.sh

verify.sh signs in as each role with its application password, and prints what each can do and what content exists. It never prints a password.

The tests

Run each test in QUILL and again in QUILL Lite, with a screen reader and the keyboard only. A result is a pass only when it is the same in both editors. For each test, note the build, the editor, the screen reader, and pass or fail.

Where the commands are (the same in both editors, from quill/core/wordpress/menu.py):

  • File > WordPress: New, Open, Open by Web Address, Open Local Draft, Save Draft to Site, Publish or Update, Schedule Publish, Open on Site, Copy Address, Properties, Previous Versions, Compare with Site, Move to Trash, Switch Site, Sites, Connect a Site.
  • Insert, Format > WordPress, View, Edit > WordPress: blocks, pictures, links, Block Settings, Image Size, Mark Language, and block navigation.
  • Tools > WordPress: the checks, the Media Library, Alt Text Review, Visual Review, Comments, Categories and Tags, Menus, Site Check, Site Settings, and the More Media and Manage submenus.

The rows about the page in front are dimmed outside a WordPress document. The commands have no keys yet: use Alt+F, W, or the Command Palette.

Connecting (4)

  1. Connect by hand. Choose File > WordPress > Connect a Site, then enter the address, quill-editor and its application password. Expect “Connected to QUILL WordPress Test Site as Editor”.
  2. Connect with the browser. Use Get Password with My Browser and approve in the browser. Expect the password to come back by itself (tier 1, on WordPress 7.1).
  3. Wrong password. Expect a plain sentence that names the site, with the dialog reopened and the fields kept.
  4. HTTP address. Use http://lp.csedesigns.com/wordpress. Expect a refusal that explains HTTPS.
  5. Many sites. Connect as quill-editor and again as quill-author, renaming one of them. In Sites, check the role on each row, Make Default, then Switch Site.
  6. Remove. Expect only the connection to be forgotten; the site is unchanged.

Writing and opening (5.1, 5.2)

  1. New Post, Markdown. Check that the slug follows the title, and that the categories and tags are listed. Ctrl+S saves locally; check that the post is not on the site.
  2. New Page, HTML.
  3. Open Page or Post. Open Posts, with Find set to “draft”, then “trash”. Each row reads title, status and last changed.
  4. Open Every Block as Markdown, change nothing, then Save Draft to Site. In the dashboard’s code editor, the content must be byte for byte the same, with only blank lines between blocks normalised. Do it again as HTML.
  5. Open by Web Address with https://lp.csedesigns.com/wordpress/welcome/ on the clipboard. Then try .../?p=<id> and a page address.
  6. Open Local Draft lists the drafts from test 7, with their site.

Saving and publishing (5.3, 5.4, 9.2)

  1. Save Draft to Site on test 7’s post. Check the site has a draft and the public page does not.
  2. Publish or Update. The confirmation names the title and the site; after publishing, the address is on the clipboard.
  3. Contributor. As quill-contributor, Publish becomes Submit for Review. The post arrives as Pending.
  4. Author and pages. As quill-author, publishing a page is refused in words.
  5. Private and Scheduled keep their status. Open A private post, change a word, and Update. Do the same with Scheduled for next month.
  6. Conflict.
    • Open Welcome in QUILL.
    • In the dashboard, edit and update it.
    • In QUILL, choose Update.
    • Expect nothing to be sent, and a sentence that names the change.
    • Then try each of Compare, Open the Site’s Copy, and Send Mine Anyway.
  7. Closing never publishes. Close an edited document; the site is unchanged.

Properties, versions, Trash (5.5, 5.6)

  1. Properties on Pinned news. Change the categories and tags, the excerpt, and Keep at the top of the blog. Send, and check them in the dashboard.
  2. Previous Versions on Welcome lists the local versions and the 3 site revisions. View one, then Restore one; nothing is published.
  3. Compare with Site after a local change.
  4. Move to Trash. The confirmation names the item and the site, and the item appears under Trash in Open.

Checks (7)

  1. Tools > WordPress > Check Before Publishing on “Things to check before publishing”. Expect each of these:

    • a heading 1 in the body;
    • a skipped heading level;
    • “click here”;
    • a link whose text is its address;
    • a new tab not said;
    • a picture with no alternative text;
    • colour alone;
    • a table with no header row.

    Go to It reaches each one.

Pictures (6)

  1. Tools > WordPress > Media Library.
    • Rows read title, kind, size, alternative text and date.
    • Find: “banner”.
    • Edit Alternative Text on wide-banner, and check it in the dashboard.
  2. Insert > Picture from the Media Library into a post. Check that the alternative text is kept per placement.
  3. Insert > Picture from This Computer.
    • Inserted at once, and marked as not uploaded yet.
    • Uploaded on Save Draft to Site, with the address swapped in.
  4. Remove from Library on a copy you uploaded in test 27. Check a backup is saved under Documents, Removed from WordPress.

Comments, categories and tags (9.8, 9.13)

  1. Tools > WordPress > Comments. Approve the waiting comment, reply to it, and mark one as spam.
  2. Tools > WordPress > Categories and Tags.
    • Add a tag.
    • Rename Unused Tag.
    • Merge Empty Category into News. Expect the post count in the sentence, and the empty category deleted.
    • Delete a tag.

Listen and watch (6.1a)

setup.sh seeds a three-second tone (quill-test-tone, WAV), a five-second silent test-pattern video (quill-test-clip, MP4), its English captions (quill-test-clip.en.vtt), and a Listen and Watch page with one audio block and one video block.

  1. Play on the tone in the Media Library.
    • A small player opens and the tone plays at once.
    • The keys are the ones in QUILL’s player: Play and Pause, Stop, Rewind, Forward, Where am I, Speed, Volume and Mute. There are no chapter buttons.
    • Go to Position 0:00:02 moves there.
    • Close, and the tone stops. Try again with Escape and with Alt+F4.
  2. Play on the clip. The picture shows with NVDA and with JAWS, and nothing else takes focus. Press Captions at about one second: expect “This is the QUILL test clip.” Press it after five seconds: expect “No caption at” and the time.
  3. Nothing is saved. After tests 31 and 32, check that the Downloads and Documents folders have no new copy of either file.
  4. Play on a picture (photo-volunteers): expect “That file is not audio or video.”
  5. Open in Browser from the player: playback here pauses and the file opens in the browser. Open in Quill Media Player starts Quill Media Player where it is installed, and says so where it is not.
  6. Play Media Here in the Listen and Watch page, with the caret on the audio block and then on the video block. On the paragraph, expect “There is no audio or video block at the caret.”
  7. QUILL Lite. Repeat 31, 32 and 36 in QUILL Lite.

The site’s own kinds (5.2)

  1. Events. File > WordPress > Open Page or Post lists Posts, Pages and Events. Choose Events: “Open Day” is there. Open it, change a word, and Save Draft to Site, then Publish or Update. Check the site shows the change, then Move to Trash and restore it from the Open list.
  2. A role that cannot list kinds. As quill-contributor, Open still offers Posts and Pages, and says nothing about the kinds it could not read.

Every route (9.16)

Sign in as quill-admin unless a test says otherwise. Each command reads the site’s list of routes first; where a test says “a site without it”, use a WordPress older than the route, or a security plugin that hides it.

  1. Hear Where a Link Goes. In a post, put the caret on a link to one of the site’s pages and choose Edit > WordPress > Hear Where a Link Goes. It says the page’s title and description. With the caret on no link, type an address with a typo: it says the page could not be reached and offers nothing to insert.
  2. Fix Link Text. Add a “click here” link to the About page. Edit > WordPress > Fix Link Text lists it with “About”; Use the Page’s Title makes the link say “About”.
  3. Dead links. Add a link to /no-such-page/, publish, and run Tools > WordPress > Check This Page. The summary says one link goes nowhere, and Dead Links names it.
  4. Insert Icon (WordPress 7.0 or later). Insert > WordPress Icon lists the site’s icons. Insert one with a label and one as decorative; publish and check with NVDA that the first is read by its label and the second is skipped. An empty label inserts nothing.
  5. Upload a Large File. Tools > WordPress > More Media > Upload a Large File with a video over 16 MB. QUILL says its size and that it can take a while, then that it is in the Media Library, and the library item plays. A file bigger than the host accepts is refused in the site’s own words. WordPress has no upload in pieces, so nothing goes to the sideload route.
  6. Regenerate Sizes. After Edit a Picture on the Site, Tools > WordPress > More Media > Regenerate Sizes on that picture. The thumbnail in the Media Library shows the edit.
  7. Previous Looks (block theme). Change a colour in Site Styles, then Tools > WordPress > Manage > Previous Looks. The earlier look is listed with its date and palette; Go Back to This Look restores it, and the look you left is now in the list.
  8. Menu History. Open Tools > WordPress > Menus, remove an item, then Tools > WordPress > Menu History: Bring Back Removed Items puts it back at the end. For a Navigation block, Restore This Version restores it whole.
  9. Space Used. Tools > WordPress > Manage > Space Used says the total and lists uploads, themes, plugins, WordPress and the database in words. As quill-editor it says the role cannot see it.
  10. Download a Copy of the Site’s Design (block theme). Tools > WordPress

    Manage > Download a Copy of the Site’s Design saves a zip that opens and holds the theme. On a classic theme it says only a block theme can.

  11. Send This Document to WordPress. Open a Markdown file with a heading and a picture beside it, and choose File > WordPress > Send, Copy and Download > Send This Document to WordPress. The draft’s title is the heading, the picture is in the Media Library, and the draft opens.
  12. Publish to Another Site and Duplicate. With two sites connected, copy a post with a category the other site lacks: QUILL asks before creating it, and the copy is a draft there with its pictures. Duplicate a page on the same site: the new draft is titled “(copy)” and opens.
  13. Download My Writing. Save the site to an empty folder; check index.md, one file per page and post, and the pictures folder. Run it again: it says everything is already up to date.
  14. Send a Folder as Drafts. A folder of three Markdown files, one with a “click here” link. The confirmation gives the count and says one has things to look at; three drafts arrive.
  15. Coming Up and What Changed. Schedule a post on each site. Tools > WordPress > Your Sites > Coming Up lists both by date. Leave a comment as quill-contributor, then What Changed on My Sites lists it; run it again and it says nothing is new.
  16. QUILL Lite. Repeat 40, 43, 50 and 54 in QUILL Lite.

The tests build one form, “Ask us anything”, as the guided Forms lessons do.

  1. New Form. File > New Form, title “Ask us anything”, template Contact form, Next, and save it. Expect “Saved Ask us anything.qaf, a contact form with 3 questions.” and the form open. View > Form Outline starts “Page 1, 3 questions”.
  2. Form Field. With the caret on Your message, Insert > Form Field, search “choose”, pick Choose one, label “Best way to reply”, choices Email and Phone. Expect “Inserted Best way to reply, choose one.” Then add a Phone number question labelled “Phone number”: “Inserted Phone number, phone number.”
  3. Form Rules. Format > Form Rules > Add Rule: when Best way to reply is phone, then Show, Phone number. Expect “Show Phone number when Best way to reply is Phone.” and an @when #reply is "phone" line under the question. Typing Phone or PHONE gives the same rule: the answer is matched to the choice in any capitals.
  4. Check This Form. Expect “Phone number has no autofill hint, so the browser cannot fill it in. The hint is tel.” Go to It lands on the question. Add @autocomplete "tel" under it; Check Again lists only the “On the site today” lines.
  5. Fill It In Yourself. Tab through: each label is read, with “required” where it is. Choosing Phone says “Phone number appears.”; choosing Email says “Phone number is hidden.” Submit shows What Would Be Sent, starting “Nothing was sent.” Escape twice returns to the document.
  6. Save As Large Print and Braille-Ready Text. Expect “Saved Ask us anything large print.docx, a large-print Word document, 18 point and up, with 5 questions, lines to write on and boxes to check.” and “Saved Ask us anything.txt, braille-ready text with 5 questions, one a block.” Open both; with the braille pack installed, also save the UEB contracted .brf. Repeat in Safe Mode: all four Save As commands still work.
  7. Not a form. In an ordinary text document, run Check This Form from the Command Palette. Expect “Check This Form works in a form document, a .qaf file. Start one with New Form in the File menu, or open one.”
  8. Publish Form. With QUILL Accessible Forms not installed, expect “Publish Form needs QUILL Accessible Forms on QUILL WordPress Test Site, and the site does not offer it.” Once it is installed: Publish as Live, then Publish. Expect “Published Ask us anything on QUILL WordPress Test Site, form” a number, “live.” Publish again: the question says Update. While the site lists both qaf/v1 and the older baf/v1, every request goes to qaf/v1 (the alias answers reads only).
  9. Changed on the site. Change the form’s title in QUILL Accessible Forms on the site, then Publish Form. QUILL asks before publishing over it, and keeps the site’s copy as a previous version.
  10. Insert Form Into Page and Test on Site. Open the Contact page, put the caret after its first paragraph, Insert Form Into Page, choose the form, and Publish or Update. Test on Site in the form opens that page in the browser, where the form can be filled in with NVDA.
  11. Responses. Send two responses from the site. Responses, with the form open, goes straight to “Responses to Ask us anything”, newest first. Read, View, Find, Export to CSV, Open as Table and Export to Word each do what they say. Mark one, then Delete: it goes to the Trash in BITS Accessible Forms.
  12. New response count. Restart, then run any site command for Forms. Expect, once a session, “QUILL WordPress Test Site:” and the number of new responses to Ask us anything. Say New Count turns it off.
  13. QUILL Lite, and Safe Mode. Repeat 56 to 61, 63 and 66 in QUILL Lite.
  14. Form files. In Explorer, Open with on Ask us anything.qaf lists QUILL and QUILL Lite. File > Open in each editor shows it under All supported files and under Forms, and the Forms commands are available once it is open. Rename a copy to .bfl and open it: it is still a form, and nothing is said about the older extension. Then in Safe Mode, Publish Form and Responses each say they are off in Safe Mode, while writing, checking, Fill It In Yourself and the four Save As commands still work.

Looking after the site

  • Where it runs: on lp.csedesigns.com, in two Docker containers, wordpress-test (WordPress 7.x, PHP 8.3, Apache) and wordpress-test-db (MariaDB 11). Both are defined in ~/app/wordpress-test/docker-compose.yml.
  • How it is reached: the web stack’s Caddy serves it at /wordpress/, through the @wordpress_test route in ~/app/web/caddy/Caddyfile. That route sits above the redirect to letitglow.app, like the other lp.csedesigns.com routes. The Caddyfile was backed up before the change, as Caddyfile.bak-2026-11-04-wordpress.
  • Secrets: in .env and test-accounts.txt, both chmod 600. Search engines are told not to index the site.
  • Reseed: reset.sh.
  • Check: verify.sh.
  • Logs: docker logs wordpress-test.
  • Update WordPress: docker compose pull && docker compose up -d, in ~/app/wordpress-test.
  • Change the database password: change it in MariaDB, update .env, then docker compose up -d --force-recreate wordpress. The container reads the password when it starts.
  • Remove it all:
    1. Run docker compose down -v in ~/app/wordpress-test.
    2. Delete the @wordpress_test route from the Caddyfile.
    3. Reload Caddy with docker exec web-caddy-1 caddy reload --config /etc/caddy/Caddyfile --adapter caddyfile.
