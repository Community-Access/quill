Part A: the product

A1. In one paragraph

The GitHub Workbench is a window in QUILL and QUILL Lite where everything you can do on GitHub can be done from the keyboard, heard clearly, read in braille, and understood without already knowing GitHub. It has a tree for where you are, a list for what is there, and details for the one you picked. Alt+Enter opens the Properties of anything. Every fact is readable, every editable thing is editable, every list filters on every attribute, every permission is known before it bites and manageable where GitHub lets it be managed, and F1 answers everywhere. It is the GitHub that a blind maintainer, a new contributor and an organization owner can all run all day.

A2. The short version

  • One window: the GitHub Workbench. It is a top-level window with its own menu bar and its own taskbar button. It is not a modal dialog, so you can Alt+Tab between it and QUILL or QUILL Lite. Open a file from it and the file opens in the editor; Alt+Tab takes you back to where you were in GitHub.
  • Three panes, the Outlook and File Explorer pattern: a Navigator tree on the left (where you are), a list (what is there), and a details pane (about the selected item). F6 moves between them.
  • Nothing is removed. Every view in GitHub Items and Explore GitHub, every button, and every context-menu row gets a named home: a tree node, a menu bar row, or a context-menu row. Appendix A lists every one.
  • The 30 buttons and choices above and below the list become a menu bar. The window shows a tree, a filter box, a list, details and a status bar, and nothing else.
  • Context menus only offer what applies to the selected item. The default action comes first, Properties comes last.
  • Alt+Enter is Properties, on everything: repositories, branches, issues, pull requests, projects, milestones, labels, releases, runs, people, teams, organizations, gists, alerts, environments, rulesets, templates (sections 15 and 16, Appendix C).
  • Edit everything GitHub lets you edit, one item or a hundred at once, checked on GitHub afterwards and undoable where GitHub allows (section 16).
  • Star, watch, follow, subscribe, react, block, sponsor, pin: every relationship you can have with a thing, on its You page (section 16.7).
  • Filter on every attribute, from the filter box, a Filter Builder, the Filter menu, or "show only items like this one" on any cell (section 17).
  • Permissions, rigidly: known before offering, explained when missing, added all at once, managed on every object that has them, previewed before anything risky, recorded afterwards (section 18, Appendix D).
  • Build and fill every kind of template, and issue forms filled natively instead of sending you to GitHub (section 21).
  • And further: Copilot agents, GitHub Models, a workflow builder, merge conflicts in the editor, an API Console as the escape hatch, threads read as documents, Watches that tell you when something happens, plain-language batches, import and export, a practice repository, View As Role (section 22).
  • Everything is measured: a coverage gate compares the Workbench with GitHub's own API description (section 19, Appendices E and F).
  • Keys you will enjoy: Windows and Outlook habits first, then families that teach themselves: Ctrl+number to go, Alt+number to hear, Delete to remove safely. Changing anything is one key, Alt+Enter, and typing always moves through the list (Part C).
  • Help that teaches: F1 on every node, row, field and menu item; Shift+F1 for "what can I do here, and with which keys"; a GitHub glossary; a search of all help that can run what it finds; tutorials and a practice repository (Part D).
  • GitHub preferences live in the Workbench, in its own file, shared by both editors; the main Options dialog gains nothing (section 4.1).

A3. The problem

Section 1 records what a new user meets today, verified in the code: two modal windows with overlapping jobs, about 28 controls before the list, a context menu of 15 rows across three scopes, Codespaces offered on every item, F1 on 6 controls, and a GitHub menu with seven doors that lead to two windows. Beyond that:

  • Most of GitHub cannot be changed here. Labels can be added in a batch but not removed; there is no general way to set an item's assignees or milestone, or edit its title; access, rules, environments and Actions settings are not reachable.
  • Issue forms are "link-only": the most common kind of template sends people to the web, which is exactly what they came here to avoid.
  • Permissions surprise people. A missing scope or role shows up as an error at the moment of use, one feature at a time, and GitHub sometimes ignores a write and still answers success.
  • github.com is hard work with a screen reader. Project boards, the rulesets editor, the conflict editor, settings pages and the access pages are among its least accessible screens, and they are where the power is.

A4. Goals

  1. Parity with GitHub: anything GitHub's API lets a person do, the Workbench lets them do, measured by GATE-GITHUB-COVER (section 19).
  2. Better than parity where it matters: the things github.com makes hard by ear (boards, rules, access, conflicts, long threads) are easier here.
  3. Findable without knowing GitHub: where, what, about; one home per feature; greyed with a reason rather than hidden.
  4. Safe at any scale: every change previewed, verified, recorded and, where GitHub allows, undoable; nobody locks themselves out.
  5. Help everywhere, and good: F1 on 100 percent of nodes, rows, fields and commands, in a human voice.
  6. Fast: it never makes you wait on a keystroke, and it is careful with GitHub's rate limits.
  7. One Workbench for the family: QUILL and QUILL Lite open the same window; QUILL Lite is never ahead.

A5. Not goals

  • Replacing Git. Local Git stays in the editor (section 6).
  • Hosting anything. The Workbench talks only to GitHub (and, by consent, to githubstatus.com).
  • GitHub Enterprise Server administration and enterprise accounts (Appendix F marks them out of scope). GitHub Enterprise Cloud organizations are in scope.
  • Classic Projects, which GitHub has retired.
  • Visual charts as the only form of anything. Every insight is a table or a sentence first.

A7. Journeys: what a good morning sounds like

Each journey is also a usability task in section 12 and a scenario test in Part F.

  1. Morning triage. Jeff presses the Workbench door, lands on Inbox (Ctrl+1 if he was elsewhere), and hears "Inbox (14)". Down Arrow reads each row in full. Delete marks one done, Ctrl+Q marks one read, Enter opens the next in details, and Alt+Enter on one opens its Properties, where the Organize page takes a label and a milestone. Fourteen rows later: "Inbox is empty. Nice work." with the done sound.
  2. A run failed. A Watch says "The build failed on main: test_paths." Ctrl+Shift+W (What Failed) reads the failing step and its first error. Ctrl+Enter opens the failing file in the editor at the line. He fixes it, commits from the editor, Alt+Tabs back, Ctrl+Shift+F5 re-runs failed jobs. The Watch says "Build passed" twenty minutes later while he is writing.
  3. A first issue. A new contributor opens the Workbench for the first time, meets Start Here, presses Ctrl+N on Issues, chooses "Accessibility bug report", and fills a form whose every field is a labelled control with its help on F1. Submit says "Filed #57. Thank you." They never visit github.com.
  4. Giving a volunteer access. An organization owner opens the repository's Properties (Alt+Enter), goes to Access (Ctrl+Tab), presses Insert, types a login, chooses Triage, and hears the preview: "Invite kellylford with Triage on Community-Access/quill. They will be able to label, close and assign issues; not push code." Before granting it, View As Role shows the Workbench as Triage sees it.
  5. Planning a release. A project lead selects 23 issues with a filter (no:milestone label:accepted), presses Alt+Enter for one sheet for all 23, goes to Organize, picks New Milestone... in the Milestone list, types 2027.1 and a due date, and hears "Created milestone 2027.1. 23 issues are in it." The project's board, read as Status groups in the tree, shows them all in "Planned".
  6. Reviewing a pull request. Enter on the pull request opens review. The reviewer reads one commit at a time, marks files viewed, leaves two line comments and a suggestion, then Read as Document exports the whole thread to braille-friendly text for a closer read before approving.
  7. Rules that read like sentences. An admin opens the main branch's ruleset and reads the Summary page: "Changes to main need a pull request with two approvals, including a code owner; build and test must pass; force pushes are blocked; maintainers may bypass." One check box adds "require signed commits"; the preview says what changes for whom.
  8. Anything else. Someone needs a GitHub feature the Workbench has not built yet. Tools > GitHub API Console finds it by name from GitHub's own description, shows the scope it needs, runs it with a preview, and saves it as a menu row with a key for next time.

A8. Delight, on purpose

Delight here is speed, certainty and a little warmth, never noise:

  • One sentence per outcome, specific and short: "Starred owner/name. 1,205 stars." "#42: added bug, removed docs." Never "Operation completed successfully."
  • Sounds for moments, from the family's sound scheme and the shared action-feedback channels (sound, speech, both, silent): done, merged, passed, failed, new notification, Watch fired, inbox empty. Each can be turned off; a failure is always also spoken.
  • Counts where you look, never announced: "Pull Requests (12 open)".
  • Celebrations that fit: inbox empty, milestone complete ("2027.1 is done: 42 of 42 closed"), first pull request merged in a repository, a run green after a red streak. Each is one sentence, once.
  • No dead ends: every greyed row says why and offers the fix; every empty list says what would fill it; every error says what to do next.
  • It remembers you: where you were, what was expanded, your columns, your filters, per account.
  • It never makes you hunt for a key: every menu row shows its key, Shift+F1 lists the keys for what you are on, and the Key Describer names any key you press.

Part B: the design (sections 1 to 22)

1. What a new user meets today (verified in the code)

  1. Two windows with overlapping jobs.

    • GitHub Items has 7 views: Issues & PRs, Branches, Commits, Tags, Releases, Workflows, Workflow Runs.
    • Explore GitHub has 35 views in one choice list, mixing four kinds of thing: searches, your own work, people, and repository administration (security alerts, secret names, Actions caches).
    • Enter on an issue in Explore closes Explore and opens it in Items. A new user has to learn which window holds what.

  2. Both are modal, and so is the PR review reader opened from them. While any of them is open, the editor cannot be reached. You cannot read an issue and the code it is about side by side.

  3. There are about 28 controls before you reach the list in GitHub Items:

    • Repository row: the repository box and Load, Pinned, Favorites, Explore, Projects, View Upstream, Files, Milestones.
    • Search row: the search box and Search, Open Link, and a quick filter.
    • Filter row: the View, Show, State, Sort and List mode choices, then Columns, Back and Forward.

    Below the list there are 12 more buttons: Refresh, View More, Open in Browser, Go To #, Diff, Review, Summarize, Compare, Batch, Actions, and Close. Tabbing through all of that is the first thing anyone does.

  4. The context menu on an issue has about 15 rows plus a submenu, mixing three scopes:

    • About the item: React, Timeline, Summarize, Worktree.
    • About the repository: Browse Repository Files, Milestones, Open in GitHub Codespaces.
    • About the app: GitHub API Rate Limit.

    Open in GitHub Codespaces is the first row on every item, including issues, releases, tags and runs. Explore's context menu has about 25 rows across its row types.

  5. Seven doors in the editor's GitHub menu lead into the two windows.

    • Three of them answer "what needs me": Inbox, My Work and Notifications.
    • "Issues and Pull Requests..." and "Repository Items..." open the same dialog on different views.

  6. F1 is thin.

    • GitHub Items sets authored help on 5 controls; Explore sets it on 1.
    • The nine per-app help gates (GATE--HELP) do not cover quill/ui/github_*. Twenty-seven modules there build windows.

  7. A correction to what I said in chat: GitHub Items does have a Show: Both / Issues / PRs choice, as GHManage does. It stays, and becomes easier to find (section 3.3).

2. Principles

  1. Where, what, about. The tree says where you are, the list says what is there, and details say what this one is. Every screen follows this pattern.

  2. Every feature has one home, chosen by what kind of thing it is.

    • Something you look at is a tree node.
    • Something you do is a menu bar row.
    • Something you do to the selected item is also on its context menu.

    The same command can sit in both menus: one command id, one handler, one key. That is two routes to one command, not a second implementation.

  3. Default action first, and Enter does it. Open for an issue, Review for a PR, Jobs and Logs for a run, Assets for a release, Commits for a branch.

  4. Scope follows the selection. Item commands go on the item, repository commands on the repository node, account commands on the Account menu, and app diagnostics under Help or the status bar.

  5. Rare means one level down, never removed, never behind a setting. Admin and occasional features live in a named folder or a More submenu.

  6. Explain instead of failing. A node that needs sign-in, push access or an opt-in is always shown. Its details pane says what it needs and offers the fix, such as Sign In... or Turn On....

  7. GATE-13 still holds. The screen reader says titles, focus and selection; the Workbench only says results and changes the reader cannot see.

  8. QUILL Lite is never ahead. The window lives in quill/ui, and both editors open the same window.

3. The window

3.1 Shape and behaviour

  • A top-level wx.Frame, titled "GitHub Workbench - owner/name". It has its own menu bar and status bar, and appears in the taskbar and Alt+Tab. Because it is a frame, its Close button must be bound through dialog_contract.bind_close_button (the close-button contract).
  • One Workbench per app. Opening it again brings the same window forward, at the place the door asked for. In QUILL Lite, all document windows share one Workbench (decision 1).
  • Back to the editor. Alt+Tab works, and Window > Switch to Editor raises the editor that opened the Workbench. These open in the editor and raise it: Open in Editor on a file, Open File Reference, and Start in Local Worktree.
  • Dialogs launched from the Workbench stay dialogs (PR review, diff, timeline, jobs and logs, release editing, and the rest). They are parented to the Workbench, so they block only the Workbench and never the editor.
  • It remembers its size, pane sizes, last node and expanded nodes, per account, in the Workbench's own files, never in the main Settings (section 4.1).
  • Closing: Alt+F4 and File > Close Workbench close it. Escape clears the filter box, then goes Back, and never closes the window (decision 5).

4.1 Workbench Options: GitHub preferences live here

GitHub preferences belong to the Workbench, so the main Options dialog in QUILL and QUILL Lite stays about writing.

  • Where: Tools > Workbench Options... in the Workbench's menu bar. It is a tabbed dialog parented to the Workbench, so it never blocks the editor. The editor's own Options dialog gets no GitHub page and no GitHub controls (decision 6).
  • Storage: its own file, github_workbench.json in the app data folder.
    • Loaded and saved by a wx-free quill/core/github/workbench_prefs.py, written atomically through write_json_atomic and schema-validated, like every other store.
    • Next to it, the existing per-account resume file (github_items_context.json, from navigation_state.py) keeps holding "where I was" state: last view, filter, selection and history. Preferences are things a person chooses; resume state is things the window remembers.
  • One store for both editors. QUILL and QUILL Lite read and write the same file through the same module, so the two cannot drift. "QUILL Lite is never ahead" holds by construction, and the settings vocabulary audit has nothing to pair because neither editor's Settings holds these fields.
  • Pages:

15. Properties: Alt+Enter on anything

15.1 The rule

Every object the Workbench can show has a Properties sheet, and Alt+Enter opens it from anywhere the object appears: a list row, a tree node, a search result, a notification (the sheet of the thing the notification is about), a line in the details pane that names an object (a label, a milestone, a person, a linked pull request), and inside the PR review reader (the pull request, or the comment or thread at the cursor).

Three routes, one command (github.workbench.properties):

  • Alt+Enter, the File Explorer and Outlook habit for Properties.
  • Item > Properties..., the last row of the Item menu.
  • Properties..., the last row of every context menu (section 5, rule 6).

On a tree node, the sheet is the node's own object: the repository on owner/name, the organization on an organization, the person on a person, the milestone on a milestone, the project on a project. On a folder node that is not an object (Needs My Attention, Search), Alt+Enter opens that view's options: its columns, sort, default filter and refresh interval.

In the editor, the GitHub menu gains Properties of This Repository..., which opens the Workbench on the repository's sheet. It has no default chord in the editor (rule 7: editor chords are for the editor); the Workbench owns Alt+Enter.

15.2 The shape of a sheet

  • A dialog parented to the Workbench, so it never blocks the editor. Its title is the object's kind and name: "Issue #42 Properties - owner/name". The reader says the title; the Workbench says nothing on opening (GATE-13).
  • Pages on a wx.Notebook. Ctrl+Tab and Ctrl+Shift+Tab move between pages, Ctrl+Page Down and Ctrl+Page Up too. The first page is always General. The pages per object type are in Appendix C.
  • Every fact is a focusable control with a label. Read-only facts are read-only text boxes, never bare static text, so Tab reaches them and the reader reads them, and a braille user can pan through them. Dates are written out ("9 November 2026, 14:05, 3 hours ago"), never relative only.
  • Editable when you may, explained when you may not. A field you have permission to change is a normal control. A field you may not change is read-only, and its F1 help and the line under it say why and what would change that: "Read only: changing labels needs triage access to owner/name. You have read access. An owner or admin can give it to you." (section 18.2).
  • Every list on a sheet is a real list. Labels, assignees, reviewers, collaborators, teams, events, branches: a wx.ListCtrl or a check list, each row reading in full, for example "bug, checked" (GHManage 1.1.0's form), with type-ahead, Space to toggle, and Add..., Remove and Change... buttons where the list can change.
  • What you need does not have to exist yet. Every picker ends with a New... row or button that creates the thing and uses it at once: New Label..., New Milestone..., New Project..., New Issue Type..., New Branch..., New Environment..., New Team..., New Discussion Category... (GHManage 1.1.0 does this for milestones, labels and projects).
  • OK, Cancel, Apply. OK saves and closes, Cancel discards, Apply saves and stays. Enter is OK and Escape is Cancel, so neither carries an access key (GATE-14). Only changed fields are sent.
  • Copy. Every sheet has Copy as Text (all pages as plain text, for a note or an email) and Copy Link. Ctrl+C in a read-only field copies the field.
  • Open on GitHub on every sheet, for the rare page GitHub shows that the API does not.
  • Several objects at once. Alt+Enter on a multiple selection opens one sheet for all of them: "Properties of 5 issues". A field the same on all shows its value; a field that differs says "Mixed" and leaves it alone unless you change it. Check lists become three-state: "bug, on 3 of 5". Saving changes only the fields you touched, on every item, and the result says per item what happened (section 16.4).
  • Fresh, and honest about it. The sheet loads current values when it opens and shows "Loaded at 14:05" in its status line. F5 on a sheet reloads.

15.3 Saving safely

  • Someone else's change is kept. Before saving, the sheet compares what it loaded with what is on GitHub now (ETag or updated_at). A field someone else changed meanwhile is listed: "Changed on GitHub since you opened this: milestone is now 2027.2." For each, Keep Theirs or Use Mine. Fields nobody else touched save without asking.
  • Nothing is claimed that did not happen. After saving, the Workbench reads the object again and compares. GitHub ignores some writes from people without access and still answers success (GHManage 1.1.0 found this for milestones, labels and assignees), so the only success message is one the re-read proves. A field that did not take says so, by name.
  • One sentence says what changed: "#42: added bug, removed docs; milestone 2027.1; assigned to kellylford." Spoken and brailled through the announcement service, since the reader cannot see a change on GitHub.
  • Undo. Every save is a step in Edit > Undo GitHub Change (Ctrl+Z in the list, when focus is not in a text box), section 16.5.

16. Edit everything GitHub lets you edit

16.1 The rule

If GitHub's API can change it, the Workbench can change it, from the object's Properties sheet, and from a menu row where it is common. Appendix C lists, per object type, every editable field and the command that edits it. The coverage gate (section 19) keeps that list complete as GitHub grows.

This replaces a rule in today's code. items_provider.update_items describes batch work as "the one deliberate exception to the viewer's read-only rule", limited to close, reopen and adding labels, with "no deletions". That rule is lifted: removal and replacement are as available as adding, with the safety of section 18.4 instead of a missing feature.

16.2 What can be changed on an issue or pull request

The full list is in Appendix C. The common ones, all on the General, Organize and Conversation pages:

  • Title and description (body), in a multi-line box with the same Markdown help as New Issue; Ctrl+Enter saves (GHManage's form).
  • State: open, closed as completed, closed as not planned, closed as a duplicate of #n; reopen. For a pull request: open, closed, draft, ready for review.
  • Labels, assignees, milestone, issue type, projects, each with its picker and New... row.
  • Project fields for every project the item is in: status, iteration, dates, numbers, text, single-select, each by its own type of control (section 16.6).
  • Relationships: parent issue, sub-issues and their order, blocked by, blocking, duplicates, linked pull requests and branches ("Development").
  • Pull request only: base branch, reviewers (people and teams) and their removal, Copilot review, auto-merge and its method, merge queue, maintainers may edit, update branch.
  • Conversation: lock with a reason, unlock, pin and unpin, transfer to another repository, subscribe and unsubscribe, hide (minimize) a comment with a reason, unhide, edit and delete your comments, reactions.

16.3 One key for every change: Alt+Enter

Jeff, 2026-11-09: "I want Alt+Enter, and typing should just move through the list. I don't need fancy keys to modify specific properties, just bring up the property sheet."

  • There are no per-property keys. Every change to an object starts the same way: Alt+Enter, then the page. The sheet opens on General with focus on its first field, and Ctrl+Tab or Ctrl+1 to Ctrl+9 reach any page.
  • Typing always moves through the list and the tree, to the first row whose text starts with what you typed, as in File Explorer. No letter is ever a command there, so a typed name can never change anything.
  • The menus still name every change (Item > Labels..., Milestone... and the rest), for people who browse menus; those rows open the sheet at the right page and carry no key of their own.
  • The sheet remembers the last page you used for each kind of object, so if you set milestones all morning, Alt+Enter on the next issue opens on Organize with focus in the Milestone list.

16.4 Many items at once

  • Select, then change. Shift and Ctrl selection in the list (and Select All), then Alt+Enter for the combined sheet.
  • Every field works in batch that GitHub lets you set per item: labels added and removed, assignees, milestone, type, projects and project fields, state with reason, lock, transfer, reviewers.
  • A preview before more than one item changes. "Change 14 issues: add bug, remove triage, set milestone 2027.1. 3 of them already have bug." Enter goes ahead.
  • A result per item. A results list (not a message box) shows each item with Done, Skipped (already so), or Failed and why. Copy Results copies it. Failed ones can be retried with one button.
  • Paced for the rate limit. Batches respect GitHub's secondary rate limits, and the status bar shows progress ("Changing 6 of 14"), which is never announced except at the end.

16.5 Undo GitHub Change

  • Every save records what it changed, before and after, in the session's GitHub change history (Account > Change History, section 18.5).
  • Edit > Undo GitHub Change reverses the last one where GitHub allows it: labels, assignees, milestone, type, project fields, title, body, state, lock, pin, reviewers, branch protection and ruleset settings, repository settings, collaborator roles.
  • A change GitHub cannot reverse (a deleted branch, a deleted release asset, a transferred issue in a repository you cannot reach) is marked "cannot be undone" in its confirmation before it happens, never after.

16.6 Projects, edited richly

Projects (GitHub's Projects, version 2) are where most of the "everything" lives, so they get their own treatment:

  • A project node in the tree for each project you can see: yours, each organization's, and those linked to the current repository.
  • Views as children: each saved view of the project (table, board, roadmap) is a child node, and the list shows its items with its columns, its filter and its sort. A board view is read as a list grouped by its column field, one group node per column, so "Status: In Progress (5)" is a place you can go.
  • Every field type has its own control: single select (a list), iteration (a list with dates: "Iteration 4, 4 to 17 November"), date (a date box), number, text, and the built-in fields (assignees, labels, milestone, repository, reviewers, linked pull requests). Moving an item to another column is changing its single-select field, from the sheet, a or Item > Move To.
  • Project properties: title, short description, README, visibility (public or private), closed or open, template, linked repositories, and the project's access list (section 18.3).
  • Fields and views are editable: add, rename, reorder and delete fields; add, rename and delete single-select options and iterations; create, rename, copy and delete views; set a view's filter, sort, group and visible fields.
  • Items: add an issue or pull request by number or address, add a draft item, convert a draft to an issue, archive and restore, delete, reorder.
  • Workflows and status updates: turn the project's built-in workflows on and off; post, edit and read status updates (on track, at risk, off track, with dates).

16.7 You and the object: star, watch, follow and the rest

Every sheet whose object you can have a relationship with has a You page, right after General, holding every such relationship GitHub offers. Each is also a context-menu row and a menu row, and each answers in one sentence ("Starred owner/name. 1,204 stars.").

  • Repositories: Star and Unstar; add to or remove from your star lists (create, rename and delete lists too); Watch level: all activity, participating and mentions, ignore, or custom (issues, pull requests, releases, discussions, security alerts, each a check box); Fork; Pin to your profile and unpin; Pin in the Workbench and Favorite; Sponsor the owner where they accept it.
  • People: Follow and Unfollow; Block and Unblock (and, for an organization owner, block from the organization); Sponsor; see whether they follow you; Report opens GitHub's report page, which has no API.
  • Organizations: Follow and Unfollow; leave an organization you belong to; accept or decline an invitation; make your membership public or private.
  • Issues, pull requests, discussions, commits, releases: Subscribe and Unsubscribe (with GitHub's reasons: all activity, or only when mentioned); react with each of the eight reactions, and remove yours; pin an issue to the repository; favorite and pin in the Workbench.
  • Gists: Star and Unstar; Fork; Pin to your profile.
  • Notifications: Mark Read, Mark Unread, Mark Done, Snooze, Unsubscribe from Thread, Ignore Repository, and Watch Level for its repository, all on the notification's own sheet as well as its context menu.
  • Topics: Enter on a topic opens its repositories as a search. GitHub has no API for following a topic, so the coverage table says so.
  • Your own profile: name, bio, company, location, website, social accounts, pronouns, hireable, profile README (edited in the editor), status text, emoji and busy flag with an expiry, pinned repositories and gists in order, contribution settings that the API offers; email addresses (add, remove, make public, primary is read-only through the API).

Batch works here too: select twelve repositories in a search and Star them, or set their Watch level, in one step, with a result per row.

17. Filtering on every attribute

17.1 One filter, four ways in

The list's filter is one query. Four ways write it, and they stay in step:

  1. The filter box (Ctrl+E or Ctrl+Shift+F): type GitHub's own search syntax, is:open label:bug -label:wontfix milestone:2027.1 assignee:@me, or plain words. Plain words filter the loaded list; qualifiers query GitHub.
  2. The Filter Builder (Ctrl+Alt+F, or Edit > Filter Builder...): a dialog that lists every attribute of the current list's row type, each with an operator and a value picker filled from the repository (section 17.2). OK writes the query into the filter box, so people learn the syntax by watching it appear.
  3. The Filter menu (View > Filter), for the everyday ones, each a checked row that combines with the others (GHManage 1.1.0's form): Assigned to Me, Assigned To..., Opened by Me, Opened By..., Mentions Me, Review Requested from Me, Reviewed by Me, No Assignee, No Milestone, No Label, No Project, No Type, Drafts, Has Conflicts, Checks Failing, Updated This Week, and Clear These Filters. The status bar and window title name what is on: "owner/name - 4 issues (open), assigned to me, no milestone."
  4. Show only items like this on any cell: the context menu of a row offers Show Only, and Hide, for each value in it. "Show only label:bug", "Hide author:dependabot", "Show only milestone:2027.1". This is the fastest filter there is, and it teaches the syntax too.

Filters stay on as you move between repositories, as State does, until cleared, and any filter can be saved: Save Search makes it a node under Search > Saved Searches, and Pin makes it a node under Needs My Attention.

17.2 The Filter Builder

  • One row per condition: attribute, operator, value.
  • Operators per type: is, is not, any of, none of, has none (no:label), has any; before, after, between, in the last n days (dates); more than, less than, between (numbers); contains (text).
  • Values come from the repository: its labels, milestones, assignable people, authors seen, projects and their field options, issue types, branches, reviewers and teams, so you choose rather than spell. @me is offered as "Me" for every person field.
  • Any of and none of in one row write GitHub's comma and minus forms: label:bug,ui, -label:docs.
  • Or between groups where GitHub search allows it (OR and brackets in issue search), and a plain note where it does not.
  • Sort and order are part of the builder: created, updated, comments, reactions of each kind, interactions, and for projects any field.
  • Save as Search and Save as Default for This View on the builder.

17.3 Every attribute, honestly

  • Server first. Every attribute GitHub search can filter on is sent to GitHub, so the filter reaches items that were never in the loaded list.
  • Local where GitHub cannot. A few attributes GitHub's search does not index (a project field on a list that is not a project view, a workflow run's duration, a release asset's size) are filtered over the loaded rows, and the status bar says so: "Filtered locally: 40 loaded. Load All to be sure." Load All fetches every page first.
  • The attribute lists per row type are in Appendix C, in the Filter column. The highlights for issues and pull requests: state and state reason, type, labels, milestone, assignee, author, mentions, commenter, involves, team mentions, project and every project field, issue type, parent issue, has sub-issues, blocked or blocking, linked pull request, created, updated, closed and merged dates, comment count, each reaction's count, interactions, locked, archived repository, draft, review state, review requested from a person or team, reviewed by, base and head branch, checks and status, merge state, language, visibility, and "has none" for every list attribute.

17.4 Grouping

View > Group By puts the list's groups in the tree as child nodes, which a screen reader reads far better than group rows inside a list: Issues > by Milestone > 2027.1 (12). Group by label, milestone, assignee, author, type, project status or any project field, repository (in cross-repository lists), review state, or workflow. Ungroup returns the flat list.

18. Permissions, rigidly and completely

Permissions have two halves, and the Workbench does both: knowing what you may do and getting you what you need, and managing what others may do on everything GitHub lets you control.

18.1 Your permissions: one place, all at once

GHManage 1.1.0 added Help > GitHub Permissions...: every extra permission, what it is for, whether gh has it, and one command that adds every one that is missing. The Workbench does the same and goes further.

  • Account > GitHub Permissions... lists every permission any Workbench feature can use, grouped by what it unlocks, each row reading in full: "project: set an item's projects and edit project fields. You have it." The scopes it covers: repo, public_repo, read:org, admin:org, write:org, project, read:project, notifications, user, user:follow, user:email, gist, workflow, write:packages, read:packages, delete:packages, delete_repo, admin:repo_hook, admin:org_hook, admin:public_key, admin:gpg_key, admin:ssh_signing_key, security_events, codespace, copilot, read:audit_log. Optional, risky ones (delete_repo, delete:packages, admin:org) are unchecked by default and each says why you might want it.
  • One step adds every missing one. For the OAuth device sign-in (PR 1794), Add Permissions... runs the device flow again asking for the old scopes plus the new ones, and you approve once on GitHub. For a classic token, it opens GitHub's token page with the scopes listed to copy. For a fine-grained token, it lists the repository and organization permissions to set, by GitHub's names ("Issues: Read and write"). For gh, Copy Command gives gh auth refresh -h github.com -s ..., GHManage's form.
  • Check Again reads the permissions again and says what changed.
  • Missing a permission at the moment you need it gives a box with the one permission, Add It, and All Permissions..., never a bare error.
  • Fine-grained tokens and GitHub Apps do not list scopes in a header, so the Workbench asks GitHub per object instead (section 18.2) and says "This token's permissions are set on GitHub" rather than guessing.

18.2 Knowing before offering

  • Every object says what you may do with it. GitHub's GraphQL API answers per object: viewerPermission on a repository (admin, maintain, write, triage, read), and viewerCanUpdate, viewerCanDelete, viewerCanClose, viewerCanReopen, viewerCanReact, viewerCanSubscribe, viewerCanMinimize, viewerCanLabel and their kin on issues, pull requests, comments and discussions. The Workbench fetches these with the object and keeps them with it.
  • Greyed with a reason, never hidden. A row or field you cannot use is greyed (menus) or read-only (sheets), and its help says exactly why: the role you have, the role it needs, and who can grant it. "Delete Branch needs write access and the branch is protected by the ruleset Main branch; only maintainers may bypass it."
  • Every write declares what it needs. In the wx-free action table, each write command and each editable sheet field names its requirement: a repository role, an organization role, a token scope, a viewerCan field, a plan feature, or a combination. A test fails when a write command or editable field has none, so a new write cannot ship without knowing who may use it (GATE-GITHUB-PERM, section 18.6).
  • Effective access, explained. On any repository, Account > What Can I Do Here? lists your effective role and where it comes from: "Write, through the team Docs; Read, as the organization's base permission. The higher one counts."

18.3 Managing access: every object that has it

Every object with an access list gets an Access page on its Properties sheet, the same shape everywhere: a list of who has access (people, teams, roles, apps), each row "kellylford, person, Maintain, direct" or "Docs, team, Write, through organization"; and Add..., Change Role..., Remove, and Show Pending Invitations. Appendix D is the full catalogue; in brief:

  • Repositories: collaborators and their role (read, triage, write, maintain, admin, and the organization's custom repository roles); teams and their role; outside collaborators; pending invitations (cancel, change role); the effective access of anyone, and why.
  • Organizations: members and their role (member, owner), billing managers, security managers, moderators, outside collaborators, pending invitations and failed invitations; the base repository permission; member privileges (who may create public, private and internal repositories, fork private ones, create Pages sites, create teams, change visibility, delete and transfer repositories, invite outside collaborators); organization roles and custom repository roles; two-factor requirement (read).
  • Teams: name, description, privacy (visible or secret), parent team, notifications on or off; members and their role (member, maintainer); the team's repositories and its role on each; the team's projects and role.
  • Branches and tags: classic branch protection and rulesets in full (section 18.3.1).
  • Environments: required reviewers (people and teams, up to six), prevent self-review, wait timer, which branches and tags may deploy, whether admins may bypass, and the environment's own secrets and variables.
  • Actions: which actions may run (all, local only, or selected, with patterns for allowed actions and reusable workflows), the default GITHUB_TOKEN permission (read, or read and write), whether Actions may create and approve pull requests, approval for workflows from forks and first-time contributors, artifact and log retention, and runner groups and which repositories may use them.
  • Projects: visibility, and who may read, write or administer it, people and teams, plus the organization's base project role.
  • Packages: visibility, and which repositories, teams and people may read, write or administer it, and whether it inherits access from its repository.
  • Codespaces: who in an organization may create them, and which repositories they may be created for; a repository's devcontainer and machine types (read).
  • Security: private vulnerability reporting on or off, Dependabot alerts and security updates on or off, secret scanning and push protection on or off, code scanning default setup, and who may dismiss alerts.
  • Deploy keys and webhooks (section 14.3), each read-only or read-write, each event chosen.
  • Gists: public or secret.
  • Interaction limits: limit who may comment, open issues and open pull requests in a repository or across an organization (existing users, contributors only, collaborators only) and for how long.

18.3.1 Branch protection and rulesets, every combination

These hold the most combinations GitHub offers, so their sheet is laid out for it:

  • Target: branch or tag patterns to include and exclude, the default branch, all branches; for organization rulesets, which repositories by name pattern or property.
  • Enforcement: active, evaluate (report only), disabled.
  • Bypass list: roles, teams and apps, each "always" or "for pull requests only".
  • Rules, each a check box with its settings: restrict creation, updates and deletion; require linear history; require deployments to succeed (which environments); require signed commits; require a pull request (approvals needed, dismiss stale approvals, require code owner review, require approval of the most recent push, require conversation resolution, allowed merge methods); require status checks (which checks, from which app, strict or not); block force pushes; require code scanning results (tool, severity); require a merge queue (method, group size, wait times, build concurrency); commit message, author email, committer email and branch name patterns; file path, extension and size restrictions (push rulesets).
  • Classic branch protection stays editable for repositories that use it, on the same sheet, with Convert to Ruleset... where GitHub allows.
  • Read it as sentences. A Summary page writes the whole rule set in plain words: "On main: changes need a pull request with 2 approvals including a code owner; checks build and test must pass; force pushes are blocked; maintainers may bypass." That page is the one people will read first.

18.3.2 All combinations: matrices and bulk changes

"All combinations and permutations" means the Workbench can answer and change access from any side:

  • Who can do what here? On a repository, organization, team, project or package: everyone with access and their role, filterable by role and by source (direct, team, organization base).
  • What can this person do? On a person or team in an organization: every repository and their role on each, filterable, sortable by role.
  • The access matrix. Organizations > org > Access Review: a list with one row per person and repository pair, columns for role and source, filterable on every column (section 17), exportable as CSV, readable row by row. This is the accessible form of a grid nobody can read with a screen reader.
  • Bulk changes, any direction. Give a team Write on 12 repositories; remove an outside collaborator from all of an organization's repositories; copy one repository's collaborators, teams, labels, milestones, branch rules and environments to others; apply one ruleset to every repository matching a pattern. Each shows the full list of changes before anything happens (section 18.4), and a result per change after.
  • Templates of access. Save a repository's access, labels, rules and settings as a named template under Tools > Workbench Options > Templates, and apply it to a new or existing repository.

18.3.3 Teams, end to end

Today QUILL can only read which teams have access to a repository (Explore's Collaborators and Team Access view), and repo_admin.py still carries the old decision "Organizations in, Teams out". This PRD overrules it: teams are how organizations give access, so the Workbench manages them completely, through GitHub's 32 team operations (Appendix E, REST: teams) and the team mutations and viewer fields of Appendix F.

  • Where teams live in the tree: Organizations > org > Teams, shown as GitHub nests them, so a child team is a child node ("Docs (5 members, 3 child teams)"). People > My Teams lists every team you belong to, across organizations. Needs My Attention > Review Requests gains "for my teams", split from the ones asked of you by name.
  • Creating a team: Ctrl+N on the Teams node opens a new team's sheet: name, description, visibility (visible or secret), parent team, notifications on or off, its first members and maintainers, and its first repositories with a role on each. The preview reads the whole team back before it is made.
  • The Team sheet (Alt+Enter on any team, wherever it appears: the tree, an Access page, a review request, a mention):
    • General: name, slug (read-only), description, visibility, parent team, notifications, created, and "You are a maintainer of this team".
    • Members: every member with their role (member or maintainer) and whether they belong directly or through a child team; pending invitations; Insert adds people (several at once), F2 changes a role, Delete removes.
    • Repositories: every repository the team can reach and its role (read, triage, write, maintain, admin, or a custom role); Insert adds repositories by name or pattern, F2 changes the role, Delete removes.
    • Projects: the projects the team can reach and its role on each.
    • Child Teams: add, move under another parent, remove.
    • Code Review: code review assignment on or off, round robin or load balance, how many reviewers, whether to notify the whole team, and members to skip.
    • Identity Provider: for organizations that sync teams with an identity provider, the linked groups (read, and linked or unlinked where GitHub allows).
    • Danger Zone: delete the team (tier 3; its child teams move up, and the preview names every repository that loses the team's access).
  • What can this team do? The Repositories page sorted by role, and the access matrix (18.3.2) filtered to the team, answer it from the team's side; a repository's Access page answers it from the repository's side.
  • Every combination, in batch: add one person to many teams, many people to one team, give one team a role on many repositories, copy one team's repositories and roles to another, or move a set of people from one team to another, each with the preview and a result per change.
  • Teams in filters: team-review-requested:org/docs and team:org/docs in the Filter Builder, with the organization's teams as the values, and Show Only on any team name in a row.
  • Permissions to manage teams: organization owners manage every team; team maintainers manage their own team's members and settings; members can create teams when the organization's member privileges allow it (Appendix D). The sheet greys what you cannot change and says which of those you are.

18.4 Rigid control: nothing risky without a preview

Every write command is in one of four tiers, set in the action table and tested:

Tier Examples What happens
0, organizing labels, assignees, milestone, project fields, reactions, subscribe Saves at once; undoable
1, visible to others comments, close and reopen, review, request reviewers, edit title Saves at once by default; Workbench Options can ask first
2, access and settings roles, teams, invitations, branch rules, rulesets, Actions permissions, environments, visibility, webhooks, interaction limits A preview lists every change in words; Enter applies; undoable where GitHub allows
3, destructive or hard to reverse delete a repository, branch, tag, release, package, project, team, environment, webhook; transfer; make a private repository public; remove an admin or owner; turn off branch protection The preview, then the object's name typed to confirm, as Delete Repository does today

Guards that hold whatever the tier:

  • No self-lockout. Removing your own admin role, the last owner of an organization, or the only admin of a repository is refused with the reason, and the sheet says who else could do it.
  • No surprise exposure. Making a repository, project, package or gist public says what becomes visible (open issues, Actions logs, secrets names never, wiki) before it happens.
  • Batch deletes list every item in the preview, and never run unattended.
  • Read-only accounts. Tools > Workbench Options > Accounts can set an account to Read Only, Organize (tiers 0 and 1), or Full. A Read Only account is ideal for demonstrating, teaching or reviewing someone else's organization: every write is greyed, with "This account is read only in the Workbench" as the reason.
  • Safe Mode (QUILL_SAFE_MODE=1) makes every account Read Only for the session.

18.5 A record of every change

  • Account > Change History lists every write the Workbench made for each account: when, what object, what changed before and after, the tier, and whether GitHub confirmed it. Filterable like any list; Copy and Save as CSV.
  • Kept on this device in the Workbench's own store, written atomically, for as long as Workbench Options says (default 90 days), and clearable from Privacy and opt-ins. Secret values and tokens never appear in it.
  • Undo GitHub Change (section 16.5) works from this list too, on any row GitHub allows.

18.6 Gates

  • GATE-GITHUB-PERM: every write command and every editable sheet field declares its requirement and its tier (section 18.2 and 18.4); a test fails on one without.
  • The action table drives the greying, so menus, context menus, Shift+F1 and sheets cannot disagree about what you may do.
  • The network egress audit gains a row for each new kind of endpoint (the access, ruleset, webhook, key and audit-log APIs). They are all to api.github.com, which the audit already knows, but the inventory names them so the review is real.

19. "Absolutely everything", measured

Jeff's brief is that anything doable on GitHub has a way here. A list written by hand goes stale the week GitHub adds a feature, so coverage is measured against GitHub's own description of itself:

  • The source: GitHub publishes its REST API as an OpenAPI description (github/rest-api-description) and its GraphQL schema. A snapshot of both is vendored under quill/data/github_api/, refreshed by a script on purpose, never fetched by the app or by tests.
  • The coverage table: quill/core/github/api_coverage.json classifies every REST operation and every GraphQL mutation (and the queries the Workbench reads) as one of:
    • covered: the command id or sheet field that does it;
    • planned: its row in the PLANNED table (section 14.4) and its future home;
    • no_api_needed: low-level plumbing the user never meets as such (Git trees and blobs, which Commit Multiple Files uses underneath; emojis; Markdown rendering; meta);
    • out_of_scope: GitHub Enterprise Server administration, and GitHub App installation internals, each with a one-line reason.
  • GATE-GITHUB-COVER: a new operation in a refreshed snapshot is missing and fails until somebody classifies it. The planned list may only shrink release over release, like every other backlog gate. Rostered in platform_report.
  • The generated reference (docs/github/workbench-reference.md) gains a "Everything GitHub can do, and where" chapter from the same table, by GitHub's own category names: Actions, Activity, Billing, Branches, Checks, Code scanning, Codespaces, Collaborators, Commits, Copilot, Dependabot, Dependency graph, Deploy keys, Deployments, Discussions, Gists, Interactions, Issues, Labels, Milestones, Organizations, Packages, Pages, Projects, Pull requests, Reactions, Releases, Repositories, Rulesets, Search, Secret scanning, Security advisories, Sponsors, Teams, Users, Webhooks, Wikis. Someone asking "can QUILL do X?" gets the answer and the key in one place.
  • Wikis have no API; GitHub serves them as a Git repository (owner/name.wiki.git). The Workbench reads and writes them through that repository (clone, edit in the editor, commit), so they are covered by the Git route, not left out.

21. Building templates: issue forms, pull request templates and more

21.1 Where it stands today

  • quill/core/github/issue_templates.py reads Markdown issue templates (front matter: name, about, title, labels, assignees), and New Issue... offers them.

  • Repository > Templates in the tree lists every template the repository has, and those it inherits from its organization (marked "inherited from org/.github"), one row each: "Bug report, issue form, adds bug and triage, 6 fields, 3 required."   • Alt+Enter on a template opens its sheet:
    • General: name, description, file name, kind; the title prefix; the labels, assignees, projects and issue type it applies, each with its picker and New... row. A label that does not exist yet is flagged and offered to be created, since GitHub silently drops labels that do not exist.
    • Fields: the form's elements as a list, one row each: "Steps to reproduce, long text, required." Add Field... asks the type (short text, long text, dropdown, check boxes, instructions), then opens that field's sheet. Alt+Up and Alt+Down move a field; Duplicate and Delete do what they say.
    • Each field's sheet: label, description, placeholder, default value, id (made from the label, editable, checked for uniqueness), required; for long text, render as code in a language (shell, YAML and so on); for a dropdown, its options in order, multiple choice, and default; for check boxes, each option and whether that one is required; for instructions, the Markdown text.
    • Preview: the form exactly as a person filing an issue will meet it, filled in with the keyboard, using Fill It In Yourself. The issue body it would produce is shown below, as GitHub will write it.
    • Checks: the problems list for this template (section 21.5).
    • Source: the YAML or Markdown, read-only, with Open in Editor.
  • The Chooser sheet (Repository > Templates, Alt+Enter on the node): blank issues allowed or not; contact links as a list to add, edit, remove and reorder; and the order templates appear in. GitHub orders them by file name, so Move Up and Move Down rename with number prefixes ("01-bug.yml") and say so.

21.4 Three ways to build one

  1. The builder above, for people who want every option labelled.
  2. As plain text, in the editor. Write the form in BFL, the plain-text form language QUILL's Forms already reads, and Save as GitHub Issue Form... writes the YAML. Open a GitHub issue form and it reads back as BFL. A new interop module, quill/core/forms/interop_github.py, maps the QAF model to GitHub's schema and back, beside the SurveyJS and XLSForm ones; where a QAF feature has no GitHub equivalent (scores, conditions, payments), the export says which and leaves it out.
  3. The YAML itself, in the editor, with Check This File (Navigate > Code) validating it against GitHub's issue form rules as you work, in the Problems pane.

And three ways to start: a starter (bug report, feature request, question, documentation, accessibility bug report with the screen reader, browser and assistive technology fields people forget to ask for, security report pointing to private reporting); a copy of a template from any repository you can read; or a conversion: a Markdown template to an issue form (its ### headings become long-text fields), an issue form to Markdown (which loses the structure, and says so first), and SurveyJS, XLSForm or QAF forms where their field types map.

21.5 Checks that catch what GitHub only reports after you commit

GitHub shows a broken issue form as an error on its template chooser, after it is on the default branch. The Workbench checks before saving, with each problem on its line:

  • Required keys: name and description; at least one field that is not instructions; every field but instructions has a label.
  • Ids and labels unique; ids only letters, numbers, hyphens and underscores.
  • Dropdowns and check boxes have options, and the options are unique and not "None", which GitHub reserves.
  • Labels, assignees, projects and type exist and you may set them.
  • Accessibility, from the Forms checks: a placeholder is never the only label, descriptions are short, required fields are marked, instructions use headings in order, and link text says where it goes.

21.6 Saving

  • Save commits the template through the Commit to GitHub route, to the default branch, or to a new branch with a pull request (decision 18). The sheet says templates only take effect from the default branch.
  • Needs write access to the repository, or to the organization's .github repository for defaults (section 18.2). It is tier 1: visible to others.
  • Copy to Repositories... applies one template, or a whole set with its chooser, to many repositories at once, with the preview and the result per repository of section 18.3.2.

21.7 Filling every kind natively

  • New Issue... with an issue form opens the form as a real dialog: each field a labelled control, required fields marked and checked, errors next to their fields and announced, dropdowns as lists, check boxes as check boxes. Submit writes the body exactly as GitHub would: each field as a ### Label heading and its answer, _No response_ for an empty optional field, check boxes as - [X] and - [ ], and long text rendered as code fenced in its language. It applies the template's title prefix, labels, assignees, projects and type. "Link-only" goes away.
  • New Discussion... in a category with a form does the same.
  • New Pull Request... offers the repository's pull request templates when there are several, and fills the one chosen into the description.
  • Possible duplicates (Appendix B) are still checked when filing.
  • Golden tests pin the body format against bodies GitHub produced, so a form filed from QUILL is indistinguishable from one filed on the web.

21.8 Community health files

The other files GitHub reads from a repository get the same treatment on Repository > Templates > Community Files: each listed as present, inherited or missing (the Community Profile checklist, Appendix A); Create from starter... for each; edited in the editor; and FUNDING.yml, CITATION.cff and CODEOWNERS each with a small sheet of their own fields (sponsor platforms and names; title, authors, version, DOI; path patterns and their owners, with a check that every owner exists and has write access).

22. Thinking further: what else GitHub does, and what only this Workbench could do

Jeff, 2026-11-09: "think very creatively here, as I don't think everything is captured." This section is a second sweep in two directions: GitHub features the sections above still leave out, and things an accessible Workbench can do that github.com cannot.

22.1 GitHub features still missing above

Each with its home, so it lands in the PLANNED table (section 14.4) and the coverage gate (section 19) from day one.

  • Copilot, all of it. Coding agent sessions: assign an issue, watch the session's log as it works, steer it with a comment, stop it, review its pull request (Item > Copilot). Copilot code review settings per repository. Custom instruction files (.github/copilot-instructions.md, .github/instructions/*.instructions.md, AGENTS.md), each with a sheet and edited in the editor. Organization Copilot seats, policies, content exclusions and usage metrics as tables (Organizations > org > Copilot).
  • GitHub Models. Prompt files (.prompt.yml) in a repository: a sheet for the model, messages, variables and test data; run a prompt against a model and compare models side by side as text; evaluations as a results list.
  • Building workflows. The template builder's approach applied to Actions YAML (Repository > Actions > New Workflow...): starter workflows from GitHub, triggers as check boxes with their filters, jobs as a list, steps as a list, each step's action found by search with its inputs as labelled controls, versions pinned to a commit with one choice, permissions per job (section 18.3), and the job graph read as "test needs build". Required workflows for an organization. Check This File for workflow YAML.
  • Dependabot configuration (.github/dependabot.yml): ecosystems, directories, schedule, groups, ignore rules, reviewers, labels, private registries, as a sheet; and the @dependabot comment commands (rebase, recreate, ignore this major version) as Item > Dependabot rows on its pull requests.
  • Merge conflicts. When a pull request conflicts, Item > Resolve Conflicts... checks out the branches in a local worktree, opens each conflicted file in the editor at its first conflict, offers Keep Ours, Keep Theirs, Keep Both per conflict, and commits the result. GitHub's web conflict editor is one of its least accessible pages.
  • Pull request review, the remaining pieces: mark a file as viewed and filter to unviewed files; multi-line and file-level comments; hide whitespace changes; split or unified diff as two ways of reading; review one commit at a time; "changes since your last review".
  • Task lists inside bodies. The - [ ] items in an issue's body are a list on the issue's sheet: check one off and the body is updated; convert an item to a sub-issue.
  • Merge queues as places. Repository > Merge Queue: each queued branch's entries in order, with their checks, Remove and Jump to front (admins).
  • Commit statuses (Item > Set Status... on a commit) for people who drive their own automation, and deployment protection rules from apps (read).
  • Repository creation, fully: owner, name (checked as you type), description, visibility, a README, a .gitignore from GitHub's list, a license from GitHub's list with each license explained in plain words, a template with or without all its branches, and the starting labels, milestones, rules and access from a saved template (section 18.3.2).
  • Moving work in and out: export your account's data or an organization migration archive (where the API allows) and download it; import issues from CSV with a preview (section 22.7); fork with only the default branch.
  • Git LFS: files tracked, storage used, and file locks (who holds which lock, lock, unlock, force unlock with permission).
  • Insights in words: Pulse for a week or month ("12 pull requests merged by 5 people"), forks with ahead and behind as the network graph's readable form, traffic referrers, popular paths, clones, and the dependency graph and dependents.
  • Your contributions: the contribution graph as a table by week and day, with streaks, totals and the repositories contributed to, read row by row.
  • GitHub Apps and OAuth apps: apps installed on an organization or repository, which repositories each may reach (add, remove), suspend and unsuspend, and requests to install; apps you have authorized.
  • OpenID Connect: the subject claim template for an organization or repository, for people deploying to clouds from Actions.
  • Security, the remaining pieces: push protection bypass requests and alert dismissal requests to review and decide; Copilot Autofix suggestions on code scanning alerts, applied as a pull request; the organization security overview as a table; dependency review on a pull request.
  • Discussions, the remaining pieces: spotlight, category sections, and polls built in the template builder's style.
  • GitHub status: a status bar cell and Help > Is GitHub Working? that read githubstatus.com (a new egress row, with consent).

22.2 The escape hatch: an API Console

Whatever this plan misses, and whatever GitHub ships next week, should still be reachable. Tools > GitHub API Console... is a dialog where you choose REST or GraphQL, write the path or query (with completion from the vendored API description, section 19), see what permission it needs, and send it as the current account. The answer is shown as a tree you can walk with the arrow keys, each node reading "title: Fix the crash", with Copy Value, Copy Path and Save as JSON. Writes go through the same tiers and previews as everything else, and land in Change History. Any request can be saved as a named command, and a saved command can be given a key and put on the Item menu, so a power user can add the feature they need the day they need it.

22.3 GitHub from the editor, where the code is

The Workbench is for GitHub; the editor is where people already are. These editor commands open no window unless they must (QUILL and QUILL Lite both):

  • Copy GitHub Link to This Line (or selection), as a permalink to the commit.
  • Who Changed This Line? speaks the last commit, author and date for the line, and a second press opens the pull request that brought it.
  • Open This Line on GitHub, and Open the Pull Request for This Line.
  • New Issue from Selection... files an issue quoting the selection with its permalink.
  • Issues Mentioning This File opens the Workbench filtered to them.
  • Comment on This Line in the Open Pull Request when the document is part of a pull request checked out in a worktree.
  • References in any document (#42, owner/name#42, @person, commit hashes) are recognized; Alt+Enter on one opens its Properties sheet.

22.4 Reading GitHub like a document

  • Read as Document (Item menu) opens an issue, pull request or discussion thread as a read-only document in the editor: one heading per comment ("kellylford, 9 November, 14:05"), quotes as quotes, code as code, so heading navigation, find, Read Aloud, braille and every reading tool QUILL has work on a GitHub conversation. Export it to Word, EPUB or DAISY to read later or offline.
  • Comment boxes are editors. Mentions (@), references (#) and emoji (:) complete as you type; Markdown preview reads aloud; saved replies insert; attachments upload.
  • What you post is accessible. Before a comment, issue, pull request or release posts, the Workbench checks it as QUILL checks documents: an image with no alt text (and an offer to describe it with AI), headings out of order, link text like "here", a table with no header row. It offers, never blocks.
  • Pictures, diagrams and math in issues are read the way QUILL reads them in Markdown pages: Mermaid diagrams as their accessible text, math as speech, and images described on request.
  • Braille-shaped rows. A Workbench Options choice makes list rows short enough for a 40-cell display: "#42 open bug Fix crash" instead of the full sentence.

22.5 Watches: tell me when it happens

GitHub's notifications are about threads. People also want to know about moments. Watch This... on any object sets a watch, kept in the Workbench and listed under Needs My Attention > Watches:

  • this pull request's checks finish, or any check fails;
  • this run finishes;
  • this pull request is approved, merged, or gets a new review;
  • this issue is closed, or gets a comment from a particular person;
  • a release is published in this repository;
  • my rate limit is back;
  • this person opens a pull request in this repository.

When it happens, the Workbench says it in one sentence and plays the moment's sound, through the shared action-feedback channels (sound, speech, both, silent), even while you are writing in the editor. Watches check on the same schedule as notifications (decision 21) and cost no extra requests where an ETag says nothing changed.

22.6 Plain language in, a previewed batch out

The Command Key work (PRs 1796, 1800, 1801) gives QUILL a way to say a command. The Workbench gives it GitHub actions to say:

  • "Close every issue labeled stale that nobody touched in 90 days."
  • "Give the Docs team write on every repository whose name starts with quill."
  • "Which pull requests are waiting on me, oldest first?"

A sentence becomes a query and a set of changes, shown in the same preview as any batch (section 16.4), with the same tiers; nothing runs until Enter. AI is also offered where it saves real work: suggest labels and a type for a new issue, explain a ruleset or an access list in plain words, draft a reply, summarize a long thread, explain why a run failed (today's What Failed, everywhere).

22.7 Lists in and out

  • Export any list as CSV, Excel, Markdown table or a QUILL table document, with the columns showing: issues, members, the access matrix, alerts, runs, Change History.
  • Import issues from CSV or a spreadsheet: map columns to title, body, labels, assignees, milestone, type and project fields, preview every issue, create them with a result per row.
  • Issues from a task list: select lines in a document and New Issues from Lines makes one issue per line, optionally as sub-issues of a parent.
  • Copy settings between repositories: labels, milestones, templates, rules, environments, access, Actions permissions and repository settings, each a check box, with the preview (section 18.3.2).

22.8 Learning GitHub, safely

  • GitHub words on F1. Every GitHub term in the Workbench (fork, rebase, squash, ruleset, environment, triage) has a one-paragraph explanation in the help catalogue, and F1 on any row offers it.
  • Tutorials: Help > Tutorials gains GitHub lessons in the shared tutorials engine: your first issue, your first pull request, reviewing, re-running a failed run, setting up a template, giving someone access.
  • A practice repository. Help > Practice on GitHub... creates a private repository in your account named for practice, seeds it with issues, a pull request and a failing run, and offers to delete it when you finish, so people can learn tier 3 actions on something that does not matter.
  • Dry Run, a Workbench-wide switch on the status bar: every write shows its preview and stops there, saying "Dry run: nothing was changed." Useful for learning and for checking a big batch twice.

22.9 Several accounts, side by side

  • Compare Accounts: what each of your signed-in accounts can do on this repository, in one list.
  • Act As... on any write: do this one change as another of your accounts, named in the preview, without switching the whole Workbench.

22.10 Permissions you can see before you grant them

  • View As Role... on a repository or organization: the Workbench greys and explains every menu row, context row and sheet field as a person with that role would meet it (read, triage, write, maintain, admin, or a custom role, or "this team" or "this person"). Read-only, and the clearest answer to "what will they be able to do?".
  • Compare Roles... lists what one role can do that another cannot, in GitHub's own words, including custom roles' added permissions.
  • Why Can't They? on a person and an action: the role they have, the role or rule that stops them, and the smallest change that would let them.

Scopes, the other half of every combination. Each place works over a scope you choose: every repository you can administer, one organization, your own repositories, or a Repository Set, a named list kept in the Workbench ("QuillVille family", "Docs sites"), made by hand or by a filter (org:Community-Access topic:quillville). Part C: the keyboard

Section 8 listed the first keys. This part is the whole map. Every key here is a proposal until it passes the checks in C1; the Workbench's own keymap.APP_KEYMAPS entry (decision 7) holds the result, the keyboard reference is generated from it, and the Key Describer names every key.

C1. How the keys were chosen

  1. Windows, Outlook and File Explorer first. A key a listener already knows from those wins over a key we invent (family rule 1's spirit): Alt+Enter is Properties, Delete removes, F5 refreshes, Ctrl+Q and Ctrl+U mark read and unread, Ctrl+1 to Ctrl+9 jump between places, Alt+Up goes to the parent, Ctrl+L goes to an address, Ctrl+E searches.
  2. Families that teach themselves. Once you know one key in a family you can guess the rest:
    • Ctrl+number goes to a top-level place; Ctrl+Shift+number goes to a part of the current repository.
    • Alt+number says something about where you are, and never moves you.
    • Ctrl+Shift+letter acts on the selected item (comment, what failed, compare, copy link).
    • F-keys keep their Windows meanings: F1 help, F5 refresh, F6 pane, F10 menu.
  3. Plain letters belong to type-ahead in the tree and the lists, so a listener can always jump to a name by typing it. No letter is ever a command, and there is no option to make one (decision 11).
  4. One key changes things: Alt+Enter. No key sets a single property; the Properties sheet does all of it (section 16.3).
  5. Nothing a screen reader owns. No Insert or Caps Lock combinations; no Ctrl+Alt+arrow keys, which NVDA and JAWS use for table navigation; no Alt+Shift or Ctrl+Shift alone, which switch keyboard layouts; nothing with the Windows key.
  6. Nothing the family owns system-wide. Checked against the system-wide show and hide keys (Ctrl+Alt+Shift+Q and R among them), DEFAULT_ALIASES, and the other apps' global hotkeys, as the free-chord check requires.
  7. No Ctrl+Alt+letter for anything typed into a text box, because on many European layouts Ctrl+Alt is AltGr and types a character.
  8. Every command has a key or a written reason (family rule 8); rare commands get a key, not a short one (rule 9); destructive commands never get a single bare key.
  9. Everything is rebindable through the Menu Editor and key settings, and the menu shows whatever is bound (_menu_label).

Part D: help, everywhere and excellent

Jeff, 2026-11-09: help must be "extensive, amazing and purely awesome throughout this experience." Section 7 set the engine and the gate. This part is the whole experience.

D1. The promise

Wherever you are and whatever has focus, help has an answer, it is written for someone who has never used GitHub, it says what you can do next and with which key, and it is never more than one key away. Nothing is "self explanatory". Nothing is help only for sighted users.

D2. The help keys

D3. Layers: what F1 says, where

  1. The window: what the Workbench is for, the three panes, F6, Enter, Alt+Enter, the context menu key, Back, and where to start.
  2. A tree node: what this place shows, what you can do here, what it needs (sign-in, a permission, a plan feature, an opt-in), and whether you have it. For example, Settings > Branch Protection: "The rules that decide who may change each branch and how. You have Admin here, so you can change them. Ctrl+N adds a rule; Alt+Enter on a rule opens all its settings."
  3. The list: the node's help, then what the selected row type is and its default action, then the five most useful keys for it.
  4. A row: the item in a sentence ("Pull request #1811, open, from claude/wxpython-4-3-2 into main, checks passing"), then its actions.
  5. A sheet page: what the page covers and when you would come here.
  6. A sheet field: what it means on GitHub, what the choices do, the default, who can change it, and an example. A read-only field adds why it is read-only and what would change that.
  7. A menu row: its topic from topics.json, its key, and, if greyed, why.
  8. A dialog: its purpose and then its controls, through the same engine.

D4. Help that appears without asking

None of this is announced; it is in the place the reader reaches next.

  • Empty states: an empty list's details pane says why it is empty and what would fill it: "No pull requests need your review. When someone requests your review it appears here and in Inbox."
  • Greyed rows and read-only fields carry their reason as their help string and their accessible description.
  • Previews explain each change in words a newcomer understands, and what it means for the people affected ("They will be able to label and close issues, not push code").
  • Errors say what happened, what it means and what to do, with a button for the fix where there is one. Each carries its QUILL-GITHUB-... error code (GATE-EC), and the code's help page is one key away.
  • The first time you meet a place, its details pane opens with a short "First time here?" paragraph, until you have used the place three times or choose Do Not Show Again.
  • Start Here (Ctrl+9): what the Workbench is, sign-in state, the five keys to learn first, the guide, the tutorials, and the practice repository.

D5. What Can I Do Here? (Shift+F1)

The single most useful help in the window. For whatever is selected (a row, several rows, a node, a sheet field), it opens a list of every action that could apply, in the order of the context menu, each row reading "Close issue, Delete" or "Merge, greyed: the required check build has not passed." Enter runs the action; F1 on a row explains it. It is built from the same action table as the menus, so it can never disagree with them.

D6. The GitHub glossary (Alt+F1)

About two hundred GitHub terms, each in one plain paragraph with an example and the place in the Workbench where you meet it: from "Actions" to "workflow dispatch", including roles (read, triage, write, maintain, admin), every rule in a ruleset, every notification reason, every alert kind, and the words GitHub uses for states ("draft", "merge queue", "stale review"). It lives in the help catalogue (workbench_help.py), renders into the F1 reference, and is searchable from Search Help.

D7. Search Help (Ctrl+Shift+F1)

A dialog with one search box and one results list. It searches everything: node help, row help, field help, menu topics, the glossary, the guide's headings, settings, tutorials and keys. Each result says what it is ("Command: Re-run failed jobs, Ctrl+Shift+F5") and Enter does the obvious thing: runs a command, goes to a node, opens a setting, starts a tutorial, or opens a help topic. Typing "who can merge" finds the merge requirements, the ruleset rules, View As Role, and Why Can't They?.

D8. The guide, the reference and the tutorials

  • The GitHub Workbench Guide is rewritten around the tree: an Introduction, then one chapter per top-level node, then chapters for Properties, editing, filtering, permissions, templates and the keyboard, each opening with why you are here, what you will do and what you will have by the end (the family's guide structure), with chapter cross-references, and a keyboard reference at the end.
  • The Workbench reference (docs/github/workbench-reference.md) is generated from the tree, menu, context, sheet and action tables, plus the coverage table's "everything GitHub can do, and where", and drift-gated.
  • The F1 reference (docs/f1-help-reference.md) includes every Workbench help string.
  • Tutorials (Help > Tutorials), each a short guided lesson on the practice repository: your first look around; triage an inbox; file an issue with a form; review a pull request; fix a failed run; plan a milestone; organize a project board; give someone access; write a branch rule; build an issue form; use the API Console.
  • Release notes tell the story of each Workbench release in the family's human voice (the docs voice rule): what you can now do, and the key.

D9. How help is written

  • A human voice: plain words, short sentences, what to do before why, no marketing, none of the AI tells the family's docs rule lists, and no engineering rationale in user-facing help.
  • Check, never tick, for check boxes; "Community Access"; no emoji.
  • One idea per help string, an example where it helps, and the key.
  • Accurate to the account: help that depends on your permission says what you have now, not only what is needed.
  • Translatable: every string through the family's gettext path.

D10. Gates that keep help excellent

  • GATE-GITHUB-HELP (section 7): every control, node, row type, sheet page and field has authored help; the missing list starts from today's and may only shrink; zero before the Workbench becomes the default.
  • check_help_coverage --strict over the github.* namespace: every command has a topic.
  • The action table test: every action has a Shift+F1 row and a reason string for each way it can be greyed.
  • The glossary test: every GitHub term used in a node, row or field name has a glossary entry.
  • The generated references (GATE-KEYREF, GATE-HELPREF) drift-gated, and both documentation-chord gates over the guide.
  • A review step: a person reads each new help string aloud before it merges, because a gate can prove help exists, not that it helps.

D12. Do Something: help that takes you there and walks with you

The fastest help is the one that does the first step for you.

  • A task list in plain words, grouped by what people come to do: "Find what needs me", "Fix a failed run", "Give someone access", "Write a branch rule", "Moderate comments", "Fix pictures without alt text", "Update plugins safely". Each task names the keys it uses.
  • Take Me There on any topic or task moves focus to the place and the control it is about: the right node, the right row, the right page of the right sheet. It says only where it put you.
  • Walk Me Through It runs the task as a guided walk on the real data (or the practice repository and practice site, if you choose): each step says what to do and waits for you to do it, F1 repeats the step, Shift+F1 lists the steps, Escape stops. The tutorials engine already does this for lessons; here any help topic can.
  • Do It on a topic whose answer is one command runs it, with its usual preview, so reading "how do I re-run failed jobs" ends with them re-running.

D13. Every result can explain itself

  • F9 says the last result again (the family's key, Part C).
  • Shift+F9, Explain That, says what the last result means and what you might do next, in a paragraph: "Re-ran 2 failed jobs of the build on main. They run again from the start, on the same commit. A Watch can tell you when they finish: Alt+Enter on the run, then Watch."
  • Why? is on everything automatic: why a Watch fired, why a row is greyed, why a filter is local, why an entry was held as spam, why a rule moved a notification, why a sheet field is read-only. Shift+F1 on the item lists it first.
  • Previews explain every change in the reader's terms, and F1 in a preview explains the change under focus in more depth.

D14. Help that knows your situation

  • Examples from your own data. Help uses what is in front of you: "On Community-Access/quill, this rule would block force pushes to main, which you did twice last month." "On Community Radio, Day and name would make this post's address https://.../2026/11/09/morning-show/."
  • Aware of your role and plan. Help says what you can do now and, when you cannot, what you would need, and who on this repository or site can give it to you.
  • Aware of the site or account: a WordPress topic knows which plugins the site runs ("Your site uses Yoast, so this page also has SEO fields"); a GitHub topic knows whether the organization uses rulesets or classic protection.
  • Aware of where you came from: help on a node you reached from a notification starts with the notification's reason.

D15. Help you can take with you

  • Key cards: Help > Keys > Make a Key Card writes the keys for this Workbench as a one-page document, a QUILL table, or a braille file (BRF), through QUILL's own braille output, ready to emboss or read on a display.

  • Offline: all of help is on this computer; nothing needs the internet except Ask a Person and the optional AI answers of D18.

D18. Ask the Workbench (optional AI)

For people who prefer to ask: Help > Ask How, in plain words ("how do I give the Docs team access to every repository?"). D19. One source for all of it

A topic is a record (id, title, body, example, keys, commands, related words, related topics, the places it applies to, and the roles and plans it mentions), so each of those surfaces is generated, and a change appears in all of them at once.

D20. Help quality, measured

  • Braille length: the first sentence of each topic fits a 40-cell display line where it can, because it is what a braille reader meets first.
  • Read aloud: a person reads each new topic aloud before it merges (D10), and the section 12 sessions with people include "find the answer in help" as a task, timed.

F3. Reliability

  • All network work on QuillTaskManager, results back through wx.CallAfter; the UI thread never waits on GitHub.
  • Offline and errors: cached views stay readable with "Offline, showing what was loaded at 14:05"; writes are refused with the reason, never queued silently; every failure has a coded error and help (D4).
  • Rate limits: the remaining budget is known (Alt+6); work pauses before the limit and resumes on its own, and says so once.
  • Atomic local stores: preferences, resume state, Change History, Watches and saved commands through write_json_atomic, schema-validated.
  • Crash reports go through the family's redaction.

F4. Security and privacy

  • Credentials stay where they are today (token_store.py, Credential Manager, DPAPI). The Workbench never shows, logs, speaks or exports a token.
  • Secret values are write-only: encrypted on this machine with the target's public key (GitHub's sealed-box scheme) before sending, through PyNaCl, which QUILL already ships for Quillin signing (decision 12, decided). The first slice is built: quill/core/github/secret_values.py and Explore's secret and variable writes (branch feat/github-secret-values).
  • Webhook secrets and deploy keys are set, never read back.
  • No telemetry. Change History, Watches and saved commands stay on this device and are clearable.
  • The API Console applies the same tiers, previews and history as every other write; it cannot bypass Read Only or Safe Mode.
  • Untrusted content: issue bodies, comments, templates and logs are data. Nothing from GitHub is executed; templates are parsed, never run (as issue_templates.py already promises).

F5. Testing

  • wx-free tables first: tree, menus, context rows, sheets, fields, actions, filters, tiers and help are data in quill/core/github, so most rules are unit tests (sections 10 and 18.6).
  • Recorded API responses for every loader and saver, including GitHub's silent-ignore cases, so tests never call GitHub.
  • Golden bodies for issue forms (21.7) and golden previews for tier 2 and 3 changes.
  • GATE-LITE-COVER for every QUILL Lite handler, by behavioural test.
  • A live regression run against a practice organization, the way WordPress has docs/qa/wordpress-live-run.py, run by the parent session before a Workbench branch merges, with the account's consent and its credentials kept in Credential Manager.
  • The section 12 tasks with five people before Phase 3 and Phase 6.
  • The suite rules: machine_global marks for anything touching the clipboard, global hotkeys or screen-reader bridges; serial re-runs before believing a parallel failure.
