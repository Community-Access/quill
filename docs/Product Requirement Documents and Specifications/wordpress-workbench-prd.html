Additional user requirement: change an existing form field's control

An existing QAF field can change to another supported control type after it has been added. QUILL preserves the label, help, rules, compatible choices and other shared properties; converts single and multiple defaults where needed; and previews settings that will be adjusted or dropped. A conversion that needs required setup first is refused with the missing properties named.

For Gravity Forms, QUILL offers conversion for common text, paragraph, email, number, drop-down, radio and checkbox controls. It reads and retains the full form object, shows the selected field and conversion preview, checks for concurrent edits, then updates through REST v2 only after confirmation and the site's gravityforms_create_form capability check. Other field families stay untouched until their API behavior is supported.

Part A: the product

A1. In one paragraph

Writing a page stays where it belongs, in the editor, where QUILL already makes blocks plain and checks a page before it goes out. Everything else about running a WordPress site (comments, media, menus, people, plugins, themes, settings, forms, the shop, the podcast, the site's health, and every site you look after) moves into one WordPress Workbench: a tree of where you are, a list of what is there, details about the one you picked, and Alt+Enter for the Properties of anything. It is built on the same engine as the GitHub Workbench, so the two windows look, sound and answer the keyboard the same way, and learning one is learning both.

A2. The short version

  • Writing stays in the editor; running the site moves to the Workbench. Enter on a post or page opens it in the editor. Everything that is not writing a document gets one home.
  • One engine, two Workbenches. The tree, list, details, Properties sheets, filters, action table, tiers, Change History, help catalogue and coverage gate are built once, in shared modules, and GitHub and WordPress are two providers of the same window shape (section 3).
  • Needs My Attention, across every site: comments waiting, drafts waiting for review, scheduled posts, updates available, Site Check and accessibility problems, new form responses, new orders, broken links, pictures with no alt text.
  • Alt+Enter is Properties, on everything: posts, pages, media, comments, categories, tags, menus, users, plugins, themes, templates, patterns, fonts, widgets, settings, forms, responses, products, orders, and any custom post type a plugin adds.
  • Any plugin's content, automatically. WordPress describes every route with a schema, so the Workbench builds a list and a Properties sheet for custom post types, taxonomies and plugin routes it has never seen (section 12).
  • Edit everything the site lets you edit, in batch through WordPress's batch endpoint, verified afterwards, undoable through revisions and Change History.
  • Filter on every attribute the REST API can query, and on the rest locally, honestly.
  • Permissions from the account's own capabilities, known before offering, explained when missing, and managed where WordPress lets them be (roles, application passwords, registration, discussion), with View As Role.
  • Bold extras: a practice site that runs on this computer through WordPress Playground, site to site copying (staging to live), a content calendar, an editorial queue, the whole site read as a book, Watches, plain-language batches, a REST Console, and the WordPress Abilities API as commands.
  • The same keys as the GitHub Workbench. Ctrl+number to go places, Alt+number to hear where you are, Delete to move to Trash (which WordPress can undo), Alt+Enter for everything else, and typing always moves through the list.
  • Help that teaches WordPress, for people who have never opened wp-admin.

A3. The problem

wordpress.md built a great deal, and put each command where a Word user looks (wordpress.md 12): File > WordPress for the document and the site, Insert, Format, View and Edit for what happens inside a page, and Tools > WordPress for everything else. Writing works well that way. Running a site does not:

  • Tools > WordPress is a row of separate windows: Media Library, Comments, Categories and Tags, Menus, Site Check and Settings, Manage (users, plugins, themes, fonts, synced patterns), Site-wide Find and Replace, Alt Text Review, Visual Review, Check the Whole Site. Each has its own layout, list and buttons. Moving from a comment to the post it is on, to that post's author, to their role, is four windows.
  • No place says what needs you. Pending comments, posts waiting for review, updates and Site Check problems are each found by opening the right window.
  • Several sites multiply it. Switch Site changes one current site, so a person who looks after five sites checks each in turn.
  • What a plugin adds is invisible. A custom post type (events, recipes, courses, products) has no window unless QUILL wrote one for that plugin.
  • wp-admin is still the fallback for whatever has no window, and wp-admin is the reason this exists.

A4. Goals

  1. Parity with wp-admin wherever the REST API reaches, measured by the route audit (wordpress.md 9.17 and 9.18) turned into a gate (section 12).
  2. Better than wp-admin by ear: moderation, media, menus, people, settings and site health become lists you can move through and sheets you can read.
  3. One window shape across the family. A person who knows the GitHub Workbench knows this one.
  4. Every site at once where that helps: one Inbox, one search, one calendar.
  5. Safe: previews, Trash first, revisions, verify after save, no self-lockout.
  6. Help everywhere, in plain words.
  7. QUILL Lite is never ahead, and never behind: the same window in both.

A5. Not goals

  • Replacing the editor for writing. The Workbench never edits a page's blocks; it opens the page in the editor.
  • Hosting or installing WordPress on a server.
  • Editing role capabilities, which WordPress's REST API does not offer; the sheet shows them read-only and says so (section 11).
  • A visual site builder. Design changes go through global styles, templates and patterns as data, with Visual Review (wordpress.md 6.11) for checking.

2. Principles

  1. Writing is a document; a site is a place. Documents open in the editor. Places open in the Workbench. Enter on a post is "write"; Alt+Enter is "about".
  2. One engine. Nothing here is built twice: if the GitHub Workbench has it, WordPress uses it, and anything WordPress needs that GitHub would too goes in the shared engine.
  3. Where, what, about (GitHub PRD 2.1); one home per feature, chosen by what kind of thing it is (GitHub PRD 2.2).
  4. Trash first. Anything WordPress can put in Trash goes there, and Delete means Trash. Permanent deletion is a separate, tier 3 command.
  5. The site's own words. Statuses, roles and settings use WordPress's names, explained in the glossary, never renamed.
  6. Discover, don't hard-code. Post types, taxonomies, statuses, settings, routes and abilities come from the site, so a plugin's additions appear without a QUILL release.
  7. The existing windows are not thrown away; their loaders, savers and checks become the Workbench's providers.

9. Edit everything the site lets you edit

  • Every writable field of every object, from its sheet; the menu rows open the sheet at the right page. No per-field keys (the GitHub PRD's rule, 16.3): Alt+Enter, and the page.
  • Batch, the way wp-admin's Bulk Edit should have been: select any rows, Alt+Enter, change status, author, categories added and removed, tags added and removed, comments on or off, pings, sticky, template, parent, format; the preview lists every item; sent through WordPress's batch endpoint (/batch/v1, 25 requests a call), with a result per item and retry.
  • Media in batch: alt text, captions, descriptions, titles, attachments, across a selection, with AI suggestions offered (wordpress.md 6.8), never written without review.
  • Terms: rename, change slug, parent and description, merge two terms (reassign every post, then delete the old one), convert a tag to a category and back.
  • Undo: Undo WordPress Change reverses a change from Change History; for content, Previous Versions restores any revision; Trash restores anything trashed.

10. Filtering on every attribute

The four ways in of GitHub PRD 17.1 (filter box, Filter Builder, Filter menu, Show Only and Hide on cells), writing one query. Here the query is the REST API's own parameters, so every filter reaches the whole site, not just the loaded rows:

  • Posts, pages and custom types: search, status, author (and not author), categories and tags (any of, all of, none of), every custom taxonomy, before and after (published), modified before and after, sticky, parent, menu order, slug, format, and ordering by date, modified, title, author, relevance, menu order.
  • Media: type, file type, attached or not, parent, author, date, has alt text (locally), size (locally).
  • Comments: status, post, author, author email, parent, type, date ranges, search.
  • Users: role, capability, has published posts, search, registered date.
  • Plugins and themes: status, has update, auto-updates on.
  • Form responses and orders: every field of the form; order status, customer, total, date, product.
  • Local filtering for anything the API cannot query, said honestly in the status bar, with Load All (GitHub PRD 17.3).
  • Across sites: the same filter can run on every connected site at once from Search and Needs My Attention.

11. Permissions

  • Know before offering: roles and capabilities from users/me?context=edit (wordpress.md 9.2), on connect and daily, per site. Every action and field declares the capability it needs (edit_posts, publish_pages, moderate_comments, manage_categories, upload_files, edit_theme_options, activate_plugins, update_plugins, list_users, promote_users, manage_options, and the rest), and the action table greys with the reason: "Publishing pages needs the Editor role or higher. You are an Author on Community Radio."
  • Managing people: add users (with role and a welcome email choice), change roles, send a password reset, remove a user with their content reassigned to someone else (the preview names how many posts move), and on a network, add a site's users and super admins.
  • Roles, read-only and explained: each role's capabilities are listed in plain words on the Users node's Properties. WordPress's REST API cannot change a role's capabilities, so the sheet says so, and points to the site's role plugin if one is installed and offers routes (section 12).
  • Application passwords: your own on each site (create with a name, revoke, see last used and from where), and other users' where you may.
  • Content access: visibility (public, private, password protected, with the password write-only), comments and pings per post, registration (anyone can register, default role), discussion settings (moderation, approval rules, blocklists).
  • Workbench access per site: Read Only, Organize, Full, and Safe Mode as Read Only (GitHub PRD 18.4).
  • Tiers and guards: GitHub PRD 18.4's four tiers, with Trash as tier 1 (undoable) and Delete Permanently as tier 3; no removing your own Administrator role or the last Administrator; deactivating the plugin that provides QUILL's own connection (for example a forms or REST plugin) warns first.
  • View As Role: the Workbench greys and explains everything as an Author, Editor, Contributor, Subscriber or any custom role would meet it.

12. Coverage: every route, discovered

wordpress.md 9.17 audits routes by hand. Here that becomes live and gated:

  • Each site describes itself. The REST index (/wp-json/) lists every namespace and route the site offers, and each route's methods and argument schema; OPTIONS on a route returns its full schema.
  • Known routes map to the tree, sheets and actions built for them.
  • Unknown routes become usable anyway. For a custom post type or taxonomy registered with REST support, the Workbench builds its node, list columns, filters (from its query arguments) and Properties sheet (from its schema: strings as text boxes, enums as lists, booleans as check boxes, dates as date boxes, integers as numbers, references as pickers). For any other route family, "More from this site" lists it by namespace with a sheet for each readable item.
  • The coverage gate (shared coverage.py) runs against the test site's recorded index: every route is covered, schema_built, planned, wp_admin_only (with the screen it opens) or out_of_scope, and a new route is missing until classified.
  • The Abilities API (WordPress 6.9 and later): the site's registered abilities appear under Abilities as commands, each with its input schema as a sheet, its permission check, and a preview; plugins that register abilities get commands here with no QUILL release.

The combination test. For each route in the recorded index, a generated test asserts that every GET argument has a Filter Builder attribute, every enum value is offered, every writable schema property has a sheet field, and every method has an action. A route that fails is missing in the coverage gate. So when WordPress or a plugin adds an argument, the gate names it.

Writing combinations. Batch edits (section 9) combine with filters: any filter's result can be selected and changed together, and the preview says how many items each change touches. Changes that conflict (setting a status some selected items cannot have, such as future without a date) are named in the preview rather than failing halfway.

12b. Making your own post types, taxonomies and fields

Why it needs something on the site. WordPress has no REST route that creates a post type, a taxonomy or a custom field. Each is registered by PHP code that runs on every page load (register_post_type, register_taxonomy, register_meta), so a desktop app cannot create one on its own. Something on the site has to keep the definition and register it. There are two ways, and the Workbench supports both.

Way 1: a plugin the site already has.

  • Advanced Custom Fields (free since 6.1) creates post types, taxonomies and field groups in wp-admin, and can show fields in REST. The Workbench reads and edits the fields it shows (WP-R-034). Whether ACF lets field groups themselves be created over REST is to verify; if not, Create Field Group opens the right wp-admin screen.
  • Pods, Meta Box and Custom Post Type UI the same way, each to the level its API reaches (Pods has REST routes of its own, to verify).

Way 2: QUILL Site Types, a small plugin of our own (or a module of QAF, decision 12):

  • REST routes to define things: post types (name, labels, slug, hierarchical, supports, archive, menu position, icon, which taxonomies), taxonomies (name, labels, hierarchical, which types), and field groups (which types, terms, users or comments they attach to, and their fields). Each definition is stored as data and registered on init with show_in_rest, so it appears in the REST index and the Workbench discovers it like anything else (section 12).
  • Field types, ours: a field has a JSON schema type (string, number, integer, boolean, array, object), which is all WordPress stores, plus a field kind that says how to edit and check it. The kinds: text, long text, rich text, number, money, date, time, date and time, true or false, choice, several choices, email, address, phone, link, colour (named, with its contrast), picture (with required alt text), file, gallery, related item (any type), related term, related user, repeater (a list of groups), group, location, and accessible-by-default kinds no field plugin has: a transcript for audio, captions for video, a long description for a picture, and a language-marked text. Each kind has its accessible control in the Properties sheet and its check (an email must be one; a picture must have alt text).
  • Your own kinds: a site can add a kind by giving its schema, its label and its check rules, and the Workbench builds its control from the schema (section 12a), so a new kind needs no QUILL release.
  • Nothing locked in: Export as Code writes the definitions as a PHP file (the register_* calls) or as theme.json-style JSON for a theme, so a site can stop using the plugin and keep its types and fields.
  • Permissions: defining types and fields needs manage_options; filling them in follows each type's own capabilities (section 11).
  • In the Workbench: Sites > site > Content Model lists the site's post types, taxonomies and field groups, whoever registered them (core, a theme, a plugin, or QUILL Site Types). Ctrl+N makes a new one, Alt+Enter opens its sheet: General, Labels, Supports, Taxonomies, Fields (a list with Insert, Delete, and Alt+Up and Alt+Down for order, each field's own sheet for its kind, label, help, required, default and choices), Permissions, and Export.   • Templates with them: a new type can come with a starter page shape and a QAF form for collecting entries of that type (an event submission form that creates an Event), tying types, fields and forms together.

13a. Spam: on the site, and in the Workbench

Spam is caught on the site, by the site, because QUILL runs on the writer's computer and is not there when a visitor presses Submit. The Workbench is where a person sees what was caught, why, and puts right what was caught by mistake. Two kinds: comments (WordPress core) and form entries (QAF and the other form plugins of 13b).

13a.1 What QAF does on the front end today

Verified in S:\code\qaf at cbc7fef (2026-11-07):

  • Honeypot, on by default (includes/security/class-qaf-honeypot.php).
  • Rate limiting, per address and per form, on by default (class-qaf-rate-limiter.php).
  • CAPTCHA, off by default, with five providers: reCAPTCHA v2, reCAPTCHA v3, hCaptcha, Cloudflare Turnstile, and a maths question (class-qaf-captcha.php).
  • An entry status of spam in its table (active, trash, spam, pending, approved, rejected), readable and settable through its REST API (/entries, /entries/{id} with status).

What it does not do yet: check what was written (links, known spam phrases, known spam senders), keep a reason or score with a spam entry, or work with the spam services and security plugins a site already has.

13a.2 The rule that matters most: never punish people for how they use a computer

Many bot detectors watch mouse movement, typing rhythm and how long a page was open. Keyboard users, screen-reader users, switch users and people dictating all look "unusual" to those signals, and they are exactly who QUILL is for. So, for QAF:

  1. Prefer checks that look at what was sent, not how it was typed: the honeypot, a minimum time to fill (generous: never under three seconds), rate limits, link counts, the site's own WordPress blocklist (disallowed_keys), and a content check by a spam service (13a.3).
  2. Prefer challenges a person never sees: Turnstile in its managed or invisible mode, reCAPTCHA v3, or proof-of-work (ALTCHA, open source, solved by the browser in the background). A visible puzzle is the last resort, and always offers an accessible alternative.
  3. Hold, never drop. Anything a check doubts is kept with status spam and the reason, not thrown away, and the visitor sees the same polite confirmation either way, so a real person caught by mistake loses nothing: someone reviews it (13a.5) and it comes back.
  4. Say why. Every held entry or comment keeps which check flagged it and its score: "Held: 6 links (the limit is 3)", "Held: OOPSpam score 5 of 6", "Held: filled in 1.2 seconds".

13a.6 Text challenges: accessible, and as strong as a text challenge can be

A text challenge (a question in words, answered in words) is the one kind of CAPTCHA that works the same by ear, by braille, by switch and by voice. QAF's maths question is the start. The honest limit first: any text a screen reader can read, an AI model can read and answer, so no text challenge stops a determined bot. What it does well is stop the large majority of form spam, which comes from cheap scripts, and cost the rest time and money. So it is built as one layer that appears only when it is needed, never as the gate.

When it appears: risk first, question second.

  • The quiet checks run first (13a.2): honeypot, time to fill, rate limit, proof of work, the content check. Most people never see a question.
  • A question is asked only when those checks are unsure. When they are sure it is spam, the entry is held without asking anything.
  • A site can choose Always Ask for a form under attack, and Never Ask.

What the questions are like. Answerable by anyone who can use the form, in any language the site offers, without trivia, arithmetic or knowledge of the site:

  • Everyday sense: "Which is colder, snow or soup?"
  • Following an instruction about the question itself: "Type the second word of this sentence."
  • Choosing from a short list, read in full: "Which of these is an animal: chair, horse, window?" (also as radio buttons, for switch and voice users).
  • Ordering: "Put these in order, smallest first: town, city, house."
  • Maths only as an option, because numbers are a barrier for people with dyscalculia.

What makes it hard to beat cheaply:

  • Made fresh each time from templates and word lists on the server (thousands of combinations per language), never one fixed question a bot can learn.
  • The answer never reaches the page. The server keeps it with a one-time challenge id that expires in 15 minutes and works once.
  • Bound to the visit: the challenge is tied to the form, the session and the proof-of-work token, so answers cannot be farmed and replayed.
  • Each failure costs the bot more: more proof of work for the next try, and a tighter rate limit, while a person sees the same gentle question.
  • The site's own words: a site can add questions in its own voice, and the bank grows with them.
  • No tricks that harm people: no hidden "if you are a bot, type X" text, because screen readers read hidden text too and would trip real users.

Generous to people:

  • Answers are matched loosely: capitals, spaces, punctuation, numbers as digits or words, common misspellings, and any of several right answers.
  • No lockout. A wrong answer gets a new question with the same patience, and after three tries the form offers Send Anyway: "A person will read it before it is published or answered." The entry is held (13a.5), never lost.
  • It is a form field like any other: a label, the question as its description, the error next to the field and announced, no time limit, and F1 help in QUILL's fill window.
  • This follows the intent of WCAG 2.2's Accessible Authentication criterion (3.3.8), which counts puzzles as cognitive tests that need an alternative, and the W3C's note on the inaccessibility of CAPTCHA.

In the Workbench: the Spam page (13a.5) shows how often the question was asked, passed, failed and sent anyway, and lets a site edit its own question bank, choose the kinds, and preview questions in each language. A sentence sums it up: "Asked 40 times this week; 31 passed, 2 sent anyway, 7 gave up."
