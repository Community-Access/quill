GitHub Workbench: keyboard and screen reader reference

This is the technical reference: what each window does and which part of GitHub it calls. For a book on doing the work, written for screen-reader users, read The GitHub Guide for QUILL and QUILL Lite, which ships with both editors.

The GitHub Workbench is the only GitHub management window (2026-11-10). Every GitHub door in both editors opens one window, quill/ui/workbench_frame.py with the GitHub provider quill/ui/github_workbench_window.py; its tree, menus, keys, context menus, options and glossary are generated at the end of this page. The separate Items and Explore management windows and their fallback preference are retired.

QUILL and QUILL Lite share the Workbench. QUILL Lite opens it from File > GitHub Workbench (Alt+F, then G). In QUILL, use File > Open from Remote > GitHub Items. Public repository reading works without an account. Account views and writes require a signed-in GitHub account. Safe Mode and first-use network consent still apply.

GitHub Workbench Mode. View > GitHub Workbench Mode (Alt+V, then K), a per-window check item in both editors, adds a GitHub menu (Alt+G) right after Tools and moves the GitHub rows of File > Open from Remote and Tools > Git and GitHub into it; turning it off puts them back. Both editors build it from one wx-free table, quill/core/github/workbench_menu.py (QUILL: quill/ui/main_frame_github_menu.py; QUILL Lite: quill/apps/lite_github_workbench.py, which also serves the empty window). QUILL Lite's menu is the table less QUILL's own rows. Rows keep their command ids, so a user-bound key follows the row; nothing in the mode has a default chord. New entry points open a view directly: Inbox, My Work and Notifications open Explore on attention, my_work and notifications; Issues and Pull Requests, Actions Runs and Releases open Items on issues, runs and releases (the new initial_view argument); Explore GitHub opens Explore on its default. They are quill/ui/github_workbench_commands.py, shared, and go through each editor's existing opener and gates. The switch announces "Workbench mode on. GitHub menu added." and "Workbench mode off." through the announcement service; nothing else in the mode speaks. While it is on, both editors' status bars carry a Workbench cell ("Workbench: owner/name", or "Workbench" with no repository), worded once in workbench_menu (STATUS_CELL_KEY, status_cell_text): QUILL's in quill/ui/main_frame_github_status.py (a workbench item in STATUS_BAR_ITEMS, hidden by default and shown only in the mode), QUILL Lite's in quill/apps/lite_status_cells.py (shown only with text). It is reached with F6 and the arrow keys like every cell and is never announced (GATE-13); the repository is looked up once per document path while the mode is on. It is not remembered across sessions. In QUILL the mode needs GitHub Remote Access (core.github_remote), which since 2026-11-08 no longer depends on core.developer.

Clone Repository. QUILL: File > Open from Remote > Clone Repository...; QUILL Lite: File > Clone Repository... (Alt+F, then Y); both: GitHub > Clone Repository... in workbench mode. Shared window quill/ui/github_clone.py, core quill/core/github/clone.py. Git is found by quill.core.git_binaries.find_git: QUILL_GIT (dev builds only), then <runtime>/mingit/cmd/git.exe, then git on PATH, then the optional component copy. It runs git clone -- <url> <folder> through run_subprocess_safely (argv, no shell) on the task manager. For an https github.com clone the signed-in token travels only in the child's environment, as GIT_CONFIG_COUNT/GIT_CONFIG_KEY_n/GIT_CONFIG_VALUE_n setting http.https://github.com/.extraheader for that process; it is never in argv, .git/config, the remote URL or the log, and it is registered with redaction.remember_secret. GIT_TERMINAL_PROMPT=0 stops a hidden password prompt. An address with a user name or password in it is refused. With no git, one sentence offers the Git for Windows download page.

Signing in. Manage GitHub Accounts (QUILL: File > Open from Remote; QUILL Lite: File, Alt+F then H) offers Sign In with GitHub... first, and as the default button while no account is saved. It is GitHub's OAuth device flow (quill/core/github/oauth_sign_in.py, UI in quill/ui/github_device_sign_in.py): QUILL posts to github.com/login/device/code with the app's own OAuth client id (the same per-app registration My GitHub Copilot uses, copilot_auth.CLIENT_IDS), puts the user code on the clipboard and in a read-only field that takes focus, opens github.com/login/device, and polls github.com/login/oauth/access_token at GitHub's interval on a worker thread, adding five seconds on slow_down. Expiry, a declined request, Cancel and a network failure each end in one sentence in the step's What to do field. The token is then checked with GET /user and saved with save_github_account, exactly like a pasted token, in the same store as every other account; Copilot's token stays in its own entry. The scopes requested are repo workflow gist read:org project security_events user:follow delete_repo, each justified beside WORKBENCH_SCOPES, so one sign-in covers every Workbench command. Add Token (Advanced)... keeps the pasted-token route for fine-grained or limited tokens; the guides teach it only in chapter 10, "Advanced: using a token". Organizations that restrict OAuth apps must approve QUILL once (Settings > Applications > Authorized OAuth Apps > Request or Grant).

Tokens (2026-11-08). Each account records how it was added (added_by: sign_in, token, or unknown for accounts saved before) and a small state (account_state in github-accounts.json, never a secret): whether the sign-in suggestion was shown, the token's expiry as GitHub reported it, and the day the expiry was last mentioned. quill/core/github/token_health.py decides both messages. The suggestion: when the active account has a classic token (ghp_, or X-OAuth-Scopes on a pasted one) with a broad scope, Manage GitHub Accounts says "This account uses a token. Sign In with GitHub is easier to keep up to date." once, then asks; Yes opens Sign In with GitHub, No opens the window as usual, and it is never asked again for that account. The expiry warning: TOKEN_EXPIRY records GitHub-Authentication-Token-Expiration from every REST reply and every items-provider repository read (the token as a SHA-256 fingerprint, in memory); each editor's Workbench gate calls quill/ui/github_token_expiry.py's watch_token_expiry, which, for a token expiring within seven days or already expired (the latter from the filed expiry, since a dead token's replies carry no header), says one sentence at most once a day per account and adds a Notifications entry whose target github-accounts opens Manage GitHub Accounts. No new network endpoint: both read headers of replies the Workbench already receives.

In QUILL, File > Open from Remote > Open GitHub Reference accepts a pasted repository or GitHub URL. The Items window also has Open Link... in both QUILL and QUILL Lite. Repository links open Items; issue links select the exact issue; pull-request links open its review reader; branch links select that branch; and GitHub file links open in QUILL at the linked line. QUILL Lite opens file and other unsupported object links in the browser after explaining that the workbench has no native view for that object. Browser fallback never attaches QUILL's GitHub token. Malformed or credential-bearing URLs are refused.

The interaction pattern

The Items window is a repository list with a read-only detail field. Choose a view, arrow through its rows, then Tab to read the selected item in full. Shift+Tab returns to the list. The Actions button and the selected row's context menu expose commands relevant to that item. Open the context menu with Shift+F10, the Applications key, or right-click. M switches between compact and fully labelled list speech. Alt+N and Alt+P move between comments in an issue or PR's details. Ctrl+F searches GitHub in the loaded repository; Ctrl+Shift+F filters the already loaded rows locally. Ctrl+D saves the selected item as a favorite.

When you reopen Items, QUILL restores the last repository, view, filters, and selected row for the same GitHub account. This is local resume state; it stores no token and never submits a draft or changes GitHub.

The PR review window uses an actual expandable tree. The root PR contains Changed files, General conversations when present, and Checks. Files contain review threads. Left and Right collapse or expand; Up and Down move between visible nodes. Tab reads the selected node's complete detail, then Shift+Tab returns to the tree. On a thread, Ctrl+R replies; Ctrl+Shift+R resolves or reopens it after confirmation, if GitHub permits. The context menu also contains these commands, copy actions, and Open File Differences. A thread's file and line select the matching file and exact changed line when its patch still contains that line. If the line is outdated or absent, the diff explains the missing location. No action is triggered merely by reading or expanding. Next Unresolved moves among threads with a known unresolved state; Next Unvisited tracks only the threads you selected in this review session. It is local navigation and never marks GitHub notifications or threads read.

The Explore window uses a list and detail field for flat results. Its View chooser switches between global search, My Work, the attention queue, activity, repositories, people, notifications, gists, and repository-specific views. Enter opens the selected result on GitHub; Use Repository sends a repository back to Items. The context menu offers actions for the current result. Search queries saved with Save Search stay on this computer and can be reopened or removed with Saved Searches. The repository chooser places pinned and recent entries first. A selected label can lead into a repository-scoped issue search. Star, watch, notification-read, and label changes require a signed-in account.

The attention queue combines work assigned to you, requested reviews, mentions, and pull requests with failed checks. Queue Options chooses up to ten repositories and the categories to include, saves and reopens local filters, and shows locally snoozed items. Snoozes and filters are stored separately for each signed-in account and do not change GitHub. Each result names its source and last update; duplicate results are combined. The status reports partial loads instead of presenting them as a complete queue. A complete load records the visit time so later visits can identify changed items. Opening the queue never marks remote notifications as read.

Repository and workflow views

Items includes issues and PRs, branches, commits, tags, releases and assets, workflow definitions, and workflow runs. Enter on a branch opens its commits; Backspace returns to branches. Enter on a release opens its assets and download counts. A workflow definition can be dispatched on a chosen branch. On a run, Jobs and Logs lists its jobs and loads a selected job's text log. View Artifacts lists downloads. The context menu exposes the same applicable commands as the buttons, including copy and browser actions. On an issue or PR, Start in Local Worktree can prepare a separate local branch and folder when the current checkout has a matching GitHub remote. QUILL shows the starting local branch and any uncommitted changes first. Those changes stay in the existing folder; the new worktree starts from the local commit and does not fetch, push, or change the GitHub repository.

Workflow diagnostics show each job's steps, the selected attempt, and the head SHA. Choose an earlier attempt from the attempt list; Load Annotations reads the check-run annotations when GitHub grants access, and reports permission errors instead of treating them as no findings. Annotation output is capped at 100 entries with a truncation message. Job logs are limited to 4 MB and mark truncation. The run and job links open their exact GitHub pages.

Projects opens the selected repository's GitHub Projects v2 boards in a list/detail view. Project rows show the fields available to your account; issue details include blockers, sub-issues, and parent progress. Next Unblocked moves to the next open issue or pull request without an open blocker. The Actions menu can update supported text, number, date, single- or multi-select, and iteration fields, or add/remove blocker and sub-issue links. Each remote change names its target and effect in a confirmation. Permission errors and incomplete project pages remain visible in the status.

Explore adds your repositories and work, starred and watched repositories, people you follow and followers, a person's public repositories and activity, repository activity and people, forks, labels, Pages site and build history, notifications, and security alerts. Private information and certain actions depend on the GitHub token's permissions and repository access. An API failure appears as a status message; empty results are distinguished from errors. The Security view combines Dependabot, code-scanning, and secret-scanning alerts. Secret values are never loaded into the view. If the account cannot read a category or the feature is disabled, the view labels that category unavailable instead of presenting it as having no findings.

Notifications triage

Explore's GitHub notifications view is the account's whole inbox. In QUILL, Tools > Git and GitHub > GitHub > Notifications opens Explore straight at it; in QUILL Lite, choose Explore in Items and pick the view. After each load QUILL says the unread count once, for example "12 unread". Each row reads its state, then why it arrived in words ("review requested", "you were mentioned", "your team was mentioned"), then the repository and title.

Under the list, shown only in this view: Include read notifications (Alt+I), Mark Done (Alt+D), Unsubscribe (Alt+U) and Mark All Read (Alt+A). Delete in the list is Mark Done. Done and Unsubscribe take the row out of the list and select the next row, so triage keeps its place. Mark All Read asks first and marks only what arrived before the list loaded. Enter marks the row read, then opens a pull request in the review window, an issue in Items at that issue, and anything else in the browser. The context menu offers the same actions.

QUILL honours GitHub's X-Poll-Interval: a refresh sooner than GitHub allows keeps the current list and says how long to wait. A refresh after that sends If-Modified-Since, so an unchanged inbox costs no rate limit.

What failed, and run actions

On a Workflow Runs row, What Failed (Ctrl+Shift+W in that view, the Actions menu or the context menu) opens a read-only text field holding one digest: each failed job, its failed steps, the annotations with file:line, then the last 40 meaningful log lines of each failed step with timestamps and ANSI codes removed. A step's lines are the ones stamped inside its start and finish times; if GitHub gave no times, the digest says so and uses the end of the job's log. Jobs and Logs has the same digest as What Failed (Alt+F), for the attempt you chose, and Re-request Check (Alt+C) for the selected job.

The same menus add Re-run Failed Jobs Only, Cancel Run (GitHub answers "accepted", so QUILL says it is stopping the run), Delete Run (the confirmation names the run, branch and result, and says logs and artifacts go with it), Approve Run from a Fork, Review Pending Deployments (a window listing waiting environments as check boxes, a required comment, and Approve and Reject) and Combined Check Status, a single line such as "3 of 4 checks pass; failing: test."

Auto-merge and the merge queue

The review window's Auto-Merge and Queue button (Alt+A) and the pull request's context menu hold Enable Auto-Merge (with a merge-method chooser), Disable Auto-Merge, Add to Merge Queue, Remove from Merge Queue and Combined Check Status. After Check Merge Policy, the combined status counts only required checks ("3 of 4 required checks pass"). A check node's context menu has Re-request Check; a legacy commit status cannot be re-requested and QUILL says so. Each change asks first and reports GitHub's confirmed result. Known refusals, such as auto-merge being turned off for the repository, are said as what to do next.

Repository files, blame and history

Files (Alt+F) in Items, or Browse Repository Files on its context menu, opens Repository Files: a real tree of the repository at a branch, tag or commit typed or picked in Branch, tag or commit (Alt+B). Right arrow or Enter opens a folder (fetched the first time), Left closes it, and each file says its size. Enter on a file or View File (Alt+V) shows it read-only in Contents. Open in Editor (Alt+E) opens it for editing: QUILL uses the same path as a GitHub file link, so Commit to GitHub works afterwards; QUILL Lite opens the text as a new untitled document. README (Alt+R) shows the selected folder's or the repository's README. Binary files and files over GitHub's 1 MB contents limit say so instead of showing text.

History (Alt+H) lists the commits that changed the selected path. Blame (Alt+L) lists the file in runs, neighbouring ranges from one commit joined into one: "Lines 10 to 14: author, date, short SHA, commit title". In both lists Alt+N and Alt+P move to the next and previous row from anywhere in the window, and Enter or Open Commit (Alt+O) opens the commit on GitHub. Blame uses GraphQL blame(path:) on the commit and needs a signed-in account.

Milestones and batch changes

Milestones in Items (no access key; Tab to it, or use the context menu) lists milestones as words: "Release 2.0: 61 percent done, 5 open, 8 closed, due 12 December". Show (Alt+S) picks open, closed or all. New (Alt+N) and Edit (Alt+E) take a title, description and a year-month-day due date; Close Milestone or Reopen Milestone (Alt+L) asks first. Every change is reported from GitHub's reply.

The Batch menu adds Set milestone (the open milestones, or clear it) and Add assignees (usernames separated by commas) beside Close, Reopen and Add label. The confirmation names the items; the result counts what GitHub confirmed, and names anyone GitHub did not assign.

Discussions and security triage

In Explore's Discussions view, Enter (or Open Discussion Thread on the context menu) opens a thread window: the discussion, then each comment followed by its replies. It says "Answered by" and the name, and reads a poll one option to a line ("Option A: 12 votes, 40 percent"). Reply (Alt+R) comments on the discussion or replies under the selected comment; Mark as Answer (Alt+M) marks or unmarks the selected comment after asking, when the category takes answers and GitHub says you may. New Discussion on the view's context menu picks a category and takes a title and body.

In the security views, Dismiss Alert on the context menu offers GitHub's own reasons for that alert kind (Dependabot: fix_started, inaccurate, no_bandwidth, not_used, tolerable_risk; code scanning: false positive, won't fix, used in tests; secret scanning: false_positive, wont_fix, revoked, used_in_tests), an optional comment of up to 280 characters, and a confirmation. Dismissed and resolved security alerts is its own view, where Reopen Alert asks and then reopens. QUILL reports a change only when the alert's new state comes back from GitHub.

The summary comes from one GraphQL query (reviewDecision, statusCheckRollup, unresolved reviewThreads, autoMergeRequest, mergeStateStatus, and baseRef.compare for a same-repository branch). Its readiness phrase goes through the same rules as the review header, so partial or unknown data reads as "merge readiness unknown", never as ready. The query takes aliases, so several pull requests can share one request.

A line comment posts through POST /pulls/{n}/comments with commit_id, path, line, side and, for a range, start_line and start_side. Add to Review keeps it in a per-account local file, pinned to the head it was written on. Compose Review sends the review and every pending comment in one POST /pulls/{n}/reviews, and refuses when the head has moved since. The outline lists pending comments, each with Edit and Delete (Delete asks first).

Changed since my last review reads the account's latest review commit_id and compares it with the head (GET /compare/{reviewed}...{head}). A missing commit, after a force-push, is said plainly and the filter shows every file.

The timeline reads GET /issues/{n}/timeline, up to five pages of 100, and says when it stopped early. Reactions list, add and remove through the REST reactions endpoints for issues, issue comments and review comments; removal deletes only the signed-in account's own reaction. Counts read in words in comment details ("3 thumbs up, 1 heart").

Rate limits and conditional requests

rate_limits.py keeps the latest X-RateLimit-* headers from every REST reply. The readout reads GET /rate_limit (free) and GraphQL rateLimit. Notification polling doubles its interval under a quarter of the allowance, quadruples it under a tenth, and waits for the reset at zero. A secondary limit (Retry-After, or a 403 or 429 naming one) is recorded once; until it passes, every request stops before the network with "GitHub asked QUILL to wait 60 seconds", and Explore folds the warnings it caused into that one sentence.

conditional_requests.py keeps the last ETag and body of each repeated read per account (64 reads, 256 KB each, in github_etag_cache.json) and sends If-None-Match; a 304 shows the stored body and costs no rate limit. Explore says "No changes since the last load" when a reload found the same rows.

Request Copilot Review sends POST /pulls/{n}/requested_reviewers with copilot-pull-request-reviewer[bot], the login GitHub's Copilot code review documentation names for the REST API, and reads the reply's requested_reviewers back: GitHub can answer 201 and leave Copilot off, which is how an account or repository without Copilot code review answers, and QUILL says so rather than reporting a request. A 422 is said as "Copilot code review may not be available".

Assign to Copilot follows GitHub's "Using Copilot cloud agent via the API". One GraphQL query reads suggestedActors(capabilities: [CAN_BE_ASSIGNED]) and the issue's ID, state and assignees; without copilot-swe-agent among the actors, QUILL says the coding agent is not available and sends nothing. Otherwise it asks, then sends replaceActorsForAssignable with the existing assignees' IDs plus the agent's, so nobody already assigned is dropped. Both calls carry GraphQL-Features: issues_copilot_assignment_api_support,coding_agent_model_selection. Success is said only when the mutation's assignee list holds the agent.

Commit Comments reads GET /commits/{sha}/comments (100 a page, up to ten pages, and says when there were more) and posts with POST to the same path, sending path and line for a comment on a line; the deprecated diff position is never sent.

Gists: POST /gists, PATCH /gists/{id}, DELETE /gists/{id}, and PUT or DELETE /gists/{id}/star. The gist window edits a local draft (gists.py), and saving sends one PATCH in which a deleted file is null and a renamed one carries filename. A file GitHub truncated is never sent back. Create and save are confirmed against the files and description GitHub returns.

The attention queue adds pr_summary.py's sentence to each pull request row from one aliased GraphQL request per refresh (attention_queue_summaries.py), covering the twenty newest pull requests. It keeps the summary's rules: unknown or partial data reads "merge readiness unknown", a pull request GitHub did not answer for reads "Summary unavailable", and the row's reason stays the first line of its details. A summary gap is said in the status line but does not mark the queue itself incomplete.

Review and write safety

The review tree announces reply counts, outdated positions, resolved state, and check status. Selecting a thread never resolves it. Reply, resolve, reopen, review submission, branch updates, and other writes each require a deliberate command and confirmation where appropriate. Actions are disabled if the PR is closed, the account is signed out, or GitHub denies that permission. If the review-thread state cannot be retrieved, threads remain readable while resolution controls are unavailable. Refresh to observe changes made elsewhere. If the review's diff cannot be loaded, the threads and checks still appear and QUILL says "Could not load the diff" with the reason. A refresh that finishes after a newer one started is dropped, so it can never overwrite newer data.

The Items Batch menu operates on checked issue or PR rows. Its confirmation names the targeted items. Visibility changes, merges and branch deletion have stronger typed confirmations in QUILL's administration flows, and Delete Repository in Explore (both apps) needs the repository's full name typed. QUILL Lite currently shares the Items, Explore, diff, and review surfaces; the separate repository administration and Local Git menus still belong to QUILL. This product difference is tracked in the workbench plan.

Architecture and verification

The Items and review windows use quill/core/github/items_provider.py and pr_review.py; review resolution uses review_graphql.py, line mapping uses diff_hunks.py, and job log retrieval uses workflow_job_logs.py. Explore uses explore.py; pinned repositories, favorites, recent repositories, and saved queries use saved_items.py. Notifications triage is notification_triage.py and explore_notifications.py; the failure digest is run_failure_digest.py; run, check and deployment actions are run_actions.py; auto-merge and the merge queue are merge_automation.py. Wave 3 adds repo_files.py (folders, files, README, history, blame), milestones.py, discussion_actions.py, alert_triage.py and github_graphql.py, whose GraphQL calls go through the same REST transport. Wave 4 adds search_views.py, repo_insights.py, repo_actions.py, release_admin.py, issue_housekeeping.py, rate_limits.py and conditional_requests.py, with Explore's routing in explore_extra_views.py. The last four add copilot.py, commit_comments.py, gists.py and attention_queue_summaries.py. The REST calls PyGithub lacks go through rest_transport.py, which refuses redirects so the token stays on api.github.com. The shared UI modules are under quill/ui/. Network calls are made off the UI thread. Tests exercise provider mapping, pagination, diff-line matching, redirect token handling, and action routing. Manual Windows screen-reader acceptance with NVDA, JAWS, and Narrator is user-owned follow-up. This reference does not claim a macOS assistive-technology acceptance matrix.

GitHub words

  • Actions: GitHub's automation: workflows that run on events, such as a push.
  • Artifact: A file a run produced and kept, to download.
  • Assignee: The person an issue or pull request is given to.
  • Branch: A line of work: a name that follows the newest commit of one set of changes. Under Code, Branches.
  • Branch protection: Rules that decide who may change a branch and what a change needs.
  • Cache: Files Actions keeps between runs to make them faster. Under Actions, Caches.
  • Check: A test or other run that reports passing or failing on a commit.
  • Codespace: A computer in the cloud with the repository ready to work on. It can cost money.
  • Collaborator: Somebody given access to one repository.
  • Commit: A saved change, with a message saying why. Under Code, Commits.
  • Deployment: Code sent to an environment, such as a website.
  • Discussion: A conversation in a repository that is not an issue.
  • Draft: A pull request that is not ready for review yet.
  • Environment: A named place code is deployed to, with its own rules and secrets.
  • Favorite: An item kept on this computer under Repositories, Favorites.
  • Fork: Your own copy of somebody else's repository, from which you can propose changes back. Under People, Forks.
  • Gist: A small shared file or snippet, with its own history.
  • Inbox: The Workbench's one list of what needs you, made from notifications, review requests, assignments and mentions.
  • Issue: A note about a bug, an idea or a task, with a conversation under it. Under a repository's Issues.
  • Job: One part of a run, on one machine, made of steps.
  • Label: A coloured tag on issues and pull requests, such as bug. Under Labels.
  • Mention: Your login written with an at sign, such as @you, which notifies you.
  • Merge: Bringing a pull request's changes into the branch it targets. Item, Merge, Ctrl+Shift+Enter.
  • Milestone: A goal with a due date that issues and pull requests belong to.
  • Notification: GitHub telling you something happened on a thread you are part of. Under Needs My Attention.
  • Organization: An account many people share, which owns repositories and teams.
  • Pin: A repository kept on this computer under Repositories, Pinned.
  • Project: A board or table for planning issues and pull requests.
  • Pull request: A proposed change: commits on one branch that somebody asks to merge into another, with a review. Under a repository's Pull Requests.
  • Rate limit: How many requests GitHub allows an account each hour. Account, GitHub API Rate Limit, Ctrl+Shift+L.
  • Rebase: Replaying commits on top of another branch, so the history reads as one straight line.
  • Release: A published version, with notes and files to download. Under a repository's Releases.
  • Repository: A project's folder on GitHub: its files, their history, and its issues and pull requests. Under Repositories in the tree.
  • Review: Reading a pull request's changes and approving them, asking for changes, or commenting. Enter on a pull request.
  • Role: What somebody may do: read, triage, write, maintain or admin.
  • Ruleset: A newer, named set of branch and tag rules that can cover many branches.
  • Run: One time a workflow ran, with its jobs, steps and logs. Under Actions, Runs.
  • Saved search: A search kept on this computer, to run again. Under Saved Searches.
  • Secret: A value, such as a password, that workflows use and GitHub never shows.
  • Security alert: A warning that code, a dependency or a secret in it is at risk.
  • Squash: Merging a pull request as one single commit, instead of all of its commits.
  • Star: A bookmark on a repository, which also shows you like it.
  • Tag: A name for one particular commit, usually a version number. Under Code, Tags.
  • Team: A group of people in an organization, given access together.
  • Triage: The role that may label, assign and close issues, but not push code.
  • Upstream: The repository a fork was copied from. Under Code, Upstream, on a fork.
  • Variable: A value workflows use that is not secret.
  • Watch: Asking GitHub to tell you about a repository's activity.
  • Workflow: One automation, defined in a file in the repository. Under Actions, Workflows.
  • Workflow dispatch: Starting a workflow by hand, on a branch you choose.
