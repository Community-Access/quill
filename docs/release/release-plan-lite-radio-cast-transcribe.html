Releasing QUILL Lite 2.0, Quill Radio 3.2, QUILL Cast 2.0 and QUILL Transcribe 1.0

Everything to do, in order, to publish these four apps as general (Stable) releases. Written 2026-10-24 from main at the commit that added this file. The general process is QUILL Release Process; this page applies it to these four apps and says which parts are already done.

Steps marked (you) need your accounts, your keys or a person at a screen reader. Everything else is a command you run in PowerShell at D:\QUILL.

Step 1: one-time setup (you)

Only what these four releases need. The Dev-build setup in RELEASE.md (the DEV_BUILDS_TOKEN secret, the dev-builds repository) is not needed.

  1. Restore the feed-signing key. Every publish and promotion signs the app’s update list with it, and it is not on this computer: neither C:\Users\jeffbis\.config\quill\quill-feed-priv.key nor QUILL_FEED_KEY_FILE exists. Put the key file back at that path, or set QUILL_FEED_KEY_FILE to where it is. It is the same key as the v1 feed’s (QUILL_FEED_SIGNING_KEY in CI). Never commit it.
  2. Code signing (done 2026-10-24: python scripts/code_signing.py doctor says “Ready to sign” and a test signature verified). Stable is always Authenticode-signed, at build time. On another computer, the Azure Artifact Signing steps are in docs/code-signing.md; in short:
    • install the client tools once (may need an administrator): winget install -e --id Microsoft.Azure.ArtifactSigningClientTools;
    • confirm the account, identity validation, certificate profile, and that your Entra ID user has Artifact Signing Certificate Profile Signer;
    • check metadata.json at the repository root names your endpoint, account and profile (it exists; see docs/code-signing.md);
    • in a normal (not elevated) PowerShell: az login, then az account set --subscription "<subscription-id>".
  3. GitHub. gh auth status shows you signed in with access to Community-Access/quill.
  4. Only if you will promote from GitHub rather than your computer: create the Environment stable-promotion with yourself as reviewer, and allow Actions to create and approve pull requests (Settings > Actions > General).

If an inventory gate stops it anyway, something on this computer has changed: follow Building the QUILL Windows family, and never rebaseline a package you cannot explain.

Code signing was proved on 2026-10-24: a test program signed through scripts/code_signing.py verified as Valid, signed by Jeffrey Bishop (Microsoft ID Verified CS AOC CA 04), with a Microsoft timestamp.

Check the signatures before going further: every installer and every program in each portable zip must say Valid.

Get-ChildItem dist\release-builds -Recurse -Include *.exe |
    Get-AuthenticodeSignature | Select-Object Status, Path

Everything lands in dist\release-builds\<date-time>\upload, with SHA256SUMS.txt.

Step 4: test, and sign off (you, or your testers)

  1. Two-minute smoke test of each, on a computer without the apps: install or unzip, start it, and:

    • QUILL Lite: open a .docx, type, save, reopen; open a text PDF and a scanned PDF (answer Yes to OCR).
    • Quill Radio: play a station; start and stop a recording.
    • QUILL Cast: play an episode; search the Podcast Index.
    • QUILL Transcribe: dictate into Notepad; transcribe a short recording.

  2. Screen-reader testing, then a sign-off sheet per app. Promotion to Stable refuses an app without one. A sheet is ready for each, to fill in:

    • docs/qa/signoffs/quilllite-2.0.0.md
    • docs/qa/signoffs/radio-3.2.0.md
    • docs/qa/signoffs/cast-2.0.0.md
    • docs/qa/signoffs/transcribe-1.0.0.md

    Set Result: pass only when the tester has done the checks it lists; the open screen-reader checks are in docs/qa/screen-reader-checks-2026-10.md. Commit and push the sheets.

Step 5: publish all four to Beta

Each app’s “What’s new” is already written, in docs/release/whats-new/. It is what people read in the update window when Check for Updates offers the build, and the GitHub release’s text, so it is short enough to show whole (the window stops at 60 lines or 4,000 characters, and tests/unit/docs/test_whats_new_fits.py fails a file that would be cut). It puts anything to do before updating first: portable QUILL Lite 1.1.2 and Quill Radio 3.0.4 must update by hand this once. Rehearse, then publish:

Each creates a GitHub prerelease, uploads the files, lists the build on Beta and signs the list. These are the first update lists for all four apps (docs/site/updates/v2/ does not exist yet); until they exist the apps keep using the GitHub path. Commit docs/site/updates/v2 and push to main; the website republishes within minutes and Beta users are offered the builds.

Then update one portable copy and one installed copy of each by hand, and read apply-update.log in the app’s updates folder.

Step 6: soak on Beta (7 days)

Promotion refuses a build that has been on Beta for less than seven days. A shorter soak needs a reason, recorded in the list: --skip-soak "the reason".

Every check prints PASS, WARN or FAIL, and one FAIL stops it: the files download with the hashes in the list, the list’s signature, a signed build that was on Beta, the changelog, the sign-off sheet, and the documentation gates. The --notes-file keeps Stable’s “What’s new” the same as Beta’s. Without it, the notes are rolled up from the changelog, which for these first update lists runs far past what the update window shows (QUILL Lite’s would merge every section back to 1.0.0). Commit docs/site/updates/v2 and push.

Step 9: afterwards

  • Watch the support inbox (FreeScout) for the first days.

  • After one full release cycle with every app on channels, remove the old v1 feed key from CI (RELEASE.md, “The old v1 list and its CI key”).
